# Agent Note: 幂等改成两阶段 —— 契约说"不得先执行再记录"，而我上一版正是那么做的

Status: implemented（取代 `.agents/notes/archived/2026-10-01-idempotency-wiring.md`）

## Problem

接第一个**写方法**（`session.prompt`）之前复核契约 §5.6，发现我第 3 轮的实现与它相反：

> **写入顺序是两阶段**：① 先落盘 `in-flight` 标记 → ② 执行 → ③ 成功后改写为 `done` + 结果引用。
> **不得先执行再记录** —— 那样崩溃窗口里会丢幂等。去重表写入失败（落盘报错）时**拒绝该写操作**，
> 不进入执行阶段。

而当时的实现是：执行 → 成功后写 `done`；**不写 `pending`**；落盘失败也照回应答。
当时的论证是"重复执行对带键的四个方法都安全（下游各自幂等/去重）"。

那条论证**不是错的，但很脆**：它依赖"带键方法就这四个"这份清单，而清单会随新增方法腐化
（我把它写进了笔记，但没人会在加方法时被强制回到那份清单）。更实在的是它有一个**真实漏洞**：
桥接与 DSH **都**重启之后，那次"执行了但没记下"的写操作在两边都没有痕迹 ——
重发就会产生第二条消息，正是 I8 要防的事。

## Decision

按契约改成两阶段，并把"失败"分成两类（这是本轮真正新增的判断）：

| 情形 | 处置 | 为什么 |
|---|---|---|
| `pending` 落盘失败 | **拒绝该写操作**，不执行 | 执行了却没痕迹 = 重发即重复 |
| handler 回**结构化失败**（`ok:false`） | 清掉 `pending`，重发可重来 | 这是方法自己在说"没生效"，我们**知道**结果 |
| handler **抛异常** | `pending` **留在表里**，重发**被拒**（`internal` + 让手机刷新） | 我们**不知道**它有没有生效 |
| 结果（`done`）落盘失败 | 应答照回，该键停在 `pending` | 执行已经生效、改不回去；停在 pending 至少不会重放 |

"抛异常"与"回失败"必须分开：前者是**我们不知道**，后者是**方法告诉我们没成**。
上一版把两者都当"不记"，于是崩溃窗口与普通失败混成一个形状。

**核对（reconciliation）还没做**：契约说停在 `pending` 的键要在启动时向 DSH 核对
（该 `requestId` 是否已随 `user/message` 落在会话日志里，`packages/api/session-controller/src/commands.ts:329-335`），
已生效的改写为 `done`、未生效的退回可重发。在它落地之前，这里选 **fail-closed**：
拒绝重发 + 提示刷新。代价是极端情况下用户要自己重发一次；收益是**绝不产生第二条消息**。

准入门槛（可机械判定）：

1. 执行的那一刻，表里已经有 `pending`（断言"两阶段顺序"，而不是断言最终结果）。
2. `pending` 落盘失败 → 抛错，且**执行闭包一次都没被调用**。
3. handler 回失败 → 表清空，重发真的重来。
4. handler 抛异常 / 结果落盘失败 → 行停在 `pending`，重发被拒且**不执行**。

## Alternatives considered

1. 保持上一版（不写 `pending`，崩溃窗口重放）
   - 最强的理由：那时已经论证过"四个带键方法重复执行都安全"，而且少一次落盘；
     再加"DSH 自己按 requestId 去重"这层，常见场景确实不会重复。
   - 为何被否：那层论证的**前提会腐化**（清单要人肉维护），而它保护的正是 I8 这条硬不变量。
     更要紧的是它有一个真实漏洞：桥接与 DSH 都重启后，重发会真的产生第二条消息。
     规格给出的两阶段方案不依赖任何"下游恰好幂等"的假设 —— 它把安全性放在我们自己的落盘顺序上。
2. 折中：写 `pending`，但重发时把 `pending` 当"没生效"直接重放
   - 最强的理由：不用等核对就能自愈（重放对我们的方法大多安全），也少一个错误路径。
   - 为何被否：那等于把上一版的漏洞原样保留（`pending` 只成了装饰），
     却多付了一次落盘。要么按契约作答，要么别写这一行。
3. 现在就实现完整核对（启动时扫 `pending` 并向 DSH 核对）
   - 最强的理由：那样连 fail-closed 的代价也没有了，用户不必手动重发。
   - 为何被否：核对要回答"这个 requestId 是否落在**哪个会话**的日志里"，而当前的去重行
     只存 `{at, status, resultRef}` —— 它不知道会话。要做得先把 `sid`（或整条请求指纹）
     写进行里（落盘格式变更 + 迁移），再定"核对不出来时"的退路。这是一块独立的工作，
     值得单独一轮，而不是塞进"接一个方法"里顺手做完。

## Consequences

- 收益：安全性不再依赖"哪些方法恰好幂等"这份会腐化的清单；崩溃窗口从"会重复"变成"会被拒绝"；
  `pending` 行本身成了那个窗口的可观测痕迹（日志里能看到）。
- 代价：每个写操作多一次落盘；极端情况（结果落盘失败 / 崩溃窗口）下用户需要刷新后重发一次。
- **仍未做的两件**（都写进了 `memory.md`）：
  1. **启动核对**（契约 §5.6）：把 `pending` 的键向 DSH 核对成 `done` 或退回可重发；
     需要先决定去重行里要不要落 `sid`（落盘格式变更 + 迁移）。
  2. **`session.prompt` 本身**：它是第一个真正的写方法，本轮先把它的前置修对了，
     方法本身下一轮接。
