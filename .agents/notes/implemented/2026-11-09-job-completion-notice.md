# Agent Note: 后台任务结束要各自提醒，窗口 30 分钟、按 jobId 去重

Status: implemented

## Problem

通知只有三类：审批、提问、"这一轮跑完了"。**任务不是轮次**：一个 10 分钟的 `bash`
任务结束时，那一轮可能还要再跑二十分钟，甚至这一轮里同时有三个任务在跑。于是
"任务结束"这件事在手机上没有任何表达 —— 用户退到后台，唯一能等到的信号是整轮结束。

任务表本身就在手上（`_jobs[sid]` 是会话级的 `JobRow` 列表，`finishedAt` 是电脑侧的真实
时间），所以这不是缺数据，是缺一条派生。

## Decision

在 `_desiredNotices()` 里加第四类：**任务行落了终态、且 `finishedAt` 在 30 分钟内** ⇒
贴一条 `NoticeKind.completed` 通知。

准入门槛（可机械判定）：

1. 通知 id = `noticeIdOf(_noticeKeyOf('job', job.id))`：从 jobId 算（同一任务只贴一条），并带电脑前缀（两台电脑的 jobId 撞名时互相撤不掉）。
2. 只有 `finishedAt != null && !isLive` 且 `now - finishedAt <= 30 分钟` 才进期望集合；运行中 / 无结束时间 / 过期的一律不进。
3. 两条写路径都要触发重算：任务快照（`refreshJobs` → `_mergeJobSnapshot`）与 `job` 帧的 `JobOpened` / `JobStatus`。`JobOutput` 帧不触发 —— 它按 chunk 到达，跟着重算只是浪费。
4. 标题用既有的 `statusText`（`后台任务已完成 / 失败 / 已停止 · <label>`），不新造状态词；正文取 `detail` 前两行，没有就退到 `progress`，再没有才用一句"点开查看详情"。
5. 测试覆盖四条：快照路径贴一条（标题/正文/id）、同 jobId 重复推只贴一条、30 分钟窗口与运行中任务、失败任务标题不冒充"完成"。

## Alternatives considered

1. 只靠会话级"跑完了"通知，不为任务单开一类
   - 最强的理由：一条判据都不用加，`completionUnread` 已经存在，通知也不会变多。
   - 为何被否：整轮结束才提醒。长任务结束时用户正盯着别的东西，而"这一轮还没完"意味着这条提醒可能永远不会在任务结束后出现。
2. 给"30 分钟后撤销"配一个 `Timer`
   - 最强的理由：窗口语义精确，到点就撤，不依赖别的事件。
   - 为何被否：多一个定时器就是多一份状态（进程被杀就丢、重连后要重建）。撤销跟着下一次"期望集合"重算足够了 —— 一条过期通知多留一会儿不会误导人，而多一个计时器会。
3. 同一会话的任务合并成一条「N 个任务结束」
   - 最强的理由：任务多时通知不刷屏。
   - 为何被否：任务身份丢了，"点开查看"要对准哪一个？jobId 去重已经保证"同一个任务只有一条"，剩下的"三个任务同时结束"是真实发生的三件事。
4. 整段照搬参考实现（`refs/remotes/pr/8:a4a9775`）
   - 最强的理由：省一轮设计，那份代码已在 0.2.x 上跑过。
   - 为何被否：它写在池化与电脑前缀之前 —— 通知 id 是 `job:${job.id}`，两台电脑的 jobId 撞名会互相撤销；它也没有"输出帧不重算"的成本考虑。语义照抄，结构不能照抄。

## Consequences

- 收益：任务结束有了独立提醒；同一任务永远只贴一条（id 从 jobId 算），跨台不互相撤销；冷启动不会把历史任务全部补贴一遍。
- 代价：`_desiredNotices()` 每个会话多扫一遍任务表（几十行量级，且只在既有重算点上跑）。
- 代价：多个任务同时结束会连贴几条（未合并）；这是为了保住任务身份而选的行为，不是遗漏。
- 代价：30 分钟是"提醒窗口"，不是"任务存在时间" —— 过期任务仍留在任务面板里，只是不再提醒。
