# Agent Note: 握手接在连接上 —— 驱动器注入，连接层只给一条「只放握手帧」的出帧路径

Status: implemented

## Problem

`connection.ts` 从落地起就有一个 `markHandshakeDone()`，而**没有任何东西会调它**：
握手三帧的组装、校验、派生各自在协议层测过，却没有一条路径把"连接进入 `handshake` 态"与"开始握手"接起来。
更硬的一层障碍是 `send()` 在 `serving` 之前恒返回 `false` —— 也就是说握手帧**根本发不出去**。

这个洞在单测里看不见：单元测试直接把帧喂给零件、或者把 socket 桩递给 `send()`，
两边各自自洽；只有"连接 + 真对端"合起来才断。

## Decision

握手由**注入的驱动器**（`protocol/handshake-driver.ts`，只做应答方）承担；
`transport/connection.ts` 只做三件事：进入 `handshake` 时启动它、给它一条**只接受握手帧**的出帧路径、
在它报成功后进 `serving` 并把会话密钥交给上层（`onEstablished`）。没有配驱动器时连接停在 `handshake`，
`markHandshakeDone()` 留给测试与"还没接驱动"的装配。

准入门槛（可机械判定）：

1. 驱动器内**没有 initiator 分支**：发起方永远是手机（`hello` 由它发）。多一个走不到的分支，
   将来会被误读成"协议支持双向发起"。
2. 握手阶段唯一的出帧路径用 `isHandshakeFrame` 判定，非握手帧被拒并留声；业务帧在 `serving` 前恒 `false`。
3. 两道校验（`verifySignature` + `verifyConfirm`）都过才 `deriveSessionKeys`，顺序不可颠倒；
   任何失败都走 `failed` → 连接层关闭（关闭码 4003），**不重试、不降级**。
4. 握手帧不占 `fc`：握手成功后第一帧业务帧的 `fc` 仍是 0（e2e 断言）。
5. 空闲计时收帧与发帧都重置（§2.2「任一方向」），**唯一例外是 `ping` 自己** ——
   它若也重置，空闲期永远攒不满两个周期，半开再也判不出来（有专门一条 e2e 盯它）。

## Alternatives considered

1. 把 `send()` 的门禁放宽到握手期
   - 最强的理由：改动最小，一处判断就能让 `hello-ack` 发出去，不必新增内部路径。
   - 为何被否：那等于给"握手期发业务帧"开口子，而 §2.2 的握手门禁正是要拦住它。
     放宽后 `send()` 的返回值不再表示"现在能不能发业务帧"，上层据此排队/丢弃的逻辑随之失真。
2. 让连接层自己实现握手（把身份、设备表都塞进 `connection.ts`）
   - 最强的理由：少一层注入，接线更直白。
   - 为何被否：`transport/` 会被钉死在"必须知道设备表与长期私钥"上，
     于是一大块安全关键逻辑（验签、派生顺序）落进一个已经有定时器/退避/攒批的文件里，
     而它恰恰是最需要被单独测的那部分。
3. 握手失败后不关连接，原地重试一次
   - 最强的理由：省一次退避重连，弱网下体感更快。
   - 为何被否：§4.1 明写「握手失败不计入业务重试次数」，且重试必须**换一套临时密钥**才安全
     （复用会让 `fc` 从 0 重数 ⇒ nonce 重用）。关掉连接重来天然满足这两条，原地重试两条都要另写。

## Consequences

- 收益：握手真的跑在连接上（连接级 e2e：真 WebSocket + 手机侧独立替身，两侧派生的密钥能用同一把 `kA2B` 往返）。
  `serving` 只能由"两道校验都过"推进，手动的 `markHandshakeDone()` 退化成测试专用入口。
- 代价：`ConnectionOptions` 多两个字段（`handshake` / `onEstablished`），连接层多一条内部出帧路径；
  会话密钥目前交给上层后**没有消费者**（方法面与业务帧 AEAD 尚未落地），这一点在 `index.ts` 里如实注明。
- 附带修正：原先 `write()` 在 `socket.send` 成功后才算"发了一帧"，但**没有重置空闲计时** ——
  §2.2 说的是"任一方向"，而 `keepalive.ts` 的契约是"收到或发出任何帧时调用"。
  现在写成"发帧也重置，`ping` 除外"，并由两条 e2e 分别盯住两半。
