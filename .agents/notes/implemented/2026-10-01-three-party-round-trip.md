# Agent Note: 三方往返通了 —— 发一句、回一句（真 socket + 真票）

Status: implemented（`tests/relay-transport-seam.test.ts` 的那条往返用例）

## Problem

第 45/47 轮分别打通了"设备经中转抵达连接器"与"无 `sid` 帧的绑定路由"。
但**反向**那条路一直没有被真 socket 覆盖过：连接器发一帧，中转要按"谁是这条 `sid` 的听众"
投回设备 —— 而听众集合是设备**先说过话**才登记的（`routing.fromDevice`）。

## Decision

一条往返用例，把两个方向都钉住：

```
设备(带票 WS) --req--> 中转 --req--> 连接器(真连接层, onFrame 里回 res)
设备(收到 res) <--res-- 中转 <--res-- 连接器
```

覆盖到的：
- **正向**：设备侧无 `sid` 归属时的登记（`req` 到达连接器的 `onFrame`）；
- **反向**：中转按听众集合把 `res` 投回**设备**（这条以前只有进程内的大脑单测覆盖，
  真 socket 上没有）；
- **帧的分层语义**：`res` 的 `id` 与请求相同（手机据此配对请求与应答）、`sid` 原样保留；
- **行级分帧**：设备那一帧以 `\n` 结尾（第 45 轮的教训，这里就地写了注释）。

**没有覆盖**（说清楚，免得把这条用例当成"端到端都通了"）：
- **密码学**：连接器侧是**明文通道模式**（`markHandshakeDone()`），所以这三帧没有封箱、没有 AEAD；
  握手与封箱各自在 `connection-*.test.ts` 与 protocol 卡片里被测，但"经中转的握手"还没有；
- **方法面与 DSH**：连接器回的是最小应答，不是真 `session.prompt`
  （真方法面 + 真幂等有另外的 e2e，见 `.agents/notes/implemented/2026-10-01-session-prompt.md`）。

## Alternatives considered

1. 直接写"带密钥的完整三方链路"（配对 → 握手 → `session.prompt` 往返）
   - 最强的理由：一步到位，就是"真机发一句"在代码层面的等价物。
   - 为何被否（**暂时**）：它需要把手机端替身（`support/phone.ts`）从"直连一个测试服务器"
     改成"带票连中转"，再接上握手驱动器与 handler 表 —— 那是一次跨三层的装配改动。
     先用本条把**路由的两向**钉住，那个改动就只剩"换一条传输"，风险小得多
     （第 45 轮的教训正是：跨越三层的改动里，最难的往往是最不起眼的一层）。
2. 用 fixture 的 `start()` 直接连中转（改动最小）
   - 最强的理由：复用现成的连接层 + 手机替身 + handler 表。
   - 为何被否：`start()` 里手机是**绑定在测试服务器**上的（peer），要把手机改绑到中转的
     socket 上，仍是一次实打实的装配改动 —— 与 1 是同一个改动，只是说法不同。

## Consequences

- 收益：中转的**两向路由**都有真 socket 证据；"发一句、回一句"在传输层成立。
- 代价：这条用例连接器侧跑在明文模式，所以它**不能**替代密码学用例（已在上面写明）。
- **仍未做（下一步）**：
  1. **带密钥的三方链路**：手机替身带票连中转 + 握手（复用 `support/phone.ts` 与握手驱动器）
     —— 这是"真机发一句"的最后一段；
  2. 手机端 Dart 客户端（需要 Flutter 工程）；每连接状态那个岔口。
