# Agent Note: 端点全失效时说准"连不上"，稳定锚点交给部署层

Status: implemented

## Problem

端点表早就能自愈：连上之后 `endpoint.describe` 把连接器**实际绑定的地址**
全部报回来（`connector/src/transport/listener.ts` 的 `urls` 枚举非内置网卡），
IP 变了下一次经中转连上就刷新。但有一个洞：**每一条端点都失效时，手机没有任何
信道去问新地址**（电脑换 IP 后中转地址也跟着失效——本部署里中转就在电脑上），
而此时界面说的是：

- 连接 sheet / 顶栏只有"连接不上"（`ConnectionStateView.gaveUp`）；
- 对话页空态更糟：配对后没连上时落到"**还没有会话** · 在电脑上用 DSH 开一个"——
  把"拨不通"表演成"电脑上没有会话"，而用户的下一步动作完全不同
  （2026-10-16 真机实测复现：换地址后空屏显示"还没有会话"）。

而拨号结果其实**已经在手里**（`EndpointTransport.onAttempt` →
`AppModel.attemptOf`，本轮刚接上），只是没有人把它说给用户听。

## Decision

分两层，代码层只做"说准"，稳定锚点交给部署层：

1. **连接状态是空态的头条**（`ui/chat_page.dart` 的 `_EmptyChat`）：
   配对但没连上时说 `connectionLabel(state)`（"已断开 / 重连中… / 连接不上"），
   不再说"还没有会话"；协议错误/诊断退为详情行。
2. **全部端点都拨不通时给一句诊断**（`connectionSummary` 的 note）：
   `N 个端点都拨不通（电脑可能不在线，或换了网络地址）`。
   准入门槛（可机械判定）：端点表里**每一条**都有失败记录才说；有"从没拨过"的
   条目时不说（可能是刚启动、第一轮还没跑完）；拨通过的条目在时不说。
   出路照旧是空态里那枚"重新配对（换一台电脑）"（议题 3 的 ≤2 步判据不变）。
3. **稳定锚点是部署选择，不是代码缺口**：电脑换 IP 要"无感"，正道是让
   `relayUrl` 指向一个**不随电脑 IP 变的地址**——Tailscale 两端（稳定 100.x，
   代码早已放行 CGNAT 直连，`isPrivateOrLoopback`）或把中转搬到局域网里一台
   稳定主机。手机换到外网同理：只有"两端都能到达的汇合点"能救，
   重新出码救不了（二维码里的 `relay:` 还是那个局域网地址）。
   结论写进 `memory.md` 的待办，代码不做对应分支。

## Alternatives considered

1. 连接器在局域网上广播"我在这儿"（UDP beacon，手机失败时听 3~5 秒）
   - 最强的理由：同局域网内电脑换 IP 真的能做到无感，且**不引入任何依赖**
     （`node:dgram` 内置；手机侧 `RawDatagramSocket` 在 `platform/` 层，
     不碰 `core/` 的纯净）；安全上也干净——beacon 只是路由提示，
     伪造地址过不了握手（电脑公钥配对时钉死）。
   - 为何被否：① 只救"同网段"这一种，且**AP 隔离（访客 WiFi 常见）会静默失效**
     ——项目纪律不接受"看起来能发现、某些网络下默默不工作"；② 电脑上多一个
     常驻广播器，又多一处要配/要关的面；③ 它复制的正是 `endpoint.describe`
     已经在做的事（任一条连接成功后就全量刷新），价值只剩"从未连上过的首连"。
2. mDNS / Bonjour 零配置发现
   - 最强的理由：真正的零配置，且是行业标准做法。
   - 为何被否：2026-10-14 的端点笔记已否（App 侧要引依赖，撞选型闸门；
     Node 侧也要一个广播器），理由今天仍然成立，不重开。
3. 重配对时保留已学到的端点表（IP 漂回去能自愈）
   - 最强的理由：端点只是地址、不是秘密，"换电脑前学到的地址"留着无害；
     电脑 IP `.43 → .50 → .43` 漂回去时，重配一次之后就不再需要配。
   - 为何被否：① 恢复路径先清凭据再进配对页（`ConnectionRecovery.repair` →
     `PairingStore.clear`），要在清之前把表捞出来 threading 三层；
     ② 换过电脑之后，旧电脑的死地址会永远留在表里被反复试、并显示在设置页
     ——"手机只缓存不推断"的代价在这里变得可见。为一个小概率场景背两个代价，不值。
4. 手机设置里手填地址
   - 最强的理由：实现量最小。
   - 为何被否：2026-10-14 已否（把发现成本转嫁用户，IP 一变还得手改一遍），
     且本轮的端点列表 + 拨号记录已经让"现状可见"，不需要第二个入口。

## Consequences

- 收益：① 全部端点失效时，用户第一次看到的是事实（哪个状态、几条端点、
  都拨不通）和出路（重新配对），而不是"还没有会话"这种指向不存在动作的文案；
  ② 零新依赖、零新协议面——诊断全部复用本轮接上的拨号记录；
  ③ "电脑换 IP 怎么办"有了书面结论（部署层 Tailscale / 稳定中转主机），
  不再每次会话重新纠结。
- 代价：① 空态在"连接中 / 握手中 / 重连中"时也显示连接状态而不是
  "还没有会话"——这是有意为之（更诚实），但两条旧界面用例因此改成
  先进入服务态再断言（`widget_test.dart` 的 FakeClient 加了可选 `state`）；
  ② Tailscale 路线要用户装两端软件，是部署行动不是代码行动，本项目替不了他做；
  ③ 诊断文案里的"可能"是实话（拨不通的原因很多），不是结论——
  真要定位到"电脑换了 IP"需要比对子网，本轮不做（见下）。

## 这轮同时做的（同一议题的界面收尾）

  `EndpointTransport.onAttempt` → `AppModel.attemptOf` 记账、装配不变量补线

  **release** 包，而 debug/release 签名不同会**先卸载旧 App**——手机上的
  配对凭据存在 App 私有目录里，一卸就全没，必须重新扫码。要装 debug 必须
  `flutter install -d <序列号> --debug`。
