# Agent Note: 待处理按会话分桶(对齐 DSH 的 per-session),不自发明优先级

Status: implemented

## Problem

DSH 原生的待处理是 **per-session** 的,而我们手机侧是一个**全局单队**:
`TakeoverController._queue` 不分 sid,`active` 只取队首。电脑上并行开着几个
会话时,两个会话的审批/提问挤同一个队 —— 用户只看到队首那个,**切会话不切换
待处理,也没有"别的会话还有 N 个在等"的提示**。`InteractionItem` 本身带 sid
(答复时用了),是 UI 层没按它分。

## Decision

`TakeoverController` **按 sid 分桶**:一个会话一队,一次只处理队首(瀑布语义
不变);切到哪个会话就看哪个会话的队首。同一会话多个待处理按 DSH 的确定性
优先级排,**大的赢**。跨会话靠两处可见:会话行「N 个待处理」+ 本会话空着时的
一行提示。

准入门槛(可机械判定):

1. `enqueue` 按 `item.sid` 进桶;`active` 只从**当前会话**的桶取;
   `setCurrentSid` 换桶后原桶项不丢(用例钉)。
2. 同桶排序用 DSH 的优先级:**计划 2 > 提问 1 > 审批 0**(字面值,
   `ui-user-questions/.../index.ts:372` 与 `ui-approval/.../index.ts:89`)。
   变异校验:把优先级全改 0,「同一会话多个待处理按 DSH 优先级」那条必须红。
3. `settle(itemId)` **不带 sid、全桶找** —— 迟到收束可能属于别的会话。
4. 跨会话可见:会话行副标题含「N 个待处理」(本地从投影数);本会话空且
   `pendingElsewhere() > 0` 时渲染提示行。两者都有用例。

## Alternatives considered

1. **保持一个全局队,加一个"切换到下一个待处理"的按钮**
   - 最强的理由:改动最小,控制器几乎不用动。
   - 为何被否:那把"属于哪个会话"这个信息从 UI 上抹掉了 —— 用户看到一张卡
     却不知道它在哪个会话里,而答复是要带回 sid 的。DSH 原生就是按会话的,
     这是复刻,不是创新。
2. **铺成列表,一次看完所有会话的所有待处理**
   - 最强的理由:信息最全,不会漏。
   - 为何被否:原型的瀑布注释原话是"一次只处理队首",而**一次批准五件事
     等于没看**。列表形态把这个判据拆了。
3. **优先级按"审批最急"自己排**
   - 最强的理由:直觉上审批是"电脑卡在那儿等",比提问紧急。
   - 为何被否:DSH 已经定过这个次序(计划 2 > 提问 1 > 审批 0),而我们没有
     比它更强的理由。自创优先级会让两边行为对不上,而用户是在两个端之间
     切着用的。

## Consequences

- 收益:并发会话下"切换着做"成立,与 DSH 桌面行为同构;切会话不再把另一个
  会话的待处理弄丢或顶到眼前。
- 收益:跨会话可见(角标 + 提示行),用户知道该切去哪个会话。
- 代价:控制器从"一个 List"变成"一个 Map + 当前 sid",`active` 之类的 getter
  全部依赖"当前会话"这一前提;测试里 33 条回归用例统一改为先设当前会话
  (判据一行未改,只换构造口子)。
- 代价:待处理数在 `AppModel`(数据层)与 `TakeoverController`(UI 层)**各有一份**
  —— 前者管"列表告诉用户有几个",后者管"输入栏显示哪个"。故意不合并:
  数据层不认识 UI 状态机。两者同源(都是未决投影),可能有一帧的偏差。
