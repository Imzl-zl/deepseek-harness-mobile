# Agent Note: 会话增量缓冲 —— `persisted` 的方向,与"只有全部设备确认才裁"

Status: implemented（`session.buffer` + 入站 `persisted` + 重订走增量；`session.page` 仍未做）

## Problem

上一轮我在笔记与 `memory.md` 里记了一条"欠账":`persisted` 水位的来源没查清。查下去发现
**那条欠账本身立错了**——我把方向读反了：

> 契约 §5.5:`persisted { sid, seq }`:**手机落盘后才发**;电脑侧据此裁剪增量缓冲,并允许中转裁剪重放窗口。

也就是 `persisted` 是**手机 → 电脑**。而当时收帧开关把它归进了 `default` 分支,
按"电脑侧方向的帧"**告警**——手机照契约发来的东西被当成协议错误。真正的缺口是三件事:

1. **电脑侧根本没有增量缓冲**,所以"重订"只能每次灌一份完整快照（宿主 `follow` 一开流就给快照）。
2. **入站 `persisted` 没有处理人**（落到 default 告警）。
3. 于是 §5.5 的两条硬约束（16 MiB / 10000 条上限、只有全部配对设备确认才可裁）都没有实现。

## Decision

- **按 §5.5 实现增量缓冲**（`src/session-buffer.ts`）：每个被订阅会话一段，上限 16 MiB 或 10000 条；
  裁剪点 = **全部配对设备**落盘水位的**最小值**；未确认的部分永不裁剪
  （超限时先"只允许快照"，而不是丢事件）。
- **逐设备记水位**：入站 `persisted` 的设备身份**只能来自握手**（`onEstablished` 的 `devId`），
  不能来自帧内容——帧里的字段是手机自己报的，可以撒谎。
- **`record` 在 `send` 之前**：崩在"发了没记"之间会让缓冲缺一段（手机无法增量恢复），
  而崩在"记了没发"之间只是重订时多补发一条（手机按 seq 幂等）——两害相权取前者。
- **重订优先走增量**：`subscribe(since)` 先看缓冲覆盖不覆盖得到（连续且未超限），
  覆盖得到就**先补发那一段**，再开宿主流，并把快照里**重复的 seq 跳掉**
  （宿主不知道我们手里有什么，它照样会给一份完整快照）。
- **出站帧直接带序列化好的 `body`**：缓冲存的就是这个串，出帧也用它——一个事件只序列化一次。

准入门槛（可机械判定）：

1. 一台设备确认了、另一台没有 → **一行都不裁**（裁了慢的那台就丢那段）。
2. 乱序到达的旧 ack 不把水位拉回去。
3. 覆盖不到（裁过头 / 有洞 / 超限放弃）→ `tailFrom` 返回 `undefined` = **要求快照**，
   而不是"没有新事件"（两者混起来的表现是"手机永远停在旧内容上"）。
4. 非递增的 seq 不记进缓冲，并且**留声**（静默丢弃最难查）。
5. 重订时同一个 seq **绝不发两遍**（补发段与快照重叠的那部分要跳掉）。

## Alternatives considered

1. 单一水位（不分设备）
   - 最强的理由：实现最短，一张 `sid → seq` 表就够；而且多数时候只有一台手机。
   - 为何被否：契约说的是"**全部配对设备**都确认"。两台手机时，快的那台确认到 500 就会把
     慢的那台需要的 200..500 裁掉 —— 而慢的那台正是"刚重连、正要重订"的那台。
2. 按"已发出"裁剪（不等确认）
   - 最强的理由：内存立刻受控，不必等任何 ack；实现上也少一张水位表。
   - 为何被否：**发出去不等于对方写下去了**。手机写盘可能失败，而那时事件已经从我们手里消失，
     只能要求快照——把一个"本该增量恢复"的场景变成"重灌一份历史"。
3. 有洞时返回"空增量"或"洞之后的部分"
   - 最强的理由：至少把手上有的发出去，看起来更"尽力"。
   - 为何被否：手机据此以为"就这些"，从此**停在旧内容上**且永远不会自己发现 ——
     这是这一层最难查的失效形状（没有错误、没有告警）。所以宁可要求快照。
4. 缓冲存解析后的对象，出帧时再序列化
   - 最强的理由：补发路径可以直接复用 `expand()`，代码更统一。
   - 为何被否：要么每个事件序列化两次（`ev` 是高频的），要么内存里同时存对象与字符串。
     现在补发帧自带 `body`，`expand()` 为它加一个分支就够了。

## Consequences

- 收益：重订从"每次重灌快照"变成"增量补发"；缓冲的内存上界与裁剪规则按契约落地；
  入站 `persisted` 不再被当成协议错误告警。
- 代价：缓冲是**有状态**的且与订阅生命周期耦合（`session.unsubscribe` 之后仍保留，
  因为手机可能马上重订；目前只在插件卸载时随进程消失 —— 见下）；多了一张逐设备水位表。
- **仍未做的三件**：
  1. `session.page`（用开启帧的 `cursor` 当 `throughSeq`）。
  2. **缓冲的释放时机**：契约 §5.3 说 `session.unsubscribe` 之后"桥接可释放该会话缓冲
     (**仍需等 persisted**)"，而现在的实现**不释放**（只在卸载时消失）。要不要在"全部设备都确认过"
     之后释放，要单独定一次 —— 想清楚再动，别顺手加一个 `forget`。
  3. **`live` 帧不进缓冲**：断线期间正在流式输出的那一段会缺，靠宿主的 `end(committed)` 与随后的
     持久事件自愈（手机侧"流式被持久事件替换"那条规则本来就这么设计）。这条要在手机端落地时验证。

## 测试抓到的一个真缺陷

`tailFrom` 第一版只检查**头部**连续性（`head.seq > since + 1` 才算不连续），于是
"`1,2,5` 从 1 开始"会返回 `[2,5]` —— 中间少了 3、4，而手机拿到 `[2,5]` 会以为"就这些"。
测试专门为此写了一条（"中间有洞就要求快照"），它当场红。修法是把整个返回段都验证连续：
**要么给完整连续的一段，要么要求快照**。
