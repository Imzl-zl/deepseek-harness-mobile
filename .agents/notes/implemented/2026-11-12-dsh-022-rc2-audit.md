# Agent Note: DSH 0.2.2-rc.2 的适配体检 —— 结论是"不用改代码"，但方法要留下来

Status: implemented

## Problem

用户问「DSH 更新了，最新版还需要适配不」。这件事有三个层次，混在一起就会得出错答案：

| 层次 | 事实来源 | 这一轮的取值 |
|---|---|---|
| 用户在用的宿主 | 本机安装的 DeepSeek Harness（`tools.md` 的固定动作：量**实际安装的**版本） | **0.2.2-rc.1** |
| 我们能装到的最新宿主 | npm `next` dist-tag | **0.2.2-rc.2** |
| 参考源码仓库 | `D:\sudy\github\deepseek-harness` 的 master | `dsh-v0.2.2-rc.2` 之后 **166 个提交** |

我们 `connector/package.json` 钉 `0.2.2-rc.1`，`engines.dsh` 是 `>=0.2.2-rc.1 <0.2.3-0`。
所以真正要回答的是两个问题：

1. **rc.2 的宿主会不会装不上/装上了坏掉**（版本闸门 + 我们调的 API 还在不在）；
2. **要不要抬线**（把 devDeps/类型基线挪到 rc.2，重新验一遍）。

## Decision

### 结论：rc.2 不需要改代码；本机宿主就是 rc.1，今天零适配

版本闸门先验一遍（`semver.satisfies(..., {includePrerelease: true})`）：

| 版本 | 落在 `>=0.2.2-rc.1 <0.2.3-0` 里 |
|---|---|
| `0.2.2-rc.1` | ✓（本机安装的那个） |
| `0.2.2-rc.2` | ✓（npm `next`） |
| `0.2.2` | ✓ |
| `0.2.2-alpha.3` | ✗（预发布线不互通） |
| `0.2.3-0` | ✗（上界，刻意挡住） |

注意这不是"碰巧"：`<0.2.3-0` 这条上界本来就是为"整条 0.2.2 线（含 rc）"写的，见
`implemented/2026-11-05-connector-engines-upper-bound.md`。

然后是**接口面体检**。四类，全部机械核对（rc.1 标签 vs master HEAD）：

| 面 | 怎么查 | 结果 |
|---|---|---|
| 服务键（16 个） | 在 DSH 里找 `super(ctx, '<键>')` / `provide('<键>')` | 16 个全在 |
| 我们调的方法（20+ 个） | `sessionController` 9 个（list/follow/prompt/cancel/selectModel/create/fork/rename/modelCatalog/projections）、`pluginManager` 6 个（listPlugins/setPluginEnabled/listBundles/installBundle/removeBundle/cancelInstall）、`settings.describe/update`、`credentials.describe/readRecord`、`jobs.list/events.subscribe`、`commands.list/execute`、`permissionPresets.catalog`、`userQuestions.answer`、`subagents.prompt`、`fileReferences.list`、`agents.get/list` | 全在，签名未变 |
| 事件与端点 | `$events` / `$events/result`、`waterfall` 帧、两条 `mode: 'waterfall'` 条目、`peer.interactions` 默认 `'answer'`、`approval/asked{id,toolName,callId?,reason?}`、`tool/call{turn,step,callId,name,arguments}`、`plugin-manager/install-state|install-log` | 全在，形状未变 |
| 导出面 | 逐个包把 `src/**/*.ts` 的 `export (interface|type|class|const|function|enum)` 名字集取出来做差集 | 13 个包：11 个**零减少**；`dsh-subagent` 少 11 / `dsh-llm` 少 1，**都不在我们 import 的那几个名字里**（我们只用 `SubagentRuntime` 与 `LlmProviderInfo`）|

两个"看起来会红但实际不影响"的差异，记在这里免得下次重查：

- `packages/core/agent` 删掉了 `CreateAgentOptions.parentAgent` / `AgentEntry.owner`
  —— 那是**子智能体运行时归属**的内部字段，我们只调 `agents.get/list` 与 `subagents.prompt`；
- `packages/interaction/user-questions` 把「这个 agent 能不能答」的判据从
  `agents.roots().includes(agent)` 换成 `agent.session.header.origin === 'subagent'`
  —— 方向是**放宽**（历史 fork 恢复成新 root 后可以照常答），不会让我们少一条路。

### 「抬线」不做（这一轮）

抬线要改 18 个 devDep 的精确版本 + `engines.dsh` 下界 + lockfile，然后在**新宿主**上
重跑 `tsc` / `build` / `test` 与真机三条链（审批 / 提问 / 子智能体）—— 那是
`cookbook/release.md` §3 的一整轮流程，而它的收益只是"类型基线跟上"，不是"修坏了的东西"。
真正该做抬线动作的时机是**本机桌面端升到 rc.2 之后**（或用户报 rc.2 上的问题时），
那时"宿主实际安装的版本"自己会变，`tools.md` 的固定动作照做即可。

### 顺手修掉一条过期引用

`connector/src/dsh/question-call.ts` 引了 `packages/core/agent-loop/src/tool-calls.ts:165-213`，
而那个文件**在 rc.1 里就已经不存在**（2026-10-19 的 `refactor(tools): separate scoped executors
from tool registration` 把它拆进了 `core/tools`）。这不是 rc.2 造成的，但它违反了
「引用 DSH 行为要给 `packages/...:行号`」那条军规 —— 引一个不存在的文件比不引更糟。

- 调度（独占屏障 / 并行池）：改引 `packages/core/tools/src/batch.ts:109-122` 的 `runGroup`，
  并注明搬家那次提交；
- 崩溃尾的合成结果：`packages/core/session/src/repair.ts:18-29` 的行号已漂，
  改引 `:43-52` 的 `openTurnClosers`（"Unmatched calls receive error results first"）。

修完再扫一遍：`connector/src` 引到的 **90 个** DSH 文件，缺失 **0** 个。

| 判据 | 结果 |
|---|---|

| 引用文件存在性（90 个） | 修复后 **0 缺失** |
| `cd connector; pnpm exec tsc --noEmit` | 0 |

**这一批没有变异校验**：改的是两句注释里的引用，可执行判据是"引到的文件存在 + 那两个
测试文件仍绿"。真正该防的是"引了不存在的文件"，而它现在由上面那条扫描兜着
（手工跑，没有进门禁——见 Consequences）。

## Alternatives considered

1. **直接把 devDeps 抬到 rc.2，顺手占住"最新"**
   - 最强的理由：npm `next` 已经是 rc.2，早点对齐早省事。
   - 为何被否：我们**编译用的类型**与**实际运行的宿主**会因此分家（本机跑的是 rc.1）。
     类型基线比宿主新，会让"本机能编译、rc.1 宿主上崩"这类问题被掩盖 —— 与
     `tools.md` 那条"先量实际安装的版本"正好相反。等桌面端真的升上来再抬。
2. **把「引用文件存在性」做进门禁（`layering.test.ts` 里读 DSH checkout）**
   - 最强的理由：这条检查一年能省几次排查，而且它是纯机械的。
   - 为何被否：它要读仓库**外面**的路径（`D:\sudy\github\deepseek-harness`），
     而 CI 里没有那个 checkout —— 那条规则在 CI 上只能"扫不到 ⇒ 跳过"，就是一条
     永不作废的假绿。要做就得先决定"DSH 源码要不要进 CI"，那是另一个决定面。
3. **删掉 `question-call.ts` 里那句"取决于循环调度"的注释，只留结论**
   - 最强的理由：引用会漂，删了就一劳永逸。
   - 为何被否：那句话解释的是**为什么这里必须做成纯函数**（并发下认领不唯一 ⇒ 认不出就
     交还桌面），删掉就只剩一个"看起来多余的防御"。引用漂了该更新引用，不是删证据。
4. **等用户报问题再说，这次什么都不做**
   - 最强的理由：rc.2 上我们没有失败证据。
   - 为何被否：用户问的就是"要不要适配"，而"要不要"必须有可核查的依据 ——
     这一篇就是那份依据（下次问同一个问题，读这一篇 + 跑一次版本量法即可）。

## Consequences

- 收益：**rc.2 不需要改代码**这件事现在有证据（闸门 + 四类接口面 + 13 个包的导出差集），
  不是"我觉得没事"。下次宿主再升，照这张表重跑一遍即可。
- 收益：`question-call.ts` 的两处引用重新指到真实存在的文件与行号；`connector/src` 的
  90 个 DSH 文件引用零缺失。
- 代价：这篇笔记里有一张"哪些面要查"的表，但它**不是门禁** —— 靠人照着做。
  机械化的代价见 Alternatives 2（要读仓库外路径，CI 上会变成假绿）。
- 未做：抬线到 rc.2（等本机宿主升上去）；真机在 rc.2 上跑三条链与安装面
  （要真机 + 一次模型请求报价）；`tools.md` 的「DSH 升级后的固定动作」没有加"导出面差集"
  这条手法 —— 它已经在本文里，等真的抬线时再决定要不要写进 `tools.md`。
