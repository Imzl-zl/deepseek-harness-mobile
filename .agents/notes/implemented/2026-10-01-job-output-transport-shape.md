# Agent Note: 任务输出的传输形状 —— 新增 `job` 帧，而不是给 `live` 的字段加第二个含义

Status: implemented（传输底座；订阅注册表与 `job.follow` / `job.unfollow` 两个方法见下一轮）

## Problem

手机要"展开任务详情就看输出"，于是要把宿主的任务输出流送到手机上。接之前三处必须定清楚，
而三处都不能靠猜：

1. **输出走哪种帧？** 通道现有的事件类帧只有 `ev`（有序号、进重放窗口）与 `live`（易变流）。
2. **谁来做合并与限帧？** 任务输出是高频的；`ctx.jobs.events` **没有任何合并窗口**
   （append 一次发一次，`jobs-local/src/index.ts:523-524`）。
3. **满窗时怎么办？** 契约 §4.3 说可补帧"暂停而不是丢弃"，但当时**没有任何机制告诉发送方"窗口又空了"**。

## Decision

**新增帧类型 `job`**（`{ v, t:'job', sid, fc, box }`，无 `seq`），而不是复用 `live`。理由是三件事叠在一起：

- 契约术语表把 `stream` 定义成「一次 **assistant 尝试**的流 id」；
- 手机侧对 `live` 的读法是硬性的：`rev == last + 1` 追加、**`rev` 跳跃即丢弃整条流**
  （`docs/subsystems/app-channel-client.md:88-91`）；
- 任务输出的推进量是**输出字节偏移**（会跳号）。

把偏移塞进 `rev`，手机就会因为一次任务的输出而**丢掉正在渲染的 assistant 文本**。
而"给同一个字段第二个含义"正是本项目在 `credit` 那一处已经否掉的做法（§4.3：`fc` 不许有两个意思）

**内容照宿主一对一**：`jobController.follow` 已经实现了成熟的观察流
（`packages/api/job-controller/src/index.ts:90-96` 的 `observeJobOutput`；**100 ms 合并**与
**64 KiB 单帧上限**在 `:29,32`；三帧 `opened` / `output` / `status` 的形状在
`packages/api/job-controller/src/types.ts:62-92`）。插件不自己写观察循环，只做映射。
唯一新增的一帧是 `error`：宿主出错就是抛，而 `docs/plugin-and-jobs-notes.md` §B.4 要求
手机把"实时输出流中断"**显式渲染**出来，所以通道补一条明确的中断帧。

**满窗恢复信号 `whenWritable`**：`Connection.send` 满窗时**不接受**那一帧（如实回 `false`），
发送方必须压住它 —— 而"什么时候可以再发"只有连接层知道（`credit` 到达且窗口释放）。
补一个 `whenWritable(type): Promise<void>`（窗口释放时兑现；**离开服务态时也兑现**，
否则等在这里的发送方会永远挂着）。任务输出是第一个由调用方驱动的可补流，所以这个洞是它压出来的。

**顺带修掉一处两个真值源**：`protocol/frame.ts` 的 `FRAME_TYPES` 是旧的 8 项
（含 `credit` 之前的化石 `'ack'`，缺 `job`/`persisted`/握手三帧），而编解码另有一份 13 项的清单。
两份已经漂移：`RoutingView.t` 与 `window.canSend()` 看到的类型集合比实际小。现在真值只有
`FRAME_TYPES` 一份，`codec.ts` 的 `KNOWN_FRAME_TYPES` 只是沿用对外名字的别名。

**同一类的第二处也一并收掉**：「参与攒批的帧」与「满窗可暂停的帧」本来是两份集合
（`connection.ts` 的 `BATCHED_FRAME_TYPES` 与 `flow.ts` 的 `pausable`），而它们**必须是同一组** ——
不同的话会出现"可暂停但没攒批"或"攒批了却不受窗口约束"这种只在满窗时才现形的组合。
现在攒批直接由 `pausable` 派生（`isBatched = pausable`），漂移在结构上不可能发生。

准入门槛（可机械判定）：

1. **DSH 会话 id 不过线**：`JobView` 带 `owner`，三帧必须**逐字段重投影**（测试断言
   `JSON.stringify(frames)` 里不出现会话 id）。
2. `job` 与 `ev`/`live` 同类：参与攒批、满窗可暂停 —— 而这两件事**由同一个 `pausable` 决定**。
3. 适配器把宿主的 `job/not-found` 转成协议码（与 `kill` 同一条纪律），其余错误照原样上抛。
4. `job` 帧必须走 AEAD，且 AAD 里**确实带了 `sid`**（少了它，同一帧能被换一个会话重放）。

## Alternatives considered

1. 复用 `live`，把 `stream`/`rev` 借给任务输出
   - 最强的理由：零新增帧类型 —— 所有"易变流"的既有处理（攒批、可暂停、不回带、恢复时丢弃）
     自动覆盖任务输出，不必在几处枚举里各加一个成员。
   - 为何被否：代价落在**手机侧的既有不变量**上（见 Decision 的三条）。而且给一个已被占用的字段
     加第二个含义，正是 `credit` 那一处否掉过的做法；那次的教训是"两个意思的字段迟早会被
     按错的那个意思读"。
2. 用 `ev` 帧承载（有序号、可重放）
   - 最强的理由：能进重放窗口，手机断线恢复时输出也能补上，不必重订。
   - 为何被否：任务输出**不在会话的 `seq` 空间里**（它有自己的字节偏移），要塞进去只能
     自己造一个 `seq` —— 而 §5.1 明说修订号是 DSH 的、插件不分配。假 `seq` 还会污染
     会话的重放窗口与水位对齐（`persisted` 的判据）。
3. 插件自己写观察循环（订阅 `ctx.jobs.events` + `readAt` + 自己合并/限帧）
   - 最强的理由：不依赖 `jobController`（它由 `dsh-web-app` 提供，base 里没有），
     于是只装 base 的部署也能看输出。
   - 为何被否：那是把宿主已经做对的三件事（100 ms 合并、64 KiB 限帧、结算与输出同流以免竞争）
     重写一遍，而且 64 KiB 与 ring 的截断语义（§B.4 要求手机显式渲染 `gapBefore`）
     必须与桌面**逐字一致** —— 两套实现迟早对不上。`jobController` 已在同一 bundle 群里，
     缺它的部署就少一个方法（与 `job.kill` 同一种处理）。
4. 满窗时丢掉输出帧（反正能重订）
   - 最强的理由：实现最短，不需要新 API；任务输出本来就是"可补"的。
   - 为何被否：违背 §4.3 明写的"暂停**不是**丢弃"。丢帧会让手机看到中间少一段而没有
     `gapBefore` 提示（那个字段描述的是宿主 ring 的淘汰，不是通道的丢弃），
     于是"输出缺了一截"这件事变得不可观测。

## Consequences

- 收益：任务输出的形状定案且与宿主的成熟实现一对一；`whenWritable` 让"由调用方驱动的可补流"
  第一次有了正确的背压（压住一帧、等信号、重发），后续会话订阅可直接复用；
  帧类型清单回到一处，`RoutingJob`/`canSend` 看到的集合与契约一致。
- 代价：`protocol/job-output.ts` 自带一份 `JobChannelOut` 而不 import DSH 类型
  （分层规则：`protocol/` 不许依赖 `@deepseek-ai/*`，见该文件说明）。
- **仍未做**：`job-subscriptions.ts`（每个 `(sid, jobId)` 至多一个订阅、按下标重启、
  跟连接生命周期、逐帧背压）与 `job.follow` / `job.unfollow` 两个方法，以及它们的 e2e。
  本轮交付的是**传输底座**：形状定案 + 帧类型 + 适配器映射 + 恢复信号。

## 一次教训：用例「绿在错误的原因上」

给"窗口松开必须唤醒"写的第一版用例是 `await pending` 之后断言 `resumed === true`。
变异校验（把窗口松开那一处的 `notifyWritable()` 删掉）**没有让它红** —— 它跑了 **16 秒后依然通过**。
查下去：那个 promise 最终是被**连接自己断掉**时的另一处兑现唤醒的
（保活判定超时 → 离开服务态 → 那里也兑现），于是断言被满足了，而真正要测的机制已经缺失。

修法两条，缺一不可：**有界等待**（`Promise.race` 500 ms，超时即判失败）+
**断言唤醒发生在连接还活着的时候**（`state === 'serving'`，且醒来后重发那一帧要被接受）。
改完之后同一个变异在 0.9 秒内精确红。

这是本仓库第三次遇到"测试绿得不是地方"：前两次是**替身不忠实**（并发用例撞不上）与
**变异没改语义**（展开诊断行）。三次的共同点是：**证据本身需要被质疑** ——
断言表达的是"我关心的那条机制"，而不是"最后有没有个好结果"。
