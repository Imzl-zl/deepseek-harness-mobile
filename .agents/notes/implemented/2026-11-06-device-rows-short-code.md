# 设备行按配对身份保留：加短码、改列名，不按手机聚合

Status: implemented

## Problem

2026-11-06 真机，「已配对设备（3）」三行都叫「我的手机」，`配对于` 分别是 10/31、11/3、11/4，
`最后活跃` 全是「从未交互」、`状态` 全是「未运行」。用户问：

> 我的手机三个是真的三个吗？我直连过两个啊？你怎么识别的手机？

三行是三次扫码留下的三条**配对身份**（每次扫码新主种子 → 新 `devId`），不是识别错误；
但面板没有让人认出"哪一行是手里这台"的手段，两列的语义也没写清。

## Decision

**保留"每次配对 = 新设备身份"，不按手机聚合，也不改协议/存储。**

1. 电脑面板每行显示 `devId` 前 6 位的「设备短码」；手机「设置 → 关于与连接」显示同一个
   短码（`AppModel.deviceShortCode`）。用户据此认出"哪一行是手里这台"。
2. `最后活跃` 改名为「最近答话」：`lastInteractedAt` 只在手机答过一次审批/提问时更新
   （`presence.interacted`），不是"最后在线"；没答过就显示「还没答过话」。
3. `状态` 改名为「此刻连接」：它就是 `presence` 的内存态，连接器重启后清零；
   显示「未连接」不代表这一行废弃。
4. 面板加一句说明：每行是一条配对身份（重扫 = 新行）。

## Alternatives considered

1. **按手机聚合（持久化主种子，生成 stable phone id）**
   - 最强的理由：一台手机一条记录，管理面不再被重扫记录淹没；审计与停用语义更清晰。
   - 为何被否：`implemented/2026-10-15-new-identity-per-pairing-is-intentional.md`
     已经否过一次 —— ① "换身份"本来是安全上需要的动作，持久化后要另开入口；
     ② `putDevice` 整行覆盖且不带 `revokedAt`，重新配对会自动解禁旧行；
     ③ 用户当时明确要求保留"重扫换新身份"。这次没有出现推翻这三条的新事实。
2. **给设备行加持久化的 `lastSeenAt`（握手成功时写库）**
   - 最强的理由：能回答"这台上次连上是什么时候"，重启后仍有值；比改列名更有信息量。
   - 为何被否：`presence` 的契约就是**瞬时事实不落盘**（`remote-channel.md` §8.1），
     加字段要动设备表 schema 与迁移；而这次要解决的是"认不出哪一行 + 两列看不懂"，
     短码与改名已经够，没必要为一句文案改存储。列为将来的候选。
3. **显示完整 `devId`（22 位）**
   - 最强的理由：绝对无歧义，复制出来就能对照。
   - 为何被否：表格一行放不下，手机上更放不下；前 6 位在"一台电脑几十行"的规模里
     足够（36 bit），且与手机端同一算法。
4. **把三行合并成一行、只保留最新配对**
   - 最强的理由：列表最短，用户不会看到"三个手机"。
   - 为何被否：旧行是**仍然有效的凭据**（另一台手机可能还在用）；合并等于静默吊销，
     而吊销有明确入口（停用）。而且旧行删掉后，那台手机只会一直重试到重新配对。

## Consequences

- 收益：不动身份模型与协议；用户能对照短码认出当前这台；两列不再被误读成
  "最后在线 / 这台在不在跑"。
- 代价：重扫仍会增加行，要靠用户自己清理（这是既有决定的代价，不是本次新增）；
  6 位短码理论上有碰撞，但只在"几十行"规模内用于人眼对照，不参与任何判据。
- 证据：`connector/tests/client-panel.test.ts`（短码、列名、状态词）、
  `app/test/settings_page_test.dart`（手机端同一短码）。
- 契约：`docs/subsystems/remote-channel.md` §8.1 的瞬时状态与设备行说明。
