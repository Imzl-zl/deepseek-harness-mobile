# Agent Note: 发送模式(排队/插话)照搬 DSH 二选一,放输入区而非设置页

Status: implemented

## Problem

DSH 原生有"繁忙时的发送行为"二选一(排队发送 / 插话发送),它**穿过协议**:
取值决定这句话在会话忙时排到下一个轮次还是插进当前轮次。我们这边
`session.prompt` 协议层一直收 `mode: 'queue' | 'steer'`
(`connector/src/handlers.ts`,透到 DSH 的 `prompt(mode)`),但**手机 UI 没有这个
入口** —— 用户只能排队,插话那条路在手机上不存在。设置搬运清单里这项标的是
"搬",一直没搬。

## Decision

照搬二选一,但**形态有意偏离 DSH**:不做设置页那一行,而是放进**输入区控制行**
(第 4 个 34px 恒宽图标,与权限并列)。

准入门槛(可机械判定):

1. `session.prompt` 的载荷必须带 `mode`,取值只能是 `SendMode.queue.wire` /
   `SendMode.steer.wire` 两个**字面值**(与连接器的词汇表逐字一致,用例钉)。
2. 插话那一项在会话没在跑时**禁用**(置灰 + 点不动),不是"点了再报错" ——
   判据是 `DshPickerRow.enabled` 为 false 时不回调 `onTap`。
3. 偏好必须落盘(`meta` 表,`AppModel.kSendModeKey`),重启后 `start()` 读回;
   盘上是认不出的值时保持默认 `queue`,不猜。
4. 窄屏 360px 下控制行不许溢出(用例钉 `takeException()` 为 null)。

## Alternatives considered

1. **放进设置页(照 DSH 的形态)**
   - 最强的理由:与 DSH 逐屏一致,设置项搬运清单也是按设置页组织的。
   - 为何被否:**手机端的设置页还没做**(入口是"还没做"的 SnackBar),而这项
     `只在会话正在跑轮次时才有区别` —— 是发送当下的选择,不是装完就不动的
     偏好。把它藏进一个不存在的页面,等于这期不交付。
2. **只在会话运行时才显示这个图标**
   - 最强的理由:更贴近"仅运行中可插话发送",静态时按钮也没有意义。
   - 为何被否:图标时隐时现会让控制行宽度跳变(模型 chip 的上限是 62%,
     多一个图标就少一分空间),而"当前是什么模式"应该随时可见。
     DSH 的设置项也是常驻的。
3. **把偏好同步到电脑(`settings.*` 方法面)**
   - 最强的理由:DSH 存 Host,两边一致。
   - 为何被否:`settings.*` 方法面本期未接(方法面 12/20),为它扩一个入口
     会把两个功能耦在一起。偏好只影响**手机侧发送时带什么参数**,存本地
     不改变电脑侧行为;将来接 `settings.*` 时再决定要不要同步。

## Consequences

- 收益:插话这条路在手机上**存在**了,且选择落盘、重启不丢。
- 收益:没有扩方法面、没有动契约 —— `mode` 参数连接器本来就收。
- 代价:控制行从 3 个控件变 4 个,模型 chip 的可用宽度少了 40px(已用 360px
  窄屏用例钉住不溢出;chip 上限仍是 62%)。
- 代价:偏好只存手机本地,**换一台手机要重设**(与 DSH 的"存 Host、跟账号走"
  不同)。这是第 3 条替代方案的既定取舍,不是遗漏。
- 未做:Enter 键的行为映射(DSH 的 `Cmd/Ctrl+Enter 使用另一行为`)—— 手机没有
  物理键盘,发送键就是唯一入口,所以本期只做"发的时候带哪个 mode"。
