# Agent Note: 中转的配对登记 —— 只登记哈希，三条失效规则缺一不可

Status: implemented（`relay/src/pairing-registry.ts` + 契约 §12.1 的补写；ticket 与网络层见"仍未做"）

## Problem

上一轮把路由核心写完时留下一个洞：**配对帧没有 `sid`**，所以"`sid` → 连接器"那张归属表
帮不上它。手机来配对时，中转必须先知道"这个 `codeHash` 属于哪台连接器"。

而这件事**不能靠中转自己推断**：它只知道连接器的令牌（谁连上来了），不知道谁在等哪一次配对。
所以必须由**电脑侧出码时主动登记**。这一步要写进契约（中转的职责边界变了：多了一张登记表）。

## Decision

**登记的是 `codeHash`，不是码。** 与第 18 轮把配对请求改成带哈希是同一条理由，
也与 §12 的中转表里那一列 `code_hash` **正好对上**：中转不需要码就能完成它的职责
（把 ticket 与连接器绑定），而拿到码就等于它能自己配上一台设备。
于是 `pairing-registry.ts` 里连"码"这个类型都不存在 —— **它收不到，也就没法泄露**。

**三条失效规则都必须有**，因为它们各自留下的都是同一种坏结果（一张指向不存在连接的 ticket），
症状都是"扫码后连不上、而中转侧看起来一切正常"：

1. **认领即消费**（配对码一次性）：`claim` 先删再返回，任何路径都不会让同一个登记被认领两次。
2. **过期 5 分钟**（与配对码同寿）：过期在**认领时就地作废**，不指望清扫兜正确性
   —— 与去重表的惰性过期同一条纪律。
3. **连接器断开即失效**：它未认领的登记全部清掉。少了这条，设备会拿到一张指向
   一条已经不存在的连接的 ticket。

## Alternatives considered

1. 中转按"最近出码的连接器"猜一个
   - 最强的理由：不必新增登记表，中转少一张状态。
   - 为何被否：多台连接器时必然猜错，而且猜错的症状（设备拿到指向别人的 ticket）
     与"没配对"完全不同 —— 那是把一次授权错误伪装成一次连接失败。
2. 中转也持有配对码（而不是哈希），这样它自己能判断"码对不对"
   - 最强的理由：手机上送的码与中转手里的码可以直接比对，认证在中转侧完成，逻辑更"完整"。
   - 为何被否：**契约 §12.1 第 3 步明说身份判定在电脑侧、中转只转发与记账**。
     让中转拿到码就违反这条，而且它一旦拿到码，就能自己配上一台设备（授权被绕过）。
     顺带一提：这正是 §12 的中转表里那一列是 `code_hash` 而不是 `code` 的原因。
3. 登记不过期，靠连接器断开时清理
   - 最强的理由：少一条规则，少一个时钟。
   - 为何被否：连接器可能**一直活着**（它本来就长连），于是作废的二维码会在中转里
     无限期地"仍然可认领" —— 而配对码本身 5 分钟就失效了，两者寿命必须一致。

## Consequences

- 收益：配对的中转路径有了完整的前置（登记 → `POST /ws-ticket` 带 `codeHash` → 绑定连接器），
  而且**码从不进入中转**这条性质在类型层面成立。6 条用例覆盖三条失效规则与两条边界
  （未登记 / 重新登记覆盖）。
- 代价：中转多一张状态表（按 `codeHash`，5 分钟窗口内很小）；电脑侧出码后要多做一次登记调用
  （网络层落地时接上）。
- **仍未做（下一轮）**：
  1. **网络层**：`ws` 的两个入口（连接器 / 设备）、`POST /ws-ticket`（一次性 ticket、
     令牌不进 URL 与日志）、连接器令牌校验、限流与审计 —— 登记表在这条路径上被调用
     （出码登记 / ticket 认领 / 断开清理）。
  2. **`relay/` 的工程骨架**：package.json / tsconfig / 测试脚本（本轮仍用连接器的工具链跑：
     `cd connector && pnpm exec tsx --test ../relay/tests/*.test.ts`），`ws` 在中转是**运行时**依赖。
  3. **电脑侧出码时登记**：`index.ts` 的出码命令里加一次登记调用（需要网络层的客户端）。
