# Agent Note: 一台中转服务多台电脑 —— 隔离模型与那道归属校验

Status: implemented

## Problem

一台公网中转要不要给多个用户用？会串吗？并发会乱吗？

中转的隔离**不是按账号**做的，是按密码学身份：连接器令牌 → `connectorId`，
设备令牌 → 名册里那一行（含它属于哪台连接器），票把 `(connectorId, deviceId)`
写死。逐条核下来，绝大多数边界本来就成立：

- 控制面：令牌认身份；同一 `connectorId` 重连顶掉旧控制连接（`server.ts` 的 `replaced`）。
- 数据面：必须由票上归属的那台连接器来拨，`attachData` 校验 `binding.connectorId === caller.id`
  且 `deviceId` 一致，否则 400。
- 通道：`channels` 按随机 `channelId` 键控，`byDevice` 的键是 `(connectorId, deviceId)` —— 带租户。
- 配对邀请：`pairing-registry.register` 已拒绝跨连接器抢占（"邀请已属于另一连接器"）。
- 背压：每条通道的待投递缓冲有上限（超限 `4008 slow consumer`），数据面挂上之前的
  pending 也有上限 —— 单个慢客户端不会把进程内存吃光。

**漏了一处**：名册表的键是设备 id，**不带租户前缀**，而且 `register` 是直接覆盖。
任何持有合法连接器令牌的人只要知道对方的设备 id，就能把那一行换成自己的摘要 ——
原设备从此换票 `401 device-unknown`（定向 DoS），中转看不出异常。

## Decision

补一道**归属校验**（唯一键 + 所有者检查，等价于多租户表的 RLS）：

- `register(connectorId, rows)`：某行的设备 id 已属于**另一台**连接器时，**拒绝该行**
  （不覆盖、不写令牌索引、不计入本次快照），并 `warn` 一行日志说明被拒几行。
- 归属为空（`detachConnector` 之后）的行仍可被认领 —— 那是"电脑离线时别的电脑报了
  同一个 id"的形状，设备 id 由公钥派生，正常不会发生。

没有改键（不加租户前缀）：设备 id 本来就是公钥派生、天然唯一，加前缀只会让
`connectorOf(deviceId)` 这一条换票路径多一层参数，而收益（防撞）在密码学上已经成立。
归属校验解决的是**写入授权**，那才是缺的那一条。

## Alternatives considered

1. **一用户一容器（silo）**
   - 最强的理由：零代码、崩溃与配额天然隔离。
   - 为何被否：中转是单进程小服务，N 个容器的收益抵不上运维成本；而且"共用会乱"
     的根因是键不带租户，不是共享进程本身。
2. **名册按 `connectorId:deviceId` 复合键**
   - 最强的理由：与关系库的多租户主键一致，物理上不可能互相覆盖。
   - 为何被否：这台中转的换票路径是"令牌哈希 → 行"（哈希已经唯一），复合键不会
     让这条更安全；真正要拦的是"拿着自己的令牌写别人的键"，归属校验正好拦在写入处。
3. **给名册行加签名（电脑侧签，中转验）**
   - 最强的理由：中转不必信任连接器报的行。
   - 为何被否：中转只转发与记账，它连设备公钥语义都不解释；为它引入一套签名意味着
     它要懂身份，和"身份判定在电脑侧"（契约 §12.1）冲突。

## Consequences

- 收益：一台中转可以安心服务多台电脑（几个熟人/几台自己机器），相互之间不能写对方的名册。
- 收益：这条校验也让"两台中转共用一份配置"之类的误配变成一条明确的 warn，而不是静默丢设备。
- 代价：仍然**没有按租户的配额与计量**（设备数、并发通道、带宽），一个租户可以合法地
  占满进程 CPU/带宽影响别人 —— 对外当公共服务前必须补，且要做按租户的日志/指标。
- 代价：名册里"设备 id 已属于别人"这种误配只会拒绝那一行，界面看不到（中转无 UI），
  只能从 `warn` 日志发现。
- 未覆盖：如果攻击者**知道**某台设备 id 且那台设备所在连接器正好离线（归属被清成空），
  它仍可认领那一行。要彻底消除需要让电脑侧对名册行签名（见 Alternatives 3），属契约改动。
