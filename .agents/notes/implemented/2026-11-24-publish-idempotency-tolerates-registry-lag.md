# Agent Note: 发布幂等的判据是"npm 上有没有这个版本"，不是"publish 有没有报错"

Status: implemented

## Problem

2026-11-24 发 v0.2.23 / connector 0.1.30 时，`publish-connector` 的**两个** run 一红一绿：

- `v0.2.23` 那个（先跑）：37 秒，发布成功，npm `latest` 变成 0.1.30；
- `connector-v0.1.30` 那个（被 `concurrency: publish-connector` 串行化到后面）：1 分 3 秒，
  `npm publish` 回 `E409 Cannot publish over previously staged version "0.1.30"`。

串行化本身是对的（2026-11-22 那次是**同时** publish，加 `concurrency` 修掉了并发）。
这次红的原因是另一个：它的**前置幂等检查** `npm view dsh-mobile-connector@0.1.30 version`
在 registry 传播完成前就问了一次，读到"还没有" ⇒ 走进 `npm publish` ⇒ 撞 E409。
即：判据问的是"我现在看得见吗"，而事实是"另一个 run 刚刚发布了"。

后果不是功能问题（npm 上 0.1.30 是对的、`latest` 也对），而是**每次发版都会留一条红 run**，
下一次真红（版本冲突、OIDC 失效）就混在噪音里看不出来。

## Decision

**`publish-connector` 的幂等判据从"发布前查一次"改成"发布失败后重新查，查到就算成功"**：
`npm publish` 非零退出时，在 30 秒内轮询 `npm view <包>@<版本>`；查到该版本即 `exit 0`，
查不到才带上原退出码失败。

准入门槛（可机械判定）：

1. publish 成功（退出码 0）⇒ 照旧成功，不动。
2. publish 失败 ⇒ 重新查 registry；**版本已在** ⇒ 成功（并把"另一个标签的 run 先发布 /
   传播延迟"写进日志），**版本不在** ⇒ 保留原退出码失败。
3. 轮询有界（6 次 × 5 秒），不无限等 —— 这条判据的目的是容忍传播延迟，不是容忍发布失败。
4. 判断只认**注册表上的版本**，不认错误码文案（`E409` 的措辞会随 npm 版本变）。

## Alternatives considered

1. **把前置检查改成"轮询到看见为止"（发布前等 30 秒）**
   - 最强的理由：逻辑更直观 —— 先确认一次，再决定发不发。
   - 为何被否：它假设"看不见等于没发布"。两个 run 的顺序由 `concurrency` 定，先跑的那个
     成功发布后，后跑的必然能看见；这次失败恰恰是传播延迟，前置轮询要覆盖的窗口只能靠
     `sleep` 硬等，而**失败后的重新查询**用同一份信息、同样有界，且只在真的要走 publish
     时才多花时间。
2. **把 `concurrency` 升级成"两个标签只触发一个 run"（例如只让 `connector-v*` 发布）**
   - 最强的理由：从根上消除重复发布。
   - 为何被否：`v*` 也触发是**故意的**（2026-11-02 踩过：只推 `v*` 时 Release 出了、npm 还停在
     旧版，用户按包名装到旧插件）。让 `v*` 也能发布是"整仓发布一次就够"的正确方向；
     重复只是它的代价，用幂等吸收。
3. **失败就失败，手动删 run / 重跑**
   - 最强的理由：零改动。
   - 为何被否：每次发版都要人盯一条红，而红的原因与"真失败"长得一样 —— 这正是噪音变事故的路径。

## Consequences

- 收益：两个标签同时推，`publish-connector` 两条 run 都会绿（后到的那条在日志里说明
  "版本已在 npm 上"），红 run 重新只剩真失败。
- 代价：失败路径多了最多 30 秒等待；`npm publish` 的真失败仍会把日志刷出来（先红后绿的解释
  要读日志才看得见）。
- 代价：这条判据依赖 `npm view` 的**读**能力。registry 全挂时两条路都失败，报出来的是原错误，
  没有被吞掉。
