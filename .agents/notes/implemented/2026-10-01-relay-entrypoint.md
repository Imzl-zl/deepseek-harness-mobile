# Agent Note: 中转的可运行入口 —— 摘要表在启动时就读进来

Status: implemented（`relay/src/main.ts` + `relay/src/digest-auth.ts`；子进程形态的 e2e 见"仍未做"）

## Problem

中转此前**没有入口**：`startRelay()` 能在测试里被调用，但没有人能把它跑起来。
而"能跑起来"这件事牵出两个必须定的点：

1. **令牌从哪来**：中转要校验连接器/设备令牌（§12.2：**中转只存 `token_hash`**），
   而摘要表存在库里——库还没实现（那是 §12 的 SQL 面）。
2. **配错了怎么办**：启动时读配置，配错（缺 `tokens`、重复条目）应当**当场失败**。

## Decision

- **`digest-auth.ts`**：从**摘要表**建出 `authenticate`（`sha256(token)` 查表）。
  配置里也只放摘要 —— 明文令牌不出现在中转的任何持久形态里，这正是 §12.2 那条表结构的意图。
  - 认不出返回 `undefined`（调用方回 401，且**不区分原因**：对客户端是同一件事）；
  - **拿摘要当令牌来试不会通过**（用例钉住）：否则"泄露摘要"就等价于"泄露凭据"；
  - 摘要表里有**重复条目 → 拒绝启动**：后一条覆盖前一条会让"谁是谁"看运气。
- **`main.ts`**：`--config <path>` 读一个 JSON（`{port, host, tokens}`），建摘要表、`startRelay`、
  打印监听地址与摘要条数；SIGINT/SIGTERM **优雅退出**（关 socket、停监听）。
  不接住所有异常继续跑 —— 那是把故障藏起来。
- **入口保持薄**：判定/接线都在别的文件里，`main.ts` 只做"读配置 → 起服务 → 退出"。
  与 `connector/index.ts` 的结构同理（生命周期与判定分层）。

准入门槛（可机械判定）：`pnpm typecheck` 0 错、`pnpm test` 39 条全绿（新增 3 条摘要用例）、
以及**真的起一次**：写一份探针配置（`port: 0`）跑 `node src/main.ts --config …`，
打印出 `中转已监听 ws://127.0.0.1:<port>（摘要表 1 条）` 后按信号退出。

## Alternatives considered

1. 配置里直接放明文令牌（启动时算摘要）
   - 最强的理由：配置更好写（照抄令牌即可），少一步 `sha256`。
   - 为何被否：那份配置就是中转的持久形态 —— 明文令牌进配置文件，等于把 §12.2
     "只存摘要"这条纪律在入口处破坏掉。摘要算起来只是一条命令。
2. 让 `main.ts` 去连数据库读摘要表
   - 最强的理由：更接近最终形态（§12 的 SQL 面）。
   - 为何被否：库还不存在，而"为了一个入口先写半个库"会把这一轮变成一次数据层设计。
     摘要表的**形状**（`{kind, id, hash}`）已经定下来，将来把来源从文件换成库，
     换的是 `main.ts` 里读配置那几行。
3. 启动时不校验配置，让连接时再失败
   - 最强的理由：入口更短。
   - 为何被否：一个"起来了但所有连接都 401"的中转比没起来更难排查 ——
     配置错误应当在启动时大声失败。

## Consequences

- 收益：中转**能跑**了（`node relay/src/main.ts --config …`），且配置错误在启动时暴露；
  relay 39 条用例（判定 33 + 冒烟 3 + 摘要 3）。
- 代价：摘要要手工算（`sha256`）；库里还没有令牌签发/吊销（§12.2 的另一半）。
- **仍未做（下一步）**：
  1. **把跨工程 seam e2e 改成子进程形态**（`node relay/src/main.ts`），撤掉 `tsconfig.e2e.json`
     这个过渡方案 —— 第 40 轮的笔记里记过它是过渡；
  2. **三方 e2e**：中转 + 连接器 + 手机替身跑通"配对 → 握手 → 发一句"；
  3. 令牌签发/吊销（§12.2）；手机端 Dart 客户端；每连接状态那个岔口。
