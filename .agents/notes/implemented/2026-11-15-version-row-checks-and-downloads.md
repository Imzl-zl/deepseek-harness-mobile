# Agent Note: 版本号那一行就是动作 —— 点一下查、查到就下载，不再分两行

Status: implemented

## Problem

用户 2026-11-15 的原话：

> 还有版本号更新那个，那做的是个啥啊，版本号点击检测更新不好了为啥一个版本号一个检测更新，
> 检测更新还只是检测更新，不是直接下载？？做的啥玩意啊，搞笑一样啊

设置页「关于与连接」当时是**两行**：

| 行 | 动作 |
|---|---|
| 检查更新 | 查 `releases/latest`，查到就弹一句「有新版本 v0.2.18（去 GitHub Releases 页下载）」 |
| App 版本（点按复制） | 复制版本号 |

三处问题，都是用户直接撞上的：

1. **一件事两个入口**：版本号是"我是谁"，检查更新是"我要新版本"—— 用户找的是后者，
   但最像它的那一行（版本号）偏偏是复制。
2. **查到之后还得人肉找包**：`release.yml` 用 `--split-per-abi` 发三个 APK
   （`-arm64-v8a` / `-armeabi-v7a` / `-x86_64`），装错 ABI 报「应用未安装」。
   一句"去 Releases 页下载"等于把**挑包**这件最容易出错的事推给用户。
3. 上一轮（2026-11-04）就收到过「设置有版本号为啥是复制不是检查更新」，
   当时的修法是**加一行「检查更新」、保留复制** —— 那是把症状绕过去了，
   没有减掉分叉。这次按原意合并。

## Decision

**一行**：`App 版本` —— 值列写"我是谁 + 有没有新版"，点它就是把"让我变成最新版"这件事做完。

准入门槛（可机械判定）：

1. 设置页「关于与连接」里**只有一行**与 App 版本有关（`检查更新` 这个行标题不再存在）。
2. 点那一行：
   - 还不知道有没有新版 ⇒ 查一次（`usage` 之外唯一会打外网的动作）；
   - 查到有新版 ⇒ **当场问一句「下载并安装」**（`confirmDownload`），确认后才下载；
   - 已经知道有新版 ⇒ **再点就是下载**，不再查一次网络；
   - 已是最新 / 查不到 ⇒ 查一次并如实说原因（查不到 ≠ 已是最新）。
3. **挑包按 ABI**（`core/app_update.dart` 的 `apkAssetFor`）：先找 `-<abi>.apk`，
   没有才退任意 `.apk`（老版本发的是通用包），一个都没有 ⇒ 不给链接。
   ABI 来自 `dart:ffi` 的 `Abi.current()`（`platform/app_update_downloader.dart`）。
4. **下载交给系统**（Android `DownloadManager`，通道 `dsh/app-update`）：
   入队即返回，进度与完成通知归系统，完成后点通知就是系统安装器。
5. 没有这个能力的设备（非 Android / 装配没注入下载器）⇒ **退成复制下载链接**并说明，
   不假装下载成功。
6. 复制版本号没消失：**长按**那一行（`SettingsRow.onLongPress`）。

## 验证（2026-11-15）

- `app/test/app_update_test.dart` **22** 项：版本比较、`tag_name` 剥 `v`、
  `latestReleaseOf`（只收 `.apk`、坏条目跳过）、`apkAssetFor` 四档（精确 / 兜底 /
  空 ABI 不猜 / 全没有）、`rowValue` 四种状态、`AppModel.downloadAppUpdate` 四种结局
  （没有 url / 没有下载器 / 交给缝的 url 与文件名 / 系统拒了带原话）。
- `app/test/settings_page_test.dart` 两条 widget 用例：**只有一行**且点它就是查
  （`检查更新` 这个词不再出现在页面上）；查到新版 → 弹确认 → 下载；再点同一行
  **不再查网络**直接下载。
- `flutter build apk --debug` 通过（Kotlin 侧 `DshAppUpdate.kt` + 通道注册编得过）。
- **变异校验**：把"再点就是下载"改回"再查一次" ⇒ 恰好 1 条红（`checks` 1 → 2）；
  把 `apkAssetFor` 的精确匹配去掉 ⇒ **2 条红**，两条都是同一件事：
  一台 `arm64-v8a` 的设备挑到了 `-armeabi-v7a.apk`（也就是真机上会报「应用未安装」的那个错）。

## Alternatives considered

1. **保留两行，只把「检查更新」那行的提示改成下载入口**
   - 最强的理由：改动最小，复制还留在显眼位置（贴 issue 时方便）。
   - 为何被否：用户抱怨的正是"两行"这件事本身。一行只承诺一件事，
     复制这种偶尔要一次的动作放长按就够了。
2. **查到新版就自动开始下载**（连确认都不要）
   - 最强的理由：真正的"一步到位"，用户点一下什么都不用管。
   - 为何被否：APK 二三十 MB，很多人在流量下；不点就下与"App 偷偷花流量"只差一个说法。
   确认那一屏同时说清了"交给系统下载器"，安装时的系统弹窗才不会显得突兀。
3. **打开浏览器（`Intent.ACTION_VIEW` 那个 URL）**
   - 最强的理由：不用通道、不引 DownloadManager，几行就能"跳出去"。
   - 为何被否：能不能落地取决于用户装了哪个浏览器、有没有开下载权限；
     而 `DownloadManager` 一定落到 `Downloads/`、一定发通知、点开就是安装器。
   "直接下载"在 Android 上有标准答案，不该退化成跳网页。
4. **继续开 `releases/latest` 页面让人自己选**
   - 最强的理由：零维护 —— 发布物怎么命名都与 App 无关（这是 2026-11-10 那篇的结论）。
   - 为何被否：三个包长得几乎一样，选错报「应用未安装」。挑包是纯函数能算对的事，
     推给用户就是把最容易出错的一步留在最不专业的那一侧。代价：发布物命名成了契约
     （`release.yml` 的 `-<abi>.apk`，已写进 `docs/cookbook/release.md`）。

## Consequences

- 收益：
  - 用户视角"点一下 → 装上"是连续的两跳（确认下载 + 系统安装），没有中间那种"自己去找包"。
  - `release.yml` 的资产命名第一次被 App 依赖 —— 它从"内部约定"升级为契约，
    写进了 `docs/cookbook/release.md`，改命名会红（`apkAssetFor` 的用例钉着）。
  - 复制版本号没有丢（长按），也没有为了它多占一行。
- 代价：
  - 新通道 `dsh/app-update` + 一个 Kotlin 文件（`DshAppUpdate.kt`，约 90 行）：
    能力面 +1，鸿蒙接的时候要自己实现一遍（没有第三方插件兜着）。
  - `AppModel` 多两个缝（`deviceAbi` / `downloadAppUpdate`）与一个方法，尺寸预算随之抬数。
  - 非 Android 只能复制链接（桌面调试时就是这样）。
  - **没有真机点过**：下载、通知、"点开即安装"这三跳的证据是系统组件的行为，
    代码只保证把正确的 URL 与文件名交出去。
