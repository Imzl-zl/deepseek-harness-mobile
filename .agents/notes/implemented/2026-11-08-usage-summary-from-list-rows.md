# Agent Note: usage.summary 只读清单行的投影提示，按天活动另起一次有界请求

Status: implemented

## Problem

用量页在真机上一直空着（2026-11-08 用户反馈「用量怎么也不显示」）。连接器的
`usage.summary` 对每个非子智能体会话调一次 `session.projections`：冷会话要把整份
日志读进来算全部投影。本机 **327 个会话 / 539 MB 日志**，页面在结果回来之前一直是
空态；任一会话超过 30 s 还会让整次调用失败（`Promise.all`）。

而 `session.list` 的每一行本来就带 `projections.values.tokenUsage`
（白名单 `protocol/session-row.ts` 的 `SESSION_ROW_PROJECTION_KEYS`）—— 宿主自己折好的
四个桶。逐会话再读一遍，是把清单已经给过的东西重算一遍。

## Decision

1. **总量 / 四个桶 / 按项目 / 按会话**：只读 `session.list` 的行提示；仅当某一行没有
   `tokenUsage` 提示时才回落一次精确读（冷行缺持久缓存 / 该部署没装 token-meter）。
2. **按天活动**（`trajectory`）不在白名单里 ⇒ 独立成一次可选请求：
   `usage.summary {days: n}`（1..366）。只读 `updatedAt` 落在窗口内的会话，同一会话按
   投影水位（`projections.asOfSeq`）缓存；不带 `days` 时响应里**没有** `byDay`。
   **每批只新扫 4 个会话**（`DAY_SCAN_BATCH`），应答带 `daysProgress:{scanned,total}`；
   手机拿到 `scanned < total` 就 350ms 后自己要下一批，界面写"正在统计活动 N/M"。
   本机实测：一个项目近 60 天就有 104 个会话 / 680 MB 解压日志（光解压 8 s），
   一次读完就是"页面转很久"。
3. **页面侧**：先出总量（一次往返），活动再补；三档窗口 7 / 30 / 90 各自是一次请求。
   请求的天数是 `2 × 窗口`（本段 + 前段对比）。

准入门槛：

1. 20 个带提示的行 ⇒ `projections.of` 调用 **0 次**（`usage-summary.test.ts`）。
2. 没有提示的行只回落 1 次。
3. `days` 只读窗口内更新过的会话；同一水位的第二次请求命中缓存。
4. `days` 越界回 `protocol/bad-frame`，不静默截断。
5. 金样两条：不带 `days` 没有 `byDay`；带 `days` 时键在（空表也算"报了"）。

## Alternatives considered

1. **保留逐会话精确读，只加缓存**
   - 最强的理由：数值与"打开会话时看到的"逐字一致，冷行缓存缺失也不会少算。
   - 为何被否：首次打开仍要把 539 MB 日志读一遍；"第一次要等一分钟"就是用户报的那个
     症状。清单提示本来就是宿主给同一批行的答案，不是第二份账。
2. **把 `trajectory` 也塞进列表行**
   - 最强的理由：一次往返就能算按天活动，页面只有一个 loading。
   - 为何被否：`trajectory` 是列表包里最大的一块（曾占 23.9% / 353 KB），每行都带会把
     "打开抽屉"变成一次大包搬运；`session-row.ts` 的白名单正是为砍它而存在。
3. **连接器本地记账（事件里累加每天多少 token）**
   - 最强的理由：零日志读、实时。
   - 为何被否：只覆盖插件在线期间，历史空着 —— 那正是被否过的"看起来像总量"。
4. **保留「全部 52 周」窗口**
   - 最强的理由：用户想看得越远越好。
   - 为何被否：一年窗口 ≈ 全部会话都要读 `trajectory`，又把慢路径请回来。90 天覆盖
     "最近在不在干活"；更长历史等有持久账本再说。
5. **一次读完窗口内全部会话（不分批）**
   - 最强的理由：一次请求给完整的热力图，客户端不需要轮询，实现最简单。
   - 为何被否：窗口里可能有上百个会话（实测一个项目 104 个 / 680 MB），一次读完
     就是"页面转很久"。分批 + 进度让首屏先有数，剩下的几秒内补齐。
6. **新增独立方法 `usage.days`**
   - 最强的理由：两个问题两个方法，语义更干净。
   - 为何被否：契约 §5.7 是封闭方法集，为一个可选展开项加方法要同步 methods 表 /
     能力位 / 金样 / 客户端三处；同一资源的可选展开用参数更小。

## Consequences

- 收益：用量页首屏一次往返；活动与总量解耦，慢的只影响热力图那一块。
- 收益（真机补记）：构成条在 `Row` 的松高度约束下取 0 高（`ColoredBox` 没有子节点），
  条子"存在但看不见" —— 改成 `crossAxisAlignment: stretch` 并加尺寸断言
  （`tester.getSize(...).height == 8`）。这条只有真机截图能看出来，单测原本全绿。
- 代价：总量来自列表提示，冷行缓存的滞后与 `session.list` 一样（打开会话后收敛）。
- 代价：按天活动只覆盖窗口内更新过的会话，且每会话最多 200 轮（既有 `MAX_TURNS` 上界）。
- 代价：分批期间"近 N 天"只是已扫会话的和 —— 界面必须同时显示 `已扫/总数`，
  否则半份账会被当成完整结果。第一次打开一页新窗口要几秒才扫完（之后命中缓存）。
- 代价：新 App 连老连接器时 `days` 会被忽略、老连接器仍算全量 —— 升级要两边一起。
