# Agent Note: 上报哪条直连地址 = 地址自己的事实，不是默认路由是谁

Status: implemented

## Problem

用户 2026-11-20 截图：出码失败，正文是

> 无法生成配对码：直连监听已启动，但没有可上报的地址（默认路由不可用，或主地址已被隐藏）；中转未连接。

用户追问：「为啥中转关了直连就不出码说没有上报地址？这个东西搞多少次了怎么一直都有问题？？」
以及「我确实开了代理的TUN这还影响吗？那这咋办？我确实需要开代理啊？」

**这台机器的真实网卡**（`os.networkInterfaces()` 实测）：

```
defaultRouteIPv4 = 198.18.0.1        ← FlClash 的 TUN 虚拟网卡（MAC 00:00:00:00:00:00）
WLAN 2  IPv4      192.168.2.75       ← 真正的局域网（MAC d0:76:02:c9:f5:46）
VMware VMnet1     192.168.40.1       ← 虚拟（MAC 00:50:56:c0:00:01）
VMware VMnet8     192.168.235.1      ← 虚拟（MAC 00:50:56:c0:00:08）
+ 2 条 IPv6 GUA（隐私扩展）
候选池共 6 条
```

旧判据是 2026-11-06 定的 `defaultDirectUrls`：**只报 `lanHint`（默认路由网卡的 IPv4）
命中的那条**，拿不到 hint 时"只有唯一候选才报，多候选不猜"。

它默认了一个前提：**默认路由所在的网卡就是局域网网卡**。开代理 TUN 时这个前提不成立，
于是同一天出现两个坏分支：

| `lanHint` 的实际值 | 旧判据的结论 | 后果 |
|---|---|---|
| `198.18.0.1`（TUN 在场） | 命中 TUN 那条 | 码里写 `198.18.0.1`，**手机拨不通** |
| `null` / 换网后的旧值 | 6 条候选不满足"唯一一条" | **一条都不报** ⇒ 用户截图那个错 |

`ws://192.168.2.75:8790` 一直在候选池里，只是被这条判据挡在外面。

**报错文案也在误导**：「或主地址已被隐藏」——用户的真实情形两种都不是（没隐藏、
默认路由也确实有，只是它指向虚拟网卡）。他照这句话查不出任何东西。

### 这不是"少数派代价"，而是当时的记账错误

2026-11-06 那篇笔记的 `Consequences` 里写着：

> 代价：默认路由不是手机所在局域网时（双网卡、默认路由走 WAN），直连默认不生效，
> 用户要到「更多地址」里点名上报。

当时把它记为**边缘代价**。但代理/VPN 客户端的 TUN 模式会让**所有**这类用户落到这一档，
而"开代理"是开发者的常态配置，不是异常。同一个症状因此在 11 月里以不同面孔反复出现
（用户原话："这个东西搞多少次了怎么一直都有问题"）—— 根因是判据选错了**数据源**。

## Decision

**判据从"默认路由是谁"改成"地址自己是什么"**，收敛在 `endpoints.ts` 的
`defaultDirectUrls()`：

1. **虚拟网卡先排除**：`transport/listener.ts` 新增 `isVirtualMac()`，按 MAC 的
   OUI 事实标记（`00:00:00:00:00:00` = TUN；`00:50:56` / `00:0c:29` / `00:05:69` /
   `00:1c:14` = VMware；`00:15:5d` = Hyper-V；`02:42` = Docker）。
   监听面把 `virtual` 作为**观察到的事实**带出去，**不在枚举层过滤** ——
   候选池仍要完整（面板的「更多地址」靠它），判据只有一处。
2. **`lanHint` 命中一条真实网卡 ⇒ 就报它**（这一档行为与旧判据完全一致，
   普通用户无感知）。
3. **hint 落空（null / 过期 / 指向虚拟网卡）⇒ 在真实局域网 IPv4 里选一条**：
   只认 RFC1918 三段（`192.168/16` / `172.16/12` / `10/8`），
   按 `192.168` → `172.16` → `10` 偏好序取第一条。
   **仍然只报一条** —— 2026-11-06 用户的抱怨（"虚拟机地址、其他地址根本用不上"）
   说的是列表被占满，这条约束保留。
4. **虚拟网卡绝不进默认集合**，即使它是唯一候选。一台只有 TUN 的机器得到空集合，
   这是如实结果（该走中转），不给 fallback —— 一条拨不通的地址上码只会让手机白等超时。
5. **报错按候选的实际情况分档**（`index.ts` 的 `listenerNoAddressReason`）：
   一条候选都没有 / 候选全是虚拟网卡 / 候选被 `hide` 光，三种各有各的说法与动作。

## Alternatives considered

1. **只按 MAC 标记虚拟网卡，`lanHint` 仍然决定报不报**
   - 最强的理由：改动最小，且"默认路由优先"在 99% 的家用环境里是对的。
   - 为何被否：这正是本次的坏分支 ②。TUN 开关切换、换 WiFi 之后 `lanHint`
     刷新落后一拍就会落空，于是回到"一条都不报"。排除虚拟网卡之后，
     "hint 落空就选局域网"是安全的——剩下的候选都是真实网卡，选哪条都比不选强。
2. **不排除虚拟网卡，只把 `198.18/15`、`100.64/10` 这类网段拉黑**
   - 最强的理由：纯地址判据，不动 `DialableUrl` 的形状，改动面更小。
   - 为何被否：VMware 的 `192.168.40.1` / `192.168.235.1` 是**标准 RFC1918 段**，
     按网段拉黑不了；而它们是这台机器上最早被用户点名抱怨的地址。
     MAC OUI 是分配事实，不随名字变——`listener.ts` 当初拒绝"按网卡名过滤"
     的理由（名字又脆又漏）在这里同样成立。
3. **默认集合放全部真实局域网地址（多报几条，让手机自己挑）**
   - 最强的理由：手机侧 `pairing_flow.dart:352` 的 `tryLan` 本来就会**逐条回退**，
     且有 `/24` 同网段排序；多给一条不会更糟。
   - 为何被否：**实测红 8 条**。`endpoints.ts` 描述的是手机的**端点列表**，
     不是拨号候选池；2026-11-06 用户的原话是"这不是多余？"。
     多网卡机器的真实局域网往往只有一张，另一张是对端可达但手机不在的网段。
     保留"只报一条"，把"多一条"交给用户的 `extra`。
4. **把默认集合写进配置（用户先选一次）**
   - 最强的理由：最可控，绝不替用户猜。
   - 为何被否：与 2026-11-06 同一条——换 WiFi / DHCP 换址后配置过期，
     而"哪条是局域网"是每个地址自带的事实，让用户重填是重复劳动。
5. **只在报错文案里说清"TUN 抢了默认路由"**
   - 最强的理由：一行改动，用户至少能照着关代理。
   - 为何被否：治的是症状。用户明确说了「我确实需要开代理」——
     要他为了出码关代理，是把系统缺陷转嫁给用户的使用习惯。

## Consequences

- 收益：**开代理 TUN 的机器能正常出码**，码里带的是真实局域网地址（本机实测：
  `lanHint` 三种取值——`198.18.0.1` / `null` / 过期旧值——全部选中 `192.168.2.75`）。
- 收益：报错文案从"猜"变成"事实"。虚拟网卡独占时直接说『可拨地址都在虚拟网卡上
  （FlClash），关掉 TUN 重试或在「更多地址」里点名上报真实局域网地址』。
- 收益：`virtual` 是**观察到的事实**而不是过滤动作，候选池完整，
  面板的「更多地址」仍然列得出来（用户随时能 `extra` 点名 TUN 那条）。
- 收益：普通机器（**hint 命中且无虚拟网卡**）行为逐字不变 —— 逐场景对照过：
  `hint` 命中（单网卡 / 多网卡 / 公网段）新老判据输出完全相同。
- 收益：`hint` **落空**的多网卡机器从"一条都不报"变成"报出一条真实局域网地址"。
  这是有意变更的那一档，也正是用户截图里的故障。
- 代价：`DialableUrl` 多一个可选字段，`listener.ts` 与 `endpoints.ts` 的契约变宽了。
- 代价：MAC 拿不到的平台上 `virtual` 是 `undefined`（当作"不知道"，按网段判断）——
  那种环境里 VMware 地址仍可能被选中。**这是已知的剩余风险**，不是已解决。
- 代价：判据偏好序（`192.168` → `172.16` → `10`）是启发式。一台同时有
  `192.168.x`（不通）与 `10.x`（通）的机器会选错。代价可接受的理由：
  手机侧 `tryLan` 会回退，且用户可以 `extra` 点名。
- 代价：仍然**没有真机扫码验证**——本次证明的是"电脑侧选对了地址并把码出了"，
  "手机扫码后局域网这条真的拨通"要真机才能确认。
- 边界：`endpoints.test.ts` 里「多网卡无 hint 一条都不报」那条断言被**改写**了。
  它不是被削弱，而是旧结论（"报哪条都是猜"）在新判据下已经不成立：
  `100.100.1.2`（Tailscale / CGNAT）手机在普通 WiFi 下拨不通，
  而 `192.168.1.5` 是真局域网——选它不是猜。

## 判据

- `cd connector; pnpm exec tsc --noEmit` → 0。
- `pnpm test` → **885 项全绿**（基线 870 + 新增 `tests/tun-default-route.test.ts` 10 条
  + `tests/no-address-reason.test.ts` 5 条；另改写了 `endpoints.test.ts` 一条旧断言，
  条数不变）。
- `pnpm build` → ok（`lib/index.js` 469.03 kB）。
- **变异校验 ①**：把 `urls.filter((e) => e.virtual !== true)` 改成恒真
  ⇒ 4 条红（TUN 上码 / 全虚拟不猜 / hide 后退回 TUN / hint 落空）。
- **变异校验 ②**：删掉"hint 落空 → 选局域网"的整段 ⇒ 3 条红。
- **变异校验 ③**：把文案分档判据退回"有真实候选就算被删掉"
  ⇒ 恰好「只有 CGNAT + IPv6」那一条红。
- 真实数据验证：用本机 `os.networkInterfaces()` 跑新判据，
  `lanHint` = `198.18.0.1` / `null` / `192.168.110.79` 三种输入均得
  `["ws://192.168.2.75:8790"]`，`lanAvailable = true`。
- 新老判据逐场景对照（单网卡 / 多网卡 / 公网段 × hint 命中 / 无 / 过期）：
  hint 命中的三种输出完全相同；变化的只有 hint 落空的两档（有意变更）。

## 审查记录（2026-11-20 收尾自查，两处已修）

1. **文档注释与代码不符**：`defaultDirectUrls` 的注释写"多条时默认路由排最前 /
   顺序即偏好"，但实现**只报一条**。已改成"最多一条"并逐档写清。
   没有代码缺陷，但注释会误导下一个改这里的人。
2. **文案分档用错了判据**：第一版用"有没有非虚拟候选"判最后一档，于是
   **只有 Tailscale（CGNAT）或纯 IPv6 的机器**会被告诉"候选地址都被你删掉了"——
   与事实相反，是本次要修的那类错话换了个位置。已改为与 `defaultDirectUrls`
   同源的 `isLanAddress`，并补 `tests/no-address-reason.test.ts` 钉住。
