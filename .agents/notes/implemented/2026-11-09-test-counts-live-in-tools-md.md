# Agent Note: 测试条数只住 tools.md，README 与 memory 改成指向

Status: implemented

## Problem

同一批测试条数抄在三个地方，而三处给出的数不一样：本批修正前 README 的 `flutter test` 写
1779、`memory.md` 写 1791、`tools.md` 写 1762；boundary 也分别是 843 / 848 / 848。没有任何门禁
会因为这三个数不一致而变红 —— 门禁只看"全绿"。于是"条数"从校验手段退化成了三份各自过期的
注释，而读它的人没有任何办法知道哪一份是真的。

## Decision

**条数只住 `tools.md`**：README 与 `memory.md` 的门禁表只留命令与"覆盖什么"，不再写数；
`memory.md` 的门禁表头写明"项数只住 `tools.md`"。`tools.md` 里的数字按最近一次实测更新
（app 1802 / connector 851 / relay 183 / protocol 454·26·49 / boundary 848）。

准入门槛（可机械判定）：

1. `README.md` 与 `memory.md` 里搜不到某个套件的本地条数（例外：README 的"fixtures 断言数须 = 454、向量须 = 49"—— 那是**跨端必须相等**的约束，不是本地条数）。
2. `tools.md` 是唯一出现"1802 / 851 / 848 / 183"这些数字的地方。
3. 门禁的判据仍是"全绿"，不是"数字对上了"。

## Alternatives considered

1. 三处都保留数字，靠"改断言时同改三处"的纪律
   - 最强的理由：读者在哪一页都能直接看到条数，不用跳转。
   - 为何被否：已经漂了（1779 / 1791 / 1762 三处各不相同），而且没有任何门禁会因此变红 —— 靠纪律守一个没有反馈的数，等于没守。
2. 用脚本把条数自动写进三处
   - 最强的理由：永远不会漂，改完测试自动同步。
   - 为何被否：条数依赖环境（本机与 CI 的跨语言用例可能差一条），自动生成会把"环境差异"固化成"文档错误"；README 也不该因为跑了一次测试就产生 diff。
3. 三处都删掉，连 `tools.md` 也不写
   - 最强的理由：最彻底，彻底消灭第二份真值。
   - 为何被否：条数是"这次改了多少"的粗粒度信号（"只多了 2 条"说明没漏测），协作知识库需要一个落点；把它从唯一的家也删掉，就再没有地方记"上次实测是多少"。

## Consequences

- 收益：一个数字一个家；README 的门禁表不再随用例增长而失效；memory 的表格只回答"跑什么"。
- 代价：看 README 的人要知道 `tools.md` 在哪（表格上方给了链接）；跨端不变量（454 / 49）仍留在 README，因为它们约束的是"两侧相等"，不是"本地多少条"。
- 代价：`tools.md` 的条数仍是人工在跑完后更新，没有自动化 —— 它可能再次过期，但至少只有一处会过期。
