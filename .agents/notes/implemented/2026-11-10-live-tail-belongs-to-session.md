# Agent Note: 流式尾不是全局的，它属于「当前那个会话」

Status: implemented

## Problem

2026-11-10 真机（另一台手机、公网中转）：点「新建会话」之后**顶栏已经是「新建会话」，
正文还是旧会话**。同一台机器（直连）走同一条路正常，所以看起来像"不稳定复现"。

标题与正文来自**同一次 build**，所以能分叉只可能是正文的数据源不认会话。
它就是 `AppModel._liveTail`：一个 `ValueNotifier<LiveMessage?>` 单例，
承载"当前这次生成正在流出来的正文/思考"，只在 `turn/end` 或持久的
`assistant/message` 到达时清空。

而 `openSession` **不退订**旧会话（退订是 `closeSession` 的事），旧会话的订阅继续活着，
它的 `live` 帧继续进 `_onDelta(oldSid, …)` —— 于是新会话页上的虚拟尾条目
继续画上一个会话的正文，直到那一轮结束。公网中转让流式窗口（首字节 + 逐段）
长得多，所以那台手机撞上、直连这台没撞上。

## Decision

把流式尾的所有权钉在「当前会话」上，两个方向一起：

1. `openSession` / `closeSession`：换了会话就清空（离开即作废）；
2. `_onDelta` 的三处写（新 `live`、收尾清空、带事件批里的 `live`）都要过
   `_liveTailBelongs(sid)` —— **只有当前会话的帧能上屏**。

准入门槛（可机械判定）：

1. 单测：`openSession('s1')` → 推一条 `live` → 有值；`openSession('s2')` → `null`；
   再推一条 s1 的 `live` → 仍然 `null`（`app/test/live_tail_test.dart`）。
2. **变异校验**：把 `_liveTailBelongs` 改成恒 `true`，**恰好**第二条断言红
   （"切走的会话不许再往新会话页写流式正文"）。
3. 不许用"切会话时退订旧会话"实现（见下面第 1 条替代方案）。

## Alternatives considered

1. 切会话时退订旧会话
   - 最强的理由：一处动作、语义最干净 —— "看不见的会话就不订阅"。
   - 为何被否：切回来要按条目上界重放整窗，而且并行会话的完成点 / 待处理一起丢；
     `live` 是"当前这次生成"的界面状态，退订是全连接层的动作，两件事不该绑在一起。
2. `_liveTail` 改成 `Map<String, LiveMessage>`，页面读当前那个
   - 最强的理由：数据模型上就对了，切回来还留着半截，不用等下一帧。
   - 为何被否：现在只有"当前会话"渲染尾条目，多一份 per-sid 状态就多一份要清理的东西
     （切回时还得判断"那一段是不是已经落了"）。真要做并行会话页时再付这个成本。
3. 只在 `openSession` 里清空，不动 `_onDelta`
   - 最强的理由：最小改动。
   - 为何被否：实测无效 —— 旧订阅的下一条 `live` 帧会把尾巴重新填上，症状照旧
     （门槛 2 的变异校验就是这条）。

## Consequences

- 收益：切会话之后"正文属于哪个会话"不再靠运气；"标题换了正文没换"这类症状消失；
  同时修掉"别的会话收尾把我这半截抹掉"的另一个方向。
- 代价：`_onDelta` 多了三处 `_liveTailBelongs` 判据（同一件事的三处应用，
  靠门槛 1 钉住）；切回一个正在生成的会话时，尾条目要等下一帧 `live` 才重新出现
  （那一帧带的是累加值，所以不缺内容）。
- 未做：没有按会话保存流式内容（替代方案 2），所以切走再切回不会立刻看到半截。
