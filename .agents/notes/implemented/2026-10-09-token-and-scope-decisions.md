# Agent Note: 令牌与范围的三条决定（长期令牌、砍多实例、鸿蒙暂缓）

## Problem

配对 v2 收口后剩下三件"做不做"的事，它们的共同点是：**都不是技术卡点，而是范围选择**，
而且此前的文档把其中两件写成了"待定/未实现"，读起来像是遗漏：

1. 刷新令牌的**轮换流程**——契约有 `refresh_hash` 落点，实现没有。
2. 中转的**多实例**——票 / 名册 / 限流都是进程内状态。
3. **鸿蒙端**——三端能力包里最大的未知。

## Decision

**1. 设备令牌长期有效 + 手动吊销，刷新令牌轮换本期不做。**
代价如实记录：设备令牌泄露后，在手动吊销前一直有效。补偿是吊销**可用**（电脑侧不再把该设备
报进名册 + 本地标 `revoked_at`），且重新扫码即可换新。`refresh_hash` 列保留为"将来的落点"，
文档明确写"只落不用"，避免下次有人以为它今天会生效。

**2. 中转砍掉多实例，保持单实例。**
I7（中转可被清空后重启、已配对设备凭名册收敛）已经覆盖单实例重启，而"重连是常态"本就是
契约假设。多实例要把票 / 名册 / 限流搬进共享存储：契约不变，但实现面大一倍，收益接近零。

**3. 鸿蒙移出近期范围，但 Flutter 3.41.9 版本锁继续保留。**
锁是为鸿蒙留的上界（`app-platform-boundaries.md` §4），锁着不花钱；OHOS 适配、HUKS、
`flutter_sqflite` 的 ohos fork 全部暂停。`docs/` 里既有的鸿蒙调研（版本线、推送频控、安全存储）
**原样保留**——那是花过力气的一手调研，暂停不等于作废。

## Alternatives considered

- **实现刷新令牌轮换**：要定轮换窗口、并发重连时两个连接同时用旧令牌的竞态、轮换失败是否
  吊销。这是一套完整的并发设计，而它的收益（令牌泄露后的自救）可以被"重新扫码"覆盖。
  否决（本期）。
- **多实例 + Redis**：收益是"中转不停机"，但个人工具的重启就是几秒，且手机本来就会重连。
  否决。
- **解除 Flutter 版本锁**：锁的成本是"用不了上游新特性"，收益是"将来接鸿蒙不用回改一大片"。
  鸿蒙只是暂缓不是放弃，所以锁继续。否决（解锁）。

## Consequences

- 文档里三处"刷新令牌"的措辞改成"只存不用"，并指向本篇（`remote-channel.md` §8.2、§12.1、
  `pairing-v2.md` §5）。
- `memory.md` 的"已知缺口"不再把这三条列为缺口，改为记录在"范围决定"里。
- 方法面的优先级因此变化：`devices.revoke` 被确认为"不需要 DSH 支持"（名册写入方本来就是
  电脑侧），从"等 DSH"变成"连接器自己的事"。
- 鸿蒙相关的既有调研文档（`channel-review-notes.md` §5、`app-platform-boundaries.md`、
  `design-and-tech-plan.md` §3/§13）不改内容，只在本篇记下"暂缓"。
