# Agent Note: 配对帧是明文，且握手完成前就要放行

Status: implemented（协议词汇 + 门禁；连接层分发与装配见"仍未做"）

## Problem

直连配对（二维码里带电脑的直连地址，手机扫码后直接连电脑）需要在**密钥建立之前**
把配对请求送到电脑侧。而我们的连接层有两条硬规则正好挡着它：

1. **`needsBox`**：除握手三帧与 `presence` 之外，所有帧都必须封箱（§3）。配对请求到达时
   **还没有密钥** —— 按原规则它会被判为"该封箱却没有密码器"，于是**被丢掉并留声**，
   配对永远做不成（而且症状是"扫了码没反应"）。
2. **握手门禁**（`assertHandshakePhase`）：握手完成前只接受握手三帧，其余一律
   `protocol/bad-frame` **并关闭连接**。配对请求恰恰必须在这之前到达。

## Decision

新增两种**明文**帧 `pair`（手机→电脑的配对请求）与 `pair-ack`（电脑→手机的回执），
并把它们放进两个"例外集合"里：

- `PAIRING_FRAME_TYPES = ['pair', 'pair-ack']`（`protocol/frame.ts`）——**和 `HANDSHAKE_FRAME_TYPES` 一样是唯一一处判据**，
  `needsBox` 与握手门禁都从它取，不再各自写一份字符串。
- `needsBox('pair') === false`：密钥还没建，谈封箱没有意义；`box` 里就是明文 JSON。
- 门禁放行配对帧，但**其余业务帧在握手完成前仍然一律拒绝**（否则"未加密的业务帧"可能溜进来）。
  报错信息同时列出两份清单，免得后来人看到"只接受 hello / hello-ack / confirm"而以为配对帧是漏掉的。

**凭什么可以明文**：载荷里带的是配对码的**哈希**（§12.1），不是码本身 —— 码只出现在二维码
这条带外路径里。所以即便这条连接穿过不可信中转，泄露的也只是一个"无法反推码、且一次性比对用"
的哈希。这一条是上一轮改请求格式时定下的，本轮只是让协议层承认它。

准入门槛（可机械判定）：

1. 帧类型清单（契约 §3）里含 `pair` / `pair-ack`。
2. `needsBox('pair') === false` 而 `needsBox('req') === true`。
3. `assertHandshakePhase({t:'pair'}, false)` 与 `{t:'pair-ack'}` **不抛**；
   `{t:'req'}` 仍然抛（错误信息里两份清单都在）。

## Alternatives considered

1. 把配对请求塞进 `hello`（例如给 `hello` 加一个可选字段）
   - 最强的理由：不加帧类型，改动最小；`hello` 本来就在握手阶段。
   - 为何被否：`hello` 的语义是"我要开始握手，这是我的设备 id/公钥/签名/nonce"，它**已经带签名**；
     把"我还没配对，这是我的配对请求"混进去，会让握手驱动器平白多一条前置分支，
     而两者的失败处理完全不同（握手失败要关连接，配对失败**不能**关 —— 手机还要能显示"码过期了"）。
2. 用一条独立的 HTTP 端点做配对（不占用帧协议）
   - 最强的理由：与帧协议解耦，明文/封箱这些规则一概不碰。
   - 为何被否：那要给桥接再加一个监听面（端口、TLS、认证、限流都要重新做一遍），
     而直连模式下手机**本来就连着一个 WSS 端点** —— 复用它只需要两种明文帧。
     中转模式将来也一样：中转把 `pair` 帧转给电脑侧即可。
3. 让配对帧也"尽量封箱"（有密钥就封、没有就明文）
   - 最强的理由：看起来更安全（密文优先）。
   - 为何被否：那会造出**同一帧类型两种线格式**，而"这一段到底该不该有 box"正是本项目
     反复警惕的"字段有两个意思"。配对帧永远出现在无密钥阶段，明文是它的定义。

## Consequences

- 收益：直连配对在协议层已经没有障碍；两份"例外集合"都只有一处判据，`needsBox` 与门禁不可能漂移。
- 代价：多两种帧类型（`RoutingView` 与窗口算术都从 `FRAME_TYPES` 取，无需另改）。
- **仍未做（下一轮，按顺序）**：
  1. ~~连接层分发~~ **已完成（同日）**：查下来入站**不需要改** —— 连接层在握手完成前本来就把非握手帧
     交给 `options.onFrame`（`connection.ts:415-419`），而门禁已经放行配对帧。
  2. ~~明文回执路径~~ **已完成（同日）**：`sendPairingFrame`（收窄成只接受 `pair` / `pair-ack`，
     与 `sendHandshakeFrame` 并列），并把 `write` 里"无 `fc`、不封箱"的判据从
     `isHandshakeFrameType` 换成 **`isPreKeysPlaintextFrame`**（握手三帧 ∪ 配对两帧）——
     一处集合决定两件事，正是本轮的原则。测试两条：未握手能收能发、明文无 `fc`、全程不关连接；
     以及递 `req` 进配对入口只会留声、不会发出去。
  3. **装配**：把 `pairing.ts` 接进出码入口（一条 DSH 命令或设置页）与 `devices` 表写入 ——
     配对成功后手机接着走正常握手，那时 `peerOf(devId)` 才有设备行。
  4. **e2e**：`pair` → 设备行写入 → **同一连接的握手成功**。这条是配对的端到端证据。
