# 设备管理以本地提交完成，名册共享 FIFO 与显式同步状态

Status: implemented

## Problem

本地行已删除或停用，却还等待公网名册上传才返回；缺中转令牌甚至将已提交的本地动作报告成失败。批删每台单独调用 delete，宿主因此多次序列化、fsync 并原子重写整域。并发名册无发布顺序，迟到旧投影能覆盖停用。客户端又等所有读面才更新清单、保存直连端口还盯无关 relay 轮询 5.5 秒。仅正常关闭会让已删除的手机靠匿名换票猜原因，错过撤销终态。

## Decision

筛选/整批拒绝/在线保护保持原契约，最终集合用宿主 deleteMany 一次持久提交，不逐行后备；API 只有本地提交确认后才完成。依据已核实的 `packages/storage/storage-domain/src/domain.ts:360–372`，批存在性、后端提交与内存更新均在宿主单写链槽内完成。

等待式与后台名册发布共享一个 FIFO。后台只 schedule，不让本地管理与配对回执等待公网；状态由发布器唯一持有 pending/synced/error/deferred，旧任务完成不能覆盖最新状态，后台错误有状态和日志。未连接不读取令牌或发 HTTP，重连沿原路径全量重报，不加私有重试/超时。所有设备写错误在一个 HTTP 边界原文转失败，不制造 ok。

读面各自提交，设备操作只等待已确认的 status；先发旧快照迟到不能覆盖新清单。连接保存使用后端已完成本次重建的回执，不再盯无关 relay 轮询。同步状态显示本地已完成与后台状态，并提供只读刷新，不重新锁住设备操作。

明确撤销/删除或已知失效身份用现有 `4003 / protocol/not-paired` 关闭终态，手机只清当前槽并停止盲目重试。普通停止与网络切换仍是 `1000 / stopped`，不得误清凭据。

## Alternatives considered

- **等待远端同步成功再完成本地动作**：最强理由是返回时名册最接近即时一致；被否是公网/令牌状态绑架了离线可用的本地管理，而且已提交结果不能被说成没发生。
- **客户端先乐观删行**：最强理由是响应最快；被否是写失败会展示假成功。清单仍取服务端确认过的真实状态，只拆掉无关读面屏障。
- **并发逐行删除**：最强理由是代码小且貌似吞吐更高；被否是宿主本就串行提交，每台仍重写整域，已有批原语才消除写放大。
- **给公开换票错误或删行后未知令牌加新推断**：最强理由是不动关闭接口；被否是未知令牌与名册暂未同步无法区分。已知本地撤销直接使用已有协议终态，不新增猜测或等待手机确认。

## Consequences

收益是本地操作不等待公网/无关读面，批提交减少写放大，旧投影不再最终盖掉新状态。代价是名册可暂时滞后，操作者看到 pending/deferred/error，并可刷新；synced 仍以既有 2xx 应答为确认，不另造 accepted-count 策略。

已经开始的 HTTP 未主动 abort；热改地址/令牌不是跨存储原子快照，排队旧投影可能先发到新 relay，随后 FIFO 的新全量收敛。这些不是“瞬间从不出现旧投影”的承诺。轮换裁剪与手动撤销仍基于本地权威行，不把中转作为授权所有者。
