# Agent Note: 中转的一次性 ticket —— 凭据不进 URL 的做法是"用令牌换一张短命票"

Status: implemented（`relay/src/tickets.ts`；`ws` 入口与 `POST /ws-ticket` 的 HTTP 面见"仍未做"）

## Problem

契约 §2 定下了连接建立的形状：**手机先 `POST /ws-ticket` 换一次性 ticket，再带 ticket 升级；
电脑侧直接带连接器令牌**。为什么要多这一跳，而不是直接拿令牌升级？

因为 WS 升级的目标是一个 **URL**，而 URL 会进日志、进代理记录、进浏览器/客户端的网络面板。
把长期令牌放进去等于把它抄送给了每一层中间设施。用票换一下，就把"凭据出现在 URL 里"
压缩成"一张 **60 秒内有效、用过即废的随机票**"出现在 URL 里 —— 泄露的窗口与价值都被压到最小。

## Decision

`relay/src/tickets.ts` 四条纪律，缺一条都不成：

1. **票是 128 位随机**（16 字节 base64url）—— 它本身就是凭据，可猜就等于可冒充。
2. **只存哈希**（sha256）：与配对码（§12.1）、令牌摘要（§12.2）同一条纪律 ——
   中转的库或日志被读到时，里面的东西不该直接能用。票是一次性的，所以"存哈希"的代价为零。
3. **绑定设备身份**：换票时认证出的 `deviceId` 记在票上，升级时必须拿回同一个 ——
   否则 A 的票能被 B 拿去冒充 A。
4. **一次性 + 短 TTL**：认领即删（先删再返回，任何路径都不会用两次）；
   过期在认领时就地作废，不指望清扫兜正确性（与去重表、配对登记同一条纪律）。

**TTL 取 60 秒，这是我们的选择**（契约只说"一次性"，没定秒数）：够一次"换票 → 立刻升级"
的网络往返（含弱网重试一两次），又短到泄露基本没有可用窗口。数值写在这里，免得下一个人以为它是契约定的。

准入门槛（可机械判定）：7 条用例 —— 发票/消费绑定、一次性、未发票值与**改一个字符**、
过期就地作废、票值形状（base64url 而非十六进制哈希）、`prune` 只清过期的、两次发票不同票。

## Alternatives considered

1. 直接把连接器/设备令牌放进 WS URL（少一跳）
   - 最强的理由：少一个 HTTP 端点、少一张状态表、少一次往返。
   - 为何被否：URL 会进日志与中间设施 —— 那是把长期凭据抄送给每一层。
     契约 §2 明写"令牌不进 URL 与日志"，这一条是它的实现方式。
2. 票不过期（只靠一次性）
   - 最强的理由：少一个时钟，行为更简单。
   - 为何被否：手机换票后如果网络断了、升级一直没发生，那张票会**无限期**有效 ——
     而它此刻正躺在客户端的某个日志或缓存里。TTL 是给"票已泄露但还没被用"这个窗口封顶的。
3. 票存在库里（而不是内存）
   - 最强的理由：中转多实例部署时任意实例都能校验同一张票。
   - 为何被否：当前中转是单进程（拓扑 §2 里它就是一个服务）。多实例是**将来**的事，
     而那时需要的不是一个"把票写盘"的补丁，而是统一的会话外部化（票、登记、路由状态一起搬）。
     现在写盘只会让"票"这一处看起来支持多实例，实际路由状态并不支持 —— 那更危险。

## Consequences

- 收益：设备入口的安全前置就绪且可测（26 条 relay 用例：路由 7 + 登记 6 + 大脑 6 + 票 7）；
  票的四条纪律各有一条会红的用例。
- 代价：中转多一张内存状态表（60 秒窗口内很小）；HTTP 面与 `ws` 入口仍未写。
- **仍未做（下一轮，按顺序）**：
  1. `POST /ws-ticket` 的 HTTP 面：校验设备令牌 → `pairing.claim(codeHash)` → `tickets.issue(deviceId)`。
  2. `ws` 两个入口：连接器（校验连接器令牌）与设备（消费票）。**`ws` 在中转是运行时依赖**
     （中转要接受连接，而连接器只拨号、用 Node 自带客户端）。
  3. `relay/` 的工程骨架（package.json / tsconfig / 测试脚本；现在仍靠连接器的工具链跑）。
  4. 电脑侧出码时的那次登记调用（走同一套 HTTP 面）。
