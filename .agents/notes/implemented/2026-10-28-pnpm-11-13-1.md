# pnpm 版本基线：11.13.0 → 11.13.1

- 日期：2026-10-28
- 状态：implemented

## Problem

`connector/package.json` 的 `packageManager` 钉的是 `pnpm@11.13.0`，而 npm registry
对这个版本给出**明确的弃用警告**：

```text
npm warn deprecated pnpm@11.13.0: This is a broken version.
Please install pnpm v11.13.1 or newer
```

`packageManager` 是 corepack 的输入：钉一个"官方说坏的版本"，等于让换机器/换人时
**自动装到一个坏 pnpm**。而 pnpm 坏掉的表现是任何命令都 `MODULE_NOT_FOUND`
（本机那次的具体成因不是这个版本，见 `tools.md` 的 Pitfalls —— 独立安装的虚拟库
被 prune 后 shim 成了死指向），排错时很容易把两件事混成一件。

## Decision

把 `connector/package.json` 的 `packageManager` 改为 `pnpm@11.13.1`。

准入门槛：`pnpm --version` = 11.13.1；`cd connector && pnpm exec tsc --noEmit &&
pnpm build && pnpm test` 三条全绿（686 项）；`pnpm install` 不再报 deprecation。

## Alternatives considered

- **保持 11.13.0**。
  最强理由：`packageManager` 是"仓库声明的事实"，改它会让别人的锁文件生成器版本号
  与本仓声明不一致，而升级本身没有带来任何代码收益。
  被否：registry 已经把这个版本标成 broken。**留着一个已知坏的钉子是纯负债** ——
  它不会在 CI 报错（本仓没有 CI），只会在下一次换机器时变成"pnpm 一上手就炸"。
- **降到 11.7.0**（本机 `%APPDATA%\npm` 里那份完好、能跑通全部门禁的版本）。
  最强理由：这正是修复过程中实际验证过、能跑 686 项测试的版本，风险最低。
  被否：11.7.0 是"碰巧装着的"，不是"当前修复线"；11.13.x 修了 11.13.0 的缺陷，
  与仓库原本想钉的版本同一条线，差异最小。
- **删掉 `packageManager` 字段**。
  最强理由：不钉版本就没有"钉到坏版本"的风险，corepack 会跟随本地。
  被否：本仓 `connector/` 与 `relay/` 是两个独立 pnpm 工程，`packageManager`
  是唯一能让两端/多台机器落到同一 pnpm 行为的声明；删掉等于把工具链交给运气。

## Consequences

收益：corepack 用户不会再被装到官方标坏的 pnpm；`pnpm install` 的弃用警告消失。

代价：

1. 这是一次**工具链版本变动**，锁文件格式若在 11.13.x 内部有差异，第一次
   `pnpm install` 可能重写 `pnpm-lock.yaml`；本仓没有 CI，只能靠人跑门禁发现。
2. 它不修"独立安装被 prune 后 shim 死指向"那个环境问题 —— 那是 PATH 层面的坑，
   记在 `tools.md` 的 Pitfalls，与版本号无关。
3. `relay/package.json` 没有 `packageManager` 字段，本次不动；两端 pnpm 版本
   仍靠本文件与人的自觉对齐。
