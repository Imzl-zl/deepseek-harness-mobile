# 移动端设置采用目录首页 + 证据分层二级页

Status: implemented

## Problem

42 项设置调研已经给出了处置结论,但如果把这些项直接搬进一张设置页面,会把手机变成桌面设置表的缩小版,同时把"手机本地偏好"、"需要 bridge 的电脑设置"、"只读状态"和"插件页面不可渲染"混在一起。后来者会无法判断某一项是未实现、只读、需要 bridge,还是本来就不属于手机。

## Decision

采用 **设置首页目录 + 二级设置页** 的信息架构,并以调研中的处置边界作为页面准入规则:

- 首页只展示连接状态与五组入口:通用、模型与服务商、权限与会话、内置插件、Agent 预设、关于与连接。
- 通用页承载手机本地偏好,不覆盖电脑 DSH 同名偏好。
- 模型页必须显示连接电脑/本机运行的分叉,API key 只能显示状态,不能显示值。
- 权限页复用现有访问模式 sheet,不创建第二套权限真值。
- 内置插件页只读展示运行中/unavailable 等状态,不伪造插件自定义 React 页面。
- Agent 预设页显示列表与默认值,配置只读。

准入门槛:每个首页入口必须对应 `docs/settings-porting-notes.md` 中已核实的设置平面;需要 bridge 的项必须显式标注,未加载/只读状态必须可见。

## Alternatives considered

1. **把 42 项全部平铺在一个设置页**。最强理由是一次性接近桌面 DSH,用户不用二次点击;否决原因是手机信息密度过高,无法表达设置平面与 bridge 边界,也会让本地偏好和电脑配置混存。
2. **完全照搬 DSH 的 settings.section 导航**。最强理由是与 DSH 页面结构一致、迁移成本低;否决原因是 DSH 的侧边栏 Plugins 面板并不属于 settings.section,子智能体/终端/网页搜索不能被误放进设置页,且手机不具备桌面侧栏语义。
3. **每个设置行直接接真实 bridge 写入**。最强理由是页面看起来完整、减少"需 bridge"提示;否决原因是当前 bridge 没有 settings/credentials/plugin 管理方法,DSH 对非 loopback 写入还有明确边界,未经扩展不能声称可写。
4. **把插件自定义页嵌进设置页**。最强理由是用户能看到电脑端已有页面;否决原因是插件页面是 React slot 组件而非可序列化页面描述,手机端没有通用渲染输入,应显示边界而不是伪造。

## Consequences

- 收益:首屏可扫描、二级页可承载足够字段;每个不可用状态有明确原因;设置页和调研清单一一对应;权限和密钥不产生第二套真值。
- 代价:用户需要多一次点击;模型/provider 与电脑侧设置在 bridge 扩展前只能看状态;插件配置与自定义页面会出现"需在电脑端编辑"的断点;本机运行模式将来需要独立的数据源和文案。
- 代码代价:原型新增 settings 页面栈、动态二级页、返回层级与 18 项设置回归脚本;截图产物作为视觉验收证据。
