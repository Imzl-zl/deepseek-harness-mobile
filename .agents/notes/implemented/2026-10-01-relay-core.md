# Agent Note: 中转大脑 —— 三种帧走三条路，`id` 因此必须可见

Status: implemented（`relay/src/core.ts` + 契约 I10 的扩容；网络层见"仍未做"）

## Problem

路由核心与配对登记各自就绪后，还差把它们**合成一个东西**：一行从某条连接进来，
该投给谁？而这个问题有三种答案，取决于帧：

1. 带 `sid` 的帧 → 按"`sid` → 连接器 / 设备在听"的归属表（§2/§5.5）；
2. `pair`（**没有 `sid`**）→ 按 ticket 绑定的那台连接器（§12.1）；
3. `pair-ack`（**没有 `sid`**）→ 回到发起配对的那台设备。

第三条暴露了一个**契约层面的缺口**：`pair-ack` 与 `pair` 之间只能靠**帧头 `id`** 关联
（`t`/`sid`/`seq` 里没有它），而 I10 原先把中转可见字段限制成"会话别名、`seq`、`fc`、帧类型"——
**没有 `id`**。于是要么中转没法把回执送回去，要么它得靠"最近一次配对"猜（多台设备同时配对时必错）。

## Decision

**把帧头 `id` 加进 I10 的可见字段**（契约 §1 已改），并在注释里写清它为什么不算越界：
`id` 是**不透明的关联标记**，不携带任何内容信息（方法名在 `box` 里、载荷也在 `box` 里，两者都不可见）。
中转要能"按连接投递回执"，就必须有一个能从回执认出发起方的字段 —— 这正是 `id` 在帧头里的用途。

`core.ts` 的三条规则与三处清理：

| 输入 | 投给谁 |
|---|---|
| 电脑侧的 `sid` 帧 | 在听这个 `sid` 的**设备**（`routing.fromConnector` 现在返回目标列表 —— 路由层不认识连接，只回答"谁在听"） |
| 设备侧的 `sid` 帧 | 归属表里的**连接器**；没有归属就丢弃并计数 |
| 设备侧的 `pair` | ticket 绑定（`claimTicket` 时记下）的连接器；同时记住 `id → 设备` 供回执回程 |
| 电脑侧的 `pair-ack` | 按 `id` 找那台设备（找不到、或设备已断开 → 丢弃并计数） |

清理（三处都会留下"指向已消失连接的投递"，缺一处症状都是"看起来一切正常但对方收不到"）：
连接器断开 → 清它未认领的登记 + 撤销设备的绑定；设备断开 → 清窗口、订阅与配对绑定。
另外**认领时再查一次连接器在不在线** —— 登记可能指向一条刚断开的连接。

准入门槛（可机械判定）：6 条用例覆盖上表每一行 + 4 种丢弃（坏行 / 未知 `sid` /
没换 ticket 的 `pair` / 来源不在线）+ 两处断开清理 + "认领时连接器已离线"。

## Alternatives considered

1. 让中转按"最近一次转发给该连接器的 `pair`"猜回执去哪
   - 最强的理由：不必扩容 I10，契约一个字都不用改。
   - 为何被否：两台设备同时向同一台连接器配对时必然猜错（回执投给错设备，
     症状是"配对码用对了却提示不对"）。而"猜"在这里的代价是把一次**关联错误**
     伪装成一次认证失败 —— 与第 27 轮否掉"猜最近出码的连接器"是同一类问题。
2. 让 `pair-ack` 也带上 `sid`（例如用一个专用的 `pair:<codeHash>` 假会话名）
   - 最强的理由：那样 `sid` 路由表就能覆盖它，中转完全不必知道 `id`。
   - 为何被否：那是**伪造会话别名** —— `sid` 是不透明别名，把配对塞进去会让
     "`sid` 一定是会话"这条不再成立（而中转的重放窗口、限流、审计全都按 `sid` 分组）。
3. 把 `id` 干脆完全放开（I10 改成"中转可见全部帧头"）
   - 最强的理由：以后要什么字段都不必再改契约。
   - 为何被否：I10 是**不变量**，它约束的是"中转能知道多少"。逐个字段决定
     （`sid`/`seq`/`fc`/`t`/`id`，每个都写清为什么）比"全放开"更能挡住下一次顺手读取。

## Consequences

- 收益：中转的"大脑"可以脱离网络测（19 条 relay 用例：路由 7 + 登记 6 + 大脑 6），
  而且它**定义了中转与传输之间的接口**：`onLine(来源, 原始行) → [{目标, 原始行}]`。
  网络层随后只做"收一行 / 投一行"，不需要懂路由。
- 代价：I10 的可见字段多了一个（已在契约里写明理由）；`routing.fromConnector` 的返回类型变了
  （从 `void` 变成目标列表 —— 路由层只回答"谁在听"，过滤"还在不在线"是大脑的职责，
  那样路由层仍然不认识连接）。
- **仍未做（下一轮）**：网络层（`ws` 两个入口 + `POST /ws-ticket` + 连接器令牌 + 限流）、
  `relay/` 的工程骨架（`ws` 在中转是运行时依赖）、电脑侧出码时的那次登记调用。
