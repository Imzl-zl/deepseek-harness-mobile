# Agent Note: 拨号改竞速，增量缓冲改按"在服务的设备"裁剪

Status: implemented

实现 `proposed/2026-10-29-one-phone-many-computers.md` 落地顺序第 3 步（通道）。
第 1 步（归属）见 `implemented/2026-10-30-endpoint-and-ui-state-host-scoping.md`，
第 2 步（凭据）见 `implemented/2026-10-30-pairing-slots.md`。

## Problem

两处"多机之后才会暴露"的旧假设：

1. **拨号是串联的**：`EndpointTransport.connect()` 按表顺序一条一条拨，每条等满
   3s（直连）/ 10s（中转）超时。2026-10-17 真机上三个死 IPv6 地址把冷启动拖成 **30 秒**。
   端点表越长，最坏耗时线性增长，而用户看到的是一个没有阶段的转圈。
2. **缓冲裁剪点 = 全部配对设备水位的最小值**（`connector/src/session-buffer.ts`，
   契约 §5.5 原话"全部配对设备"）。从没确认过的设备按 0 算 ⇒ 一行都不裁。
   独占模型下"配 3 台只连 1 台"是**常态**，于是缓冲永远涨到 16 MiB / 10000 条，
   之后每次切回那台都退化成一次全量快照。

## Decision

### 1. 拨号竞速（只竞速"连接建立"）

- 按表顺序**错开 250ms** 启动（Happy Eyeballs 的节拍），**第一个建立 socket 的赢**。
- 赢家把流交给连接层（握手仍在那里，一层不多）；**输家连上也不进握手，立刻关**。
  输家不报 `onAttempt` 成功（它不是这一轮的连接），失败照实报（它确实拨过、确实没通）。
- 总耗时 ≈ 单条上限 + (N−1)×250ms，不再随端点条数线性增长。
- 文件名与入口不变：`core/endpoint_transport.dart` 的 `connect()`。

### 2. 中转端点同一时刻只让一条在飞

中转对**同一个 `(connectorId, deviceId)`** 的新数据通道会先关掉上一条
（`relay/src/server.ts:184-185` 的 `replaced`，换网重连靠的就是它）。
两条中转端点并发会各自换票、各建一条数据通道，**后到的把先到的顶掉** ——
若先到的正是赢家，它会被中转无声关掉。

所以 relay 端点用一道容量 1 的闸串行；直连监听面没有这层"同设备单通道"语义，
可以随便并发。两条中转端点因此**互相不竞速**（少见配置；换来的是不自伤）。

### 3. 错误语义

- 全部失败：原因取**表里最后一条**（与串联时代一致），`code` 一起带上去。
- 终态错误（`ClientAction.rePair`）**立即结算**，尚未开始的端点不再拨。
  已经在飞、或者已经被选为赢家的连接收不回来（`ChannelTransport` 没有取消缝）——
  但同一身份在握手处会以 `not-paired` 失败，最终动作仍是回配对页。
- 工厂抛的非传输错误（代码 bug）**照旧抛出去**，不吞。

### 4. 缓冲裁剪点：在服务的设备

契约 §5.5 的"全部配对设备"改成：

```text
在服务 = 此刻在线 ∪ 本轮确认过（有 persisted 记录）
裁剪点 = 在服务且未吊销的设备水位最小值
```

- **在线但还没确认** ⇒ 按 0 保护（刚连上、还没写盘，不能裁掉它手里那段）。
- **从没连过**的已配对设备**不参与** —— 这是 problem 2 的根因。
- 已吊销 / 已删除设备的旧水位不参与（不占坑；与占用位"停用不占位"同一条）。
- 一台在服务的都没有 ⇒ 0（一行不裁）：宁可留着等重连，也不因为"名册有设备但都不在线"丢事件。
- 装配层（`connector/src/index.ts`）把 `presence.devices()` 的在线集喂进来。

这是**对契约文字的偏离**，所以 `docs/subsystems/remote-channel.md` §5.5 同批改成上面的规则。

准入门槛（可机械判定，均已跑过）：

1. **竞速只赢一条**（准入门槛 8d）：两条直连都启动、先连上的赢，输家 `close` 一次、
   不报 ok（`app/test/endpoint_transport_test.dart` 的「第一个先通」「输家连上」）。
2. **慢端点不拖累**：两个在飞的死端点不完成时，赢家已返回（同文件「两条死端点不再拖累」）。
3. **中转串行**：前一条 relay 还在飞时，第二条 relay **连工厂都没造**；闸放开后才启动
   （同文件「中转端点串行」）。
4. **终态不换端点**：401 结算后 `activeEndpoint` 为空、错误码是 `notPaired`
   （同文件「终态错误不再换端点」，断言从"只启动了一条"改成"没有赢家"）。
5. **契约同批**：`docs/subsystems/remote-channel.md` §5.5 的规则文字与
   `session-buffer.ts` 的实现一致。

变异校验（一次性，条数写进提交）：
- 裁剪点改回"全部配对设备（未连过按 0）" → 恰 3 红（配 3 连 1 / 服务过又离开 / 已吊销不占坑）；
- 去掉 relay 闸 → 恰 1 红（中转串行那条）；
- 输家不关 → 恰 4 红（三处"立刻关"断言 + 中转串行里 direct 那条）。

## Alternatives considered

1. **保留串联，只把单条超时调短**
   - 最强的理由：不动并发与错误语义，改动最小；死 IPv6 每个少等几秒。
   - 为何被否：总耗时仍是 N×超时。三个死地址就算压到 1s，也要 3s，且端点越多越慢；
     而"首选通常最快"这一点竞速天然利用，串联完全浪费。
2. **竞速所有端点，不做 relay 闸，靠中转 `replaced` 兜底**
   - 最强的理由：实现最简，两条 relay 也能竞速；反正中转会关掉上一条。
   - 为何被否：被关掉的可能是**赢家**。那会让"连上了又自己断了"，症状与换网重连完全一样，
     而根因是我们在跟自己抢同一条通道。
3. **给 `ChannelTransport` 加取消缝，输家"拨到一半"就中止**
   - 最强的理由：不占 socket、不浪费握手前的 RTT，输家立即释放。
   - 为何被否：接口加一个方法要让三个实现（WS / 带票 WS / 假替身）都实现，
     而收益只是"输家多活几十毫秒"。现在的做法是"连上就关"，同样保证**不进握手**；
     真正的半开风险来自握手完成后的链路，那一层有 keepalive。
4. **裁剪点只按"在线设备"**
   - 最强的理由：只保留确实有人在收的那段，内存最省。
   - 为何被否：设备刚断开（换网、切后台被杀）时，它已经确认过的水位还是要接着收；
     只看在线会让"掉线一秒钟"退化成一次全量快照。ack 记录正是"最近活跃"的事实来源。
5. **给"最近活跃"加时间窗口（比如 10 分钟没连就不保护）**
   - 最强的理由：设备彻底不回来了也不占内存。
   - 为何被否：那是一道新的时间边界，宿主与契约都没有；而且"多久算最近"只能猜。
     ack 记录 + 吊销过滤已经覆盖了"永不回来"的两种情况（撤销 / 上限快照退化）。
6. **把缓冲上限调小，让快照退化更早发生**
   - 最强的理由：一行配置，永不裁剪也不会撑爆内存。
   - 为何被否：上限是契约 §5.5 / §10 的一组实测标定值（16 MiB / 10000 条）；
     调小只是让"每次切回都全量快照"来得更早，问题原样在。

## Consequences

- 收益：冷启动不再被死地址线性拖慢；多机常态下增量缓冲能真正裁剪，切回不必每次全量重灌。
- 收益：拨号有明确阶段（启动 → 赢家），设置页的"通不通"仍按端点各自记账（输家失败也报）。
- 代价：输家会在选出赢家后短暂多活一拍（等到 `connect()` 完成才关）——
  协议层一帧未发，代价是一个已建立的 socket 和一次关闭。
- 代价：两条中转端点不再互相竞速（串行等待），这是为 `replaced` 语义付的代价；
  常见配置是"一条中转 + 若干直连"，不受影响。
- 代价：终态错误在"已经赢了"之后才到达时，不会被回滚成失败（流已经交出去）——
  用户看到的仍是握手失败后的 `not-paired`，只是晚一个 RTT。
- 代价：缓冲裁剪点依赖 `presence` 的在线集，`session-buffer` 多一个可选依赖；
  不给在线集时（单测 / 别的装配）退化成"只按 ack 记录"，语义仍成立。
- 未覆盖：竞速目前**没有总预算**（15s 是第 4 步的切换状态机）；本节只保证
  "不再线性增长"，不保证"到点一定有结论"。
