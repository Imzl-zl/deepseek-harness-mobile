# Agent Note: 令牌签发 —— 配置是摘要表，不是凭据表

Status: implemented（`relay/src/issue-token.ts` + 入口的 `--issue-token` 模式；3 条用例）

## Problem

第 41 轮把中转的令牌校验做成"**只存摘要**"（配置里放 `sha256(token)`，§12.2），
但签发那一半没做：摘要要**手工算**，而手工算意味着有人会把明文令牌先贴在某个临时文件里
再 `sha256` —— 那正是这条纪律想避免的事。

而且签发与启动有一个**顺序**上的硬要求：签发必须能在 `tokens` **为空**时运行，
否则第一台设备永远没有引导路径（启动要求 tokens 非空，而签发又要先启动 ⇒ 死锁）。

## Decision

`relay/src/issue-token.ts`：

- `issueToken({kind, id})` → `{token, hash}`：令牌 16 字节 base64url（128 位随机，
  与 `requestId`、配对码、一次性 ticket 同规格 —— 它是长期凭据，但长度不该因为"长期"而缩短，
  随机性是它唯一的防线）；摘要 `sha256(token)` 十六进制。
- `appendTokenToConfig(configPath, {kind, id, hash})`：读配置、追加摘要、写回；
  **同一 `(kind, id)` 重新签发会替换旧摘要** —— 否则旧令牌仍然有效，那是"吊销不了"的形状。
- 入口加 `--issue-token <device|connector> <id>` 模式：签发、写摘要、**把令牌打印一次**、
  退出（不启动服务）。这一段放在"tokens 为空就拒绝启动"**之前** —— 那就是引导路径。

**唯一必须钉住的安全性质**：令牌本体只出现在签发者眼前，**绝不写进配置**。
写进去那份配置就从"摘要表"退化成"凭据表"，而 §12.2 只存摘要正是为了
"配置或库被读到时里面的东西不能直接用"。用例直接**读回文件断言不含令牌**。

准入门槛（可机械判定）：3 条用例 —— 令牌形状与摘要一致、每次签发不同；
**配置里不含明文令牌**（含摘要）；追加保留既有条目 + 重新签发后旧令牌失效而别的身份不受影响
（用 `createDigestAuthenticator` 验证）。外加一次真跑：空 `tokens` 的配置 → 签发 →
打印令牌一次 + 配置里只有摘要（已人工核对输出）。

## Alternatives considered

1. 签发时把明文令牌也写进配置（并注明"仅本地"）
   - 最强的理由：操作者日后还能查回来，不必"只显示一次"。
   - 为何被否：那等于把 §12.2 的纪律在入口处推翻，而且"日后能查回来"对长期凭据来说是
     **纯风险**（多一处泄露面、少一次轮换动力）。
2. 让签发命令去连数据库（最终形态）
   - 最强的理由：与 §12 的表结构一致。
   - 为何被否：库还不存在；而摘要表的**形状**已经定下，将来把 `appendTokenToConfig`
     换成"插入一行"即可，签发逻辑与测试都不动。
3. 签发时不替换旧摘要（只追加）
   - 最强的理由：改动更小，且"轮换"应当是显式操作。
   - 为何被否：同一身份两条摘要意味着 `createDigestAuthenticator` 会因**重复条目拒绝启动**
     （第 41 轮那条判断），于是"重新签发"会变成"服务起不来"—— 那不是轮换，那是自伤。

## Consequences

- 收益：引导路径完整（空表 → 签发 → 启动）；"配置里没有明文令牌"这条安全性质有会红的用例；
  轮换语义明确（同身份替换）。
- 代价：配置文件的写回是**读-改-写**（无锁）：并发签发会丢一次。中转的签发是人工低频操作，
  所以先如实记下而不引锁 —— 将来若要多实例，那一步应当与"状态外部化"一起做。
- **仍未做**：`relay/` 的吊销（§12.2 的 `revoked_at`）；手机端 Dart 客户端；
  每连接状态那个岔口（监听面/多设备）。
