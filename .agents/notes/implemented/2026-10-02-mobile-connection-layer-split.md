# Agent Note: 连接层拆分——量出两处真耦合，也量出**一处不该拆**

Status: implemented（2026-10-02 落地：`connection_resources.dart` + `call_registry.dart`）

## Problem

### 一、`sync_client_impl.dart` 到了 971 行，六件事挤在一个类里

上一轮交付时我在笔记里写了"已接近该拆的边界"。这一轮先**量**再决定 ——
这是本项目第 61 轮起的一条纪律（"这是个大改动"应该先量再下），
而它上一轮救过一次（把"重构"降级成"搬家"）。

### 二、量出来的第一处：**两份重复的清单**

```
_box 6  _handshake 8  _subscription 6  _counter 3  _window 7  _splitter 3
```

六个字段、33 处引用。关键不是数量，而是：

- `_connect()` 里逐个**重置**（5 行）；
- `_enterClosed()` 里逐个**作废**（4 行）；
- **两处各写一遍同一个清单**。

两份清单迟早不一致，而漏掉任何一项都是**静默 bug**：漏 `box` 会让新连接用旧密钥
（症状"解不开"），漏 `splitter` 会把两条连接的字节拼在一起（症状"偶尔收到一帧乱码"）。
这正是"缺一个对象"的经典特征 —— 生命周期完全相同的字段散落在两个方法里。

### 三、量出来的第二处：**一个真缺口**（在途请求永远不返回）

`_pendingCalls` 是一张 `Map<String, Completer>`，**既没有超时，`_enterClosed()` 也不清它**。
后果：连接在请求在途时断掉，调用方的 `await` **永远不返回**。
而断连是**常态**（§2.1 明写"重连是常态，不是异常路径"），所以这条路必然走到 ——
UI 的表现是"转圈转到天荒地老"，用户只能杀掉 App。

先写用例复现（结果：2 s 超时先触发，而不是协议错误 —— 证明它确实挂着），再修。

### 四、量出来的第三处：**一处不该拆**

我原本计划把订阅面也拆成 `SessionHub`。量完发现它只有 **17 处引用**
（`_sessionControllers` 5 + `_live` 2 + `_emit` 3 + `LiveAccumulator` 4 + 其余 3），
而且**没有"两份清单"的问题**（它只在 `close()` 里被清理一次）。

所以**没拆**。理由写在 Alternatives 里 —— 这条比前两条更值得记：
"文件太长"本身不是拆分理由，**重复的清单**与**缺失的所有者**才是。

## Decision

**按"生命周期是否一致"拆，不按函数名或行数拆。** 两处提取：

1. **`ConnectionResources`** —— 六个字段收成一个对象，`dispose()` 一次性作废。
   于是"建一份"与"作废一份"各只有一处，不会漏。
2. **`CallRegistry`** —— 在途请求表 + `failAll()`。**它不跟着连接资源一起换**：
   旧 `id` 绝不能被新连接的应答兑现（那是上一条连接的请求），
   所以它挂在 `_SyncClient` 上、由连接状态迁移驱动。

同时删掉死代码 `_writableWaiters` / `_notifyWritable`（实测**没有任何生产者**：
手机侧只发 `req`/`res`/`credit`/`persisted`/`ping`，而 §4.3 只压可补的
`ev`/`live`/`job` —— 手机一个都不发）。

准入门槛（可机械判定）：

1. **每连接状态只在一处作废**：`ConnectionResources.dispose()` 是唯一的清单。
2. **在途请求遇到断连必须被拒绝**：`sync_client_test.dart` 有用例
   （它断言错误码是 `relay/offline`，并断言 `lastRejectedCalls == 1`）。
3. **`dispose()` 必须是同步的**（见下"代价"）。
4. 全部测试绿（132 项），`dart analyze --fatal-infos` 0 问题。

### 关键取舍一：`dispose()` 同步，而不是 `await subscription.cancel()`

我最初把 `dispose()` 写成 `Future<void>` 并 `await subscription.cancel()`。
**一条重连用例因此失败**（不是崩溃，是**时序漂移**）："资源已死"与"状态已 closed"
之间多了一个 `await` 窗口，而收口路径全在事件回调里，任何一条都可能在那个窗口里
被再次触发 —— 退避计时器的起点跟着漂。

修法是回到同步，并把理由写进代码：**`cancel()` 返回的 Future 只表示"清理完成"，
不表示"还会收事件"** —— 调用 `cancel()` 的那一刻起事件就不再投递了。
所以不需要等它（与电脑侧 `unawaited(...)` 的写法同一个理由）。

### 关键取舍二：在途请求用"连接级拒绝"，而不是"每请求超时"

两者都能让 `await` 返回，但**客户端动作不同**：
- 连接级拒绝 → 错误码 `relay/offline` → 动作是"退避重试"（请求本身没问题）；
- 每请求超时 → 动作是"超时重试"（而请求可能已经在电脑侧执行了）。

用连接级拒绝更准确：请求失败的原因是"这条连接没了"。而且它**不需要每个请求一个定时器**。

## Alternatives considered

1. **把订阅面也拆成 `SessionHub`**
   - 最强的理由：文件会更短（约 -60 行），而且"订阅"确实是一个独立概念。
   - 为何被否：**量完发现它只有 17 处引用、且没有重复清单** —— 拆它是纯搬家，
     收益是"看起来整齐"，代价是多一个文件与一层间接。而"文件太长"本身不是拆分理由
     （本项目 `AGENTS.md` §7 的立场：尺寸限制属于 linter，不属于人的记忆）。
     真正该拆的信号是**重复的清单**（`ConnectionResources`）与**缺失的所有者**
     （`CallRegistry`）—— 这两处都拆了。
2. **只做 `ConnectionResources`，不动 `_pendingCalls`**
   - 最强的理由：在途请求那个缺口是**既有行为**，可以单独排期；本轮只做"优雅拆分"。
   - 为何被否：量它的过程中已经写出了复现用例，而那个缺口的表现是
     **用户杀 App**（不是"偶发不便"）。既然已经证明了，修它比留着便宜。
3. **给每个请求加超时（而不是连接级拒绝）**
   - 最强的理由：不依赖连接状态，单个请求也能兜底（比如对端卡住但不掉线）。
   - 为何被否：超时的错误码与"连接断了"不同，而调用方据此分支 ——
     报错了类别就会让"重发"变成"重试同一个已执行的请求"。
     （对端卡住不掉线这一档，将来由 §9 的请求超时统一处理，那时它是**协议级**行为。）
4. **保留 `_writableWaiters`（"将来手机会发可补帧"）**
   - 最强的理由：契约 §4.3 是双向的，将来手机可能发 `job` 控制帧，那时需要它。
   - 为何被否：现在**没有任何生产者**，而"将来可能需要"的代码从来没被跑过 ——
     它会在真正需要时以"看起来能用但没测过"的形态存在。删掉，需要时随
     "手机发可补帧"一起加（那时它会有真实的调用方与用例）。
     `canSend` 的判定**保留**（它是一行、有契约依据），并在注释里写明为何目前恒为真。

## Consequences

- 收益：**修掉一个会让 UI 永久转圈的缺口**（在途请求遇到断连被拒绝，错误码 `relay/offline`）。
- 收益：每连接状态的"建/废"各只有一处，六个字段不会再漏掉一个。
- 收益：删掉 15 行死代码（`_writableWaiters` + `_notifyWritable`），
  并把 `canSend` 恒为真的原因写进注释（而不是让下一个人重新推导一遍）。
- 代价：**`sync_client_impl.dart` 没有变短**（971 → 969 行）。这不是失败 ——
  拆出去的是两个对象（各自带完整文档），而宿主多了装配与委派。
  如实记录：这次拆分的收益是**正确性**（两处真耦合 + 一个真缺口），不是行数。
- 代价：多两个文件（`connection_resources.dart` 143 行、`call_registry.dart` 76 行）。
  间接层多一层，读代码要跳文件 —— 由文件头的"为什么"补偿。
- **仍未做**：`platform/` 的真实 `ChannelTransport`、`data/`+`model/`、`ui/`、三端能力包。
  真机仍在整条链末端。
- **本轮验证了一个怀疑，结论是"没有这个 bug"**（如实记录）：
  我怀疑 `Keepalive` 不随连接重置会让"旧连接的沉默算到新连接头上"（刚连上就被踢）。
  写了两版用例都通过 —— 查明原因是 `hello` 经 `_write` 会重置它，把问题掩盖了。
  所以**不是 bug**，但"靠 hello 顺带重置"是**隐式耦合**（正确性依赖"握手一定会发一帧"）。
  这一条留作观察：若将来握手改成"不发帧也能完成"，它就会变成真 bug。
