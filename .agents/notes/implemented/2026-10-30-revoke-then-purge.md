# Agent Note: 撤销与清理分开（删除只对已停用的行）

Status: implemented

## Problem

"删除设备"在手机侧是**没有结论**的：行被硬删 → 名册差集把它带走 → 中转只剩
"不认识这枚令牌"（`device-unknown`），而它与"电脑刚启动、名册还没同步"**在中转侧
不可区分**。那台手机于是只会一直重试（结论后 60s 静默慢重试），永远走不到配对页。

手机唯一能"知道被移除"的通道是**换票 401 带原因**，而那只在**行还在名册里**时成立。
所以问题不是"缺一个信号"，而是**删除把发出信号的凭据一起删了**。

## Decision

**撤销（停用）是让手机知道的唯一通道；删除是清理，只能在撤销之后。**

- 面板：活跃行只有「接管（在服务时）/ 停用」；**「删除」只出现在「已停用」那一段**。
- 服务端：`POST /devices/remove {devIds}` 对未停用的行**整批拒绝**（全有或全无，
  `refusedActive` 回 id，路由回 400「先停用再删除」）。半成功会让操作者以为
  "删掉的那几台知道了"，而它们其实拿不到任何终态信号。
- 多选浮现栏的动作从「删除所选」改成「停用所选」（顺序调用同一个单台端点，
  不新开批量接口）。
- 按状态批量保留：`revoked`（常规清理）与 `all`（"重置这台电脑"，会连还在用的
  离线设备一起删 —— 那些手机只会重试到重新配对，界面上有单独的确认框）。
- **不做墓碑、不改协议**：墓碑（名册带"删过的哈希"）能解决同一个问题，但它是为
  "硬删活跃行"这个动作存在的；把动作去掉，就不需要那份要过期策略的状态。

## Alternatives considered

1. **名册带墓碑（`removed: [tokenHash…]`）**
   - 最强的理由：保留"一键彻底删除"的体验，手机仍能收到 `device-revoked`。
   - 为何被否：墓碑永久留着会无限增长，加 TTL 又要定"多久算久"；而它服务的场景
     （硬删一台正在用的设备）本身正是主流产品不提供的（OAuth/mTLS/MDM 都是
     撤销与清理分开：撤销保留记录，清理是带保留期的运维动作）。
2. **删除 = 软删 + 隐藏（加 `deletedAt` 字段）**
   - 最强的理由：一键删、手机也拿得到结论，面板不用改成两步。
   - 为何被否：要在 `peerOf` / `pairedAtOf` / 名册 / 面板 / prune 五处各加一条
     "已删也算失效"的判据 —— 五个可能判漏的地方，换来的只是省一次点击。
3. **删除时先自动停用再删**
   - 最强的理由：对操作者仍是一步。
   - 为何被否：行在同一瞬间消失，手机照样拿不到撤销信号（等于把墓碑问题绕回来了）。
4. **保持现状，只在界面提示"被删除的设备可能一直重试"**
   - 最强的理由：零改动。
   - 为何被否：那是把"手机永远不知道自己被移除"写成文档而不是修掉。

## Consequences

- 收益：停用（含「接管」）在手机侧第一次有**确定的结论**：清这一台的凭据、回配对页。
- 收益：删除仍然是真的删行（满足 2026-10-15 那次"记录删不掉"的诉求），只是顺序变成
  "先停用 → 再在「已停用」里删"。
- 代价：**活跃行的一键硬删没有了**（这是有意收回：那正是让手机失明的动作）。
  `removeScope('all')` 仍是"重置这台电脑"的口子，被它删掉的离线设备只会重试 ——
  确认框里写明。
- 代价：多选的动作从"删"变成"停用"，界面文案与用例同批改。
- 未覆盖：`all` 批量仍会留下"重试到重新配对"的手机（与删除同一类后果，但它有
  单独的、写明后果的确认框）。要彻底消除仍需要墓碑或 `deletedAt`，见 Alternatives。
