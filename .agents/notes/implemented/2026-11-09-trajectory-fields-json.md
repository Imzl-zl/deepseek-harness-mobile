# Agent Note: 轨迹段能看「原始 JSON」，但它标明是投影字段、不是原始 payload

Status: implemented

## Problem

轨迹页只能看到投影给出的东西：一段多长、成没成、标签是什么。想核对"这一段到底带了哪些
字段"时没有任何入口 —— 而 `trajectory` 投影本身**是有字段的**（`kind` / `seq` /
`startTime` / `endTime` / `offsetMs` / `durationMs` / `isError` / `label`），只是界面上
只用了其中两三个。

直接加一个叫「原始 JSON」的按钮很危险：投影只下发结构化字段，**电脑侧的原始事件帧没有过线**
（契约 §5.7 的投影包）。那个按钮一旦被当成"电脑侧到底发了什么"，拿它去排查线上形状就会得出
错误结论，而且不会有任何报错。

## Decision

段详情 sheet 加一个动作「原始 JSON」：把这几段的**投影字段**编成 JSON 展示
（可整段选中复制）。标题**必须**带「非原始 payload」，正文第一句必须说明"这些是轨迹投影的
字段，不是电脑侧的原始事件帧"。

准入门槛（可机械判定）：

1. JSON 的字段集合 = `TrajectoryStep` 的全部字段，逐字段原样：不派生、不做减法、缺席的保持 `null`（不补 0 —— 补 0 会让"进行中"变成"0 毫秒"）。
2. 对话框标题含「非原始 payload」；正文含「不是电脑侧的原始事件帧」。两条都由 `trajectory_json_test.dart` 断言。
3. 只有**段详情** sheet 有这一项；轮详情 sheet 不加 —— 那一屏是聚合数字，没有"字段"可看。

## Alternatives considered

1. 真的把原始事件帧接过来（新增 RPC / 让连接器把 payload 过线）
   - 最强的理由：这才是"这一轮到底发生了什么"的完整答案，排线上问题时不可替代。
   - 为何被否：宿主没有"给我这一段的原始帧"的接口，payload 大小也不受控（撞单帧预算，契约 §40）；而且这一批的目标是让已有的投影字段可见，不是扩协议。真要做，得先量帧大小再设计分页。
2. 按钮就叫「原始 JSON」，不加限定词
   - 最强的理由：短，且与桌面"看 JSON"的用词一致。
   - 为何被否：这正是最容易误导的写法 —— 见 Problem。多七个字换来"不会被当成抓包证据"，值得。
3. 做成可折叠的 JSON 树（带类型着色、可展开对象）
   - 最强的理由：字段多时更好读。
   - 为何被否：这一屏是核对而不是浏览，`SelectableText` + 等宽 + 缩进已经够；树要自己维护展开状态、缩进与着色，收益远小于成本。

## Consequences

- 收益：核对投影字段有了入口；误解被标题与正文第一句挡住。
- 代价：这份 JSON 是**我们这边的形状**（连接器 fold 出来的投影），不是线上形状 —— 排线上问题时它只能证明"投影出了什么"，不能证明"电脑侧发了什么"。
- 代价：字段表要与 `TrajectoryStep` 手工同步（Flutter 没有反射）。加字段时这里不会自动跟上，靠 review 与测试兜；测试只钉现有字段，新增字段漏了不会被发现。
