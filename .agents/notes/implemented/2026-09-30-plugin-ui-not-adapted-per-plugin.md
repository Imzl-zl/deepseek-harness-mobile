# 插件界面不做逐插件适配,只做管理面 + volatile 通用表单

- 状态:已落地(结论已写入 `docs/design-and-tech-plan.md` §12、`docs/plugin-and-jobs-notes.md` §C)
- 日期:2026-09-30

## 背景与约束

手机端要控制电脑上的 DSH,插件是绕不开的一块:用户会装插件,自然期望在手机上也能配置甚至操作它们。最初的设想有两条:①给每个插件做一个手机页面;②推动插件作者"自己维护一套移动端界面"。

需要先回答的事实问题是:**插件的界面在手机上到底能不能渲染?**

## 候选方案

1. **逐插件手写手机页面** —— 我们为每个插件写一套原生/Flutter 界面。
2. **插件作者自维护移动端界面** —— 定义一个移动端协议,由插件作者各自实现。
3. **只做管理面 + 通用配置表单** —— 手机只做"清单/状态/启停/安装卸载/日志",配置部分只对**声明过的字段**渲染通用表单,插件自定义界面一律"在电脑端打开"。
4. **内嵌 WebView 直接跑 DSH Web 客户端插件页** —— 把插件 `client.js` 在手机 WebView 里跑起来。

## 决定与理由

选 **3**;同时把 **4** 记为未来可选,但**不作为第一版**。

理由基于查实的三条事实:

- **插件页 = 注册进 slot 的 React 组件**,slot 收到的是 `view: 'summary' | 'page'` 加 `state`/`mutate` **活对象**,**没有任何可序列化的页面描述**(没有 JSON 页面结构、没有布局 DSL)。因此方案 1 与 2 都缺少可渲染的输入:方案 1 无据可依(每个插件的界面逻辑只在它自己的 React 代码里),方案 2 需要先发明一套描述协议 —— 那是重做一个 DSH,不是适配。
- **官方插件自己就是"一插件一个手写页面"**,这是缺少通用渲染器的直接证据,不是我们能靠工程量追平的差距。
- **配置 schema(Schemastery)确实会过线**,且带 `required` / `description` / `disabled` / `collapse` / `badges` 等 UI 元数据 —— 这条窄路是真实可用的,所以方案 3 的通用表单部分**能做**,不是妥协性的空话。

方案 4 被推迟而不是否决:它等价于在手机上跑 DSH Web 客户端,是"换运行时",与 Flutter 自绘三端一致的既定路线冲突(`docs/design-and-tech-plan.md` §3),但在少数重插件上可能是唯一出路,留作后续选项。

## 代价

- **覆盖面换可用性**:只有声明了 `.volatile()` 的字段会出现在线上 `describe()` 结果里,**多数插件的多数配置手机上看不到也改不了**,只能显示"需在电脑上编辑"。这是 DSH 侧的既定设计,不是我们的实现缺陷,必须在 UI 上如实说明而不是显示空表单。
- **手机端需要自建 Schemastery 渲染器**:现成积木只有一个不带 schema 的受控输入组件,渲染器要自己写,且要跟 Schemastery 的序列化格式演进。
- **"在电脑端打开"成为常用路径**:它打开的是电脑上的原生编辑器,手机只能当遥控器 —— 用户体验上会有"这里要切到电脑"的断点。
- **把选择权交给插件作者**:字段声明 `.volatile()` + 写 `description` 就会自动进手机表单。这意味着"能不能在手机上配"从一个产品决定变成一个**插件作者的实现选择**,我们无法单方面保证覆盖率。

## 影响

- 第一版插件相关只做:只读清单 + 状态、bundle 列表、行级(组件级)开关、安装日志/阶段流、安装卸载(两段确认)。
- **安装脚本批准**(会执行任意包脚本)必须保留显式确认,是插件安装里唯一能执行代码的权限,不因"手机上少一步"而省略。
- 不做"重试"式的一键安装,不做静默批准构建脚本,不在 `pluginManager` 里找配置读写(配置只在 `settings.*`)。
- 后续若要提升覆盖率,方向是**向 DSH 上游提"移动端可见的声明"扩展**,而不是在客户端堆特例。
