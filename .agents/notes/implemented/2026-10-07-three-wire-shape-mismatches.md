# 三处"两侧对线上形状的理解不一致"——都不报错，只在真机上表现为"连上了但什么都干不了"

- Status: implemented
- Date: 2026-10-07

## Context

修完 AEAD 算法（另见 `2026-10-07-electron-lacks-chacha20.md`）之后，真机仍然**能连上、
但会话列表永远是空的**，而且：

- 手机侧**不报错**：空态显示"还没有会话 / 在电脑上用 DSH 开一个"——那句话把用户指向电脑，
  而真正的问题在链路上；
- 电脑侧**也不报错**：连接器确实收到了 `session.list`，也确实回了 `ok:true` 与满当当的列表；
- 两端各自的单测全绿（`app` 313 项、`connector` 292 项、`relay` 65 项）。

一句话：**每一个局部都"对"，合起来不通**。真因是三处**独立的**线上形状分歧，
它们的共同点是 —— **不一致时不抛错，只是静默地什么都不发生**。

## 三处根因

### 一、`session.list` 的返回形状：电脑侧给对象，手机侧只认数组

- 电脑侧（`connector/src/handlers.ts` 的 `session.list`）返回 `{ sessions: [...] }`，
  且 `connector/tests/connection-methods.test.ts` 有多处按 `result.sessions[…]` 断言 ——
  **它是权威**；
- 手机侧 `AppModel._parseSessionList` 原文是 `if (result is! List) return const []`，
  于是**每一条都被静默跳过**：列表恒为空，且不是错误。

两边的假客户端也跟着"各认各的"：`app/test/widget_test.dart` 的 `FakeClient` 回**裸数组**，
所以这条分歧在单测里永远撞不上 —— 假数据把真问题挡住了。

### 二、手机的 `ping` 没有 `fc`：对端在解箱那一步就把它判成坏帧

`ping` 是要**封箱**的（契约 §3：控制帧的载荷是空串，封箱买到的是认证），
而 `fc` 是 nonce 的唯一来源。手机侧原先直接走"裸写"那条路（`_write`），
绕开了 `fc` 的分配点，于是发出的 `ping` 没有 `fc`：

```text
[connector] ping 帧没有 fc,不该封箱   ← 对端拒收 → 关连接 → 每 15 秒一轮重连
```

**这一条的成因值得记**：它是"出帧有两条路"造成的 —— 一条分配 `fc` 并封箱（业务帧），
一条不分配（握手/配对帧）。`ping` 属于前者，却被写进了后者。

### 三、`ping` / `credit` 没有身份标记：电脑侧回的那一半在中转被丢弃

`pong` 与 `credit` 都是**没有 `sid`** 的帧，而中转的连接器分支对"没有 `sid`"的帧
**只按 `id` 回查**（那是给 `pair-ack` / `hello-ack` / `confirm` 用的）：

```text
中转丢弃一帧：ping 找不到对应设备 { requestId: '' }
中转丢弃一帧：credit 找不到对应设备 { requestId: '' }
```

契约 §2.2 早就写明了机制（"回帧回显请求的 `id`"），`hello-ack` / `pair-ack` 都照做了，
**但 `pong` 没有**；`credit` 更是连"请求方"都没有（它是纯推送的累计确认，没有可回显的 `id`）。

## Decision

1. **`session.list` 的形状以电脑侧为准**：手机侧解析器改成认 `{ sessions: [...] }`
   （裸数组也兼容，那是早期假客户端的形状）。两侧只有一个真值。
2. **`ping` / `pong` 都带 `id`**，并写进契约 §3 的帧类型表与 §2.2 的回显规则。
   `pong` 回显 `ping` 的 `id`。
3. **手机的 `ping` 改走 `_sendFrame`**（分配 `fc` + 封箱），不再走裸写。
4. **`credit` 的对称缺口留作未决**，理由见下。

## Alternatives considered

### 一 的替代：让电脑侧改回裸数组

**最强的理由**：手机端只改一行（甚至不用改），而且"返回一个列表"比"包一层对象"更直观。

**为何被否**：**电脑侧已经是对的、而且被 9 处测试钉住**；改它等于让 9 处断言跟着改，
还会破坏"返回体是自描述对象、将来加字段不破坏兼容"这个既有约定。
更关键的是：这不是"哪边更方便"，而是**必须挑一个真值**——挑被测试覆盖更多、
且已经在跑的那一侧。

### 三 的替代：给 `credit` 也编一个"请求 id"来配对

**最强的理由**：形状上立刻对称，中转那一个分支不用动。

**为何被否**：`credit` 不是应答，它没有请求方 —— 编一个 id 是**为了迁就中转而伪造协议语义**。
而且这解决不了真问题：中转要判断的是"这条连接器 socket 上回来的 `credit` 属于哪台设备"，
而**一条连接器 socket 同时服务多台设备**（`connector/src/index.ts` 只向中转拨**一条**连接）。
给 `credit` 加 id 只是把"不知道属于谁"推迟到"id 是谁生成的"。

**真正要定的是拓扑问题**：连接器与中转之间是"一台设备一条连接"还是"一条连接多台设备"？
现有证据不足以定案 —— 回环测试（`verify-loopback.mjs`）的模型是"一台手机 + 一个连接器"，
而实现里是一对多。**先定拓扑，再动代码**；在没定论前按猜测补一个路由分支，
正是这套代码里已经出现过两次的那类错误。

## Consequences

- **收益**：会话列表在真机上**第一次真的出来了**（空态从"还没有会话"变成"选一个会话"）；
  连接不再每 15 秒因坏帧重连。
- **收益**：补上了三个**跨层**回归判据（`app/test/session_list_wiring_test.dart` 等），
  并把假客户端改成**照电脑侧的真实形状**回数据 —— 假数据形状不对会把真问题挡住。
- **代价**：契约 §3 的帧类型表与 §2.2 多加了两处 `id`；`codec.test.ts` 里那条逐字节断言
  跟着改了一次（这正是"线上形状进测试"该有的代价）。
- **未决（如实记录）**：**电脑侧主动发起的、不属于任何"请求-应答"配对的帧，在中转侧没有去处。**
  真机日志里能看到两类（`requestId` 已被回显，说明帧本身是对的，只是没人认领）：

  ```text
  [relay:debug] 中转丢弃一帧：credit 找不到对应设备 { requestId: '' }
  [relay:debug] 中转丢弃一帧：ping  找不到对应设备 { requestId: 'rzIL2I82mqbfjtXUBxvqmA' }
  ```

  根因是同一个：中转的连接器分支对"没有 `sid`"的帧**只按 `id` 回查** `noSidByRequestId`，
  而那张表只在**设备发来的**帧上登记。于是：
  - **`credit`**：纯推送的累计确认，本来就没有请求方 ⇒ 被丢。后果是**单向流控** ——
    电脑侧的窗口由手机的 `credit` 正常关闭（那个方向是通的），而**手机的窗口不会被关闭**，
    累积到 128 帧后手机会暂停发送（§4.3）。手机发的帧很少，短会话里看不出来。
  - **连接器自己的保活 `ping`**：它是**主动探针**、不是谁的回执 ⇒ 被丢 ⇒
    **电脑侧的探针永远到不了手机** ⇒ 电脑侧数不到回应，到点判半开并关连接。
    真机表现为每 30–45 秒一轮的重连。
    **注意这跟手机侧的 `ping` 是两回事**：手机发的 `ping` 走设备分支、按绑定路由，那条是通的
    （手机侧的 `ping` 缺 `fc` 是另一个 bug，已修，见根因二）。

  **为什么不当场修**：要修先得回答一个**拓扑问题** —— 一条连接器 socket 同时服务多台设备时
  （`connector/src/index.ts` 只向中转拨**一条**连接），这个没有设备标记的保活帧该送给谁？
  现有证据不足以定案：回环测试（`verify-loopback.mjs`）的模型是"一台手机 + 一个连接器"，
  而实现是一对多。**先定拓扑，再动代码** —— 在没定论前按猜测补一个路由分支，
  正是这套代码里已经出现过两次的那类错误（先猜拓扑、再让真机来纠正）。

  三个候选方向（**都还没验证**，列出来是为了让下一个会话不必重走一遍）：
  1. **连接器为每台在线设备各发一个探针**（探针带设备 id）—— 名册在连接器那儿，它知道有哪些设备；
     代价是"连接层保活"要依赖"设备名册"，层次上不干净。
  2. **中转自己承担保活**（它本来就看得见两端）—— 那 `ping` / `pong` 就不该穿到对端。
  3. **承认保活是"每条设备连接"的事，让连接器与中转之间一设备一条连接** ——
     拓扑改动最大，但语义最直。

## 第四、五处根因（真机"发一句什么也没有"）

修完上面三处之后，会话列表终于出来了，但**发消息仍然没反应**。继续挖，又找到两处：

### 四、`requestId` 被编码函数整个丢掉

`sync_client_impl.dart` 的 `encodeRequestEnvelope` **签名里压根没有 `requestId` 参数**，
而它上方的注释却写着"`method` / `params` / `requestId` 顶层" —— **注释说了、代码没做**。
带幂等键的方法（`session.prompt` 等）少了它会被电脑侧直接拒：
`session.prompt 必须带 requestId（幂等键）`。

顺带发现 `outbox.dart` 里**另有一份** `encodeRequest`（它是对的），但**没有任何调用点** ——
两处编码、一份真值，而真正在用的那一份是错的。

### 五、**一条连接器 socket 服务多台设备，与"握手是每连接一次"直接冲突**（架构级，未修）

这是本轮挖到的**最深的一处**，而它的症状是"时好时坏"，极具误导性：

- **连接器刚启动后的第一次连接 → 握手正常**；
- **之后每一次手机重连 → 手机发 `hello`，连接器不回 `hello-ack`** ⇒ 手机 10 秒超时、
  关连接、重连、再超时（无限循环）。

铁证（连接器自己打的）：

```text
[connector] 握手期收帧 t=hello session=有        ← 第一次：正常
[connector] 忽略握手帧 t=hello（handshakeDone=true）  ← 重连：被当成"重放"丢掉
[connector] 忽略握手帧 t=hello（handshakeDone=true）
```

**为什么**：连接器向中转拨的是**一条** socket（`index.ts` 的 `makeConnection` 只调一次），
而这条 socket 上 `handshakeDone` 与 `session` 是**连接级**状态。手机断线重连是**新 socket、
新握手**，但连接器那条 socket 还停在 `handshakeDone=true` ⇒ 新的 `hello` 走进
`if (isHandshakeFrame(frame)) { 忽略 }` 那条分支。

而契约 `connector-and-relay.md:129-130` 写的是"一次挂载可以有**多条连接**
（直连拓扑下每条手机 socket 一条）" —— 那是**直连**拓扑。**经中转时是一条多路复用**，
两种拓扑下"连接的粒度"根本不是一回事，而实现只按直连那条写的。

**未修的理由**：这不是能顺手补的一行，而是要先定**拓扑**：
经中转时，连接器与中转之间是保持一条多路复用、还是**每台设备一条**？
两种选择牵动帧路由、`fc`/nonce 的作用域、以及中转的 `noSidByRequestId` 表。
在没定论前按猜测改，正是这套代码里已经反复出现过的那类错误（先猜、再让真机纠正）。

**拓扑已于同批定案**（`connector-and-relay.md` §1.6）：**每台在线设备一条数据连接**，
控制面另有一条。据此可删掉 `noSidByRequestId` 那张表 —— 它存在的唯一理由就是多路复用下
"没别的东西能说明这一帧属于谁"。实现见 `docs/prompts/per-device-data-connection-prompt.md`。

## 一处教训(值得单独记)

**"静默的局部正确"是最难查的一类故障**：三处分歧没有一处抛错 ——
第一处让列表"看起来像电脑上没有会话"，第二处表现为"连接莫名重连"，
第三处只在日志深处留一行 `丢弃一帧`。而**所有单测都绿**，因为每处分歧都发生在两层之间，
而单测只在一个层里跑。

所以这轮之后**特意补的是跨层判据**（把 `AppModel` 与 `SyncClient` 接起来跑），
并把"空列表 + 有错"与"空列表 + 真没有"在界面上**分开显示** ——
少了这一支，下一次同类故障还是要靠猜。
