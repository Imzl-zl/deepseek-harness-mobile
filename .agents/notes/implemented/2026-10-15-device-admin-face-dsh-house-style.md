# Agent Note: 设备管理面照 DSH 插件页范式重做 —— 停用可逆、删除可挑、确认必带后果

Status: implemented

> 后续：本篇的「显式点名可以删在线的」那条已被
> `implemented/2026-10-30-revoke-then-purge.md` 取代（撤销与清理分开：删除只对
> 已停用的行开放）。其余结论（解禁可逆、确认必带后果、按状态批量绝不动在线的）
> 仍然成立。

## Problem

管理面(渲染在 DSH「插件」页本组合包详情面板的 `connector/client.js`)改造前:

- **停用是单向的**:只有「吊销」(软),没有解禁 —— 一台设备被停用后,复活它的唯一途径是
  那台手机重新扫码换一个新身份(于是电脑侧多一行记录)。
- **删除只能一台一台**;按状态一键清有三类(离线 / 已吊销 / 全部)。
- **2026-10-15 事故**:按"当前离线"批量**硬删**把用户自己那台删了 —— 他当时正在排查
  "断开后一直重连",正是离线态,而这个 scope 的人口专门命中这种状态;服务端"跳过在线"
  保护不了它。确认文案还写「真删除 {n} 条**已吊销**记录？」(实际删的是离线记录),
  且**不说后果**;破坏性操作走 `window.confirm`,而 `chrome-devtools` 的
  `evaluate_script` 有默认 accept 的 `dialogAction`,脚本一次点击就穿窗而过。
  复盘见 `docs/postmortem/2026-10-15-offline-batch-hard-delete-nuked-own-phone.md`。
- **三个写操作内联在 `index.ts` 的 `start-transport` 闭包里**:"解禁到底有没有把
  `revokedAt` 拿掉""在线的到底有没有被跳过"只能靠读代码确认,没有任何单测能钉。
- `revokeAllOffline` 端点在 UI 里**没有任何调用者**(死代码);`client.js` 此前**零自动化
  覆盖** —— 而事故的确认文案正长在它里面,且它有一个 `node --check` 查不出的 TDZ bug
  (`S` 字面量里向前引用 `S.value`),会让**整个 slot 条目变白**。

## Decision

**端点与交互照 DSH 插件管理器的 house style**(`packages/client/ui-plugin-manager` +
`packages/boot/plugin-manager`),不自己发明:

1. **停用/启用是一对布尔端点**,不是两个动作:照 `setBundleEnabled(name, enabled)`
   (`boot/plugin-manager/src/index.ts:476`)。`POST /api/dsh-mobile/devices/enabled`
   收 `{devId, enabled}`;停用写 `revokedAt`,解禁把**键从行上拿掉**(解构剔除,
   不写 `undefined` —— 域表 `put` 不过 zod,写 `undefined` 会留一个悬空键)。
2. **删除**:`POST /devices/remove` 收 `{devIds: string[]}`(单台就是长度 1 的数组)或
   `{scope: 'revoked' | 'all'}`;未知 id 一律 400 + `未知设备：<id>`(与 `enabled` 一致,
   404 是异类)。
3. **删掉 `offline` scope**。它的人口命中"暂时离线但还在用"的设备,而"跳过在线"保护不了
   它 —— 事故的直接机制。要删具体的几台用多选。
4. **在线豁免按形状生效**(`device-admin.ts` 全文最重要的一条):按状态批量**绝不碰在线的**;
   显式点名的 id **可以删在线的**。改之前单台删除一直允许删在线的,**悄悄收回一项既有能力
   比危险更糟**;且手机丢了还在线时要能立刻弄死它,为此先"让那台手机断开连接"是荒谬的。
5. **抽出 `connector/src/admin/device-admin.ts`**:三个写操作 + `purge()` 唯一实现,
   不碰 cordis,于是一条内存设备表就能把三条不变量逐条钉住。
6. **浏览器半侧**:每行 停用/启用 + 删除;行首 checkbox + 顶部浮现操作栏;
   **启用不弹确认**(可逆,照 DSH 只有 `uninstall` 走 `pendingConfirm`);硬删走**页面内
   DOM 对话框**(照 `confirmUninstall`:标题问句 + 一句后果 + 确认键),**不用
   `window.confirm`**;失败必须带原因(`停用失败：{reason}`);遮罩用**面板内绝对定位**而不用
   `fixed` —— 本面板渲染在 DSH「插件」页详情页里,那一页有滑入过渡、很可能带 `transform`,
   `fixed` 在带 transform 的祖先里会改成相对该祖先定位。
7. **词汇**:界面说「停用 / 启用 / 删除」,状态词「运行中 / 未运行 / 已停用」(照 DSH
   `locales.ts`);**底层字段与协议仍叫 `revokedAt` / `revoked`,一个都没改名**(形状透传)。
8. `client.js` 从零覆盖变成 **13 条自动化**(最小 React 桩真跑面板:locale 键集合、按钮、
   浮现栏、逐字对话框文案、失败原因),并加一条看门狗:"按当前离线批量硬删不许回来"。

## Alternatives considered

1. **保留 `offline` scope,只在确认文案里写清后果**
   - 最强的理由:少删一个按钮;"清掉当前离线"对纯清理场景确实方便,用户少一个选择。
   - 为何被否:它的人口专门命中"暂时离线但还在用"的设备 —— 用户排查重连时他的手机正是
     离线态,事故就是这么发生的,而"跳过在线"保护不了它。**后果文案救不了一个人口定义
     错误的批量操作。**
2. **停用与解禁做成两个端点**
   - 最强的理由:两个动作两个名字,直白。
   - 为何被否:它们本来是同一件的两个值;DSH 的 `setBundleEnabled` 就是一个布尔。
     两个端点会让"停用"与"解禁"看起来像两件不相干的事。
3. **多选改成"编辑模式"切换**
   - 最强的理由:编辑态能顺带做重命名 / 批量停用,扩展性好。
   - 为何被否:多选是**临时动作**(挑完就删、删完就散);模式切换改变整个列表的交互语义 ——
     进编辑态后每行首当其冲的是勾选框而不是名称,行级按钮语义也要收起,用户为了删两台
     要先切换再切回。浮现栏只在有勾选时出现,**不改变行本身**。
4. **保留 `window.confirm`,不自己画面板内对话框**
   - 最强的理由:零成本;原生对话框的无障碍支持最好。
   - 为何被否:`chrome-devtools` 的 `evaluate_script` 有默认 accept 的 `dialogAction`,
     脚本一次点击就穿窗而过 —— 事故的直接机制;且原生对话框呈现不了 DSH 的 token 与
     逐动作后果文案。

## Consequences

- 收益:停用可逆;删除可挑;确认逐字对行为且必带后果;三条不变量有单测;死代码清掉;
  `client.js` 有自动化覆盖,并当场抓出一个 TDZ 真 bug。
- 代价:
  - **多选是对 DSH 范式的有意偏离**(插件管理器逐行 + 逐个确认、无多选),已按项目规则
    写进 `docs/design-and-tech-plan.md`。
  - 面板内遮罩只盖面板、不盖全页(换来的是不会被页面 transform 带跑)。
  - 端点形状变了(旧 `{devId}` body 删除;全仓无其他调用方)。
  - **在线设备可以被显式删除**,误点自己那台的后果仍在 —— 缓解是确认句必带
    "这台在线,正在使用" + 删除实心红、停用描边红的视觉分级。
