# Agent Note: 幂等只记成功，崩溃窗口里重放执行而不是 fail-closed

Status: implemented

## Problem

幂等的两块料早就到位：`protocol/dedupe.ts` 给了表的语义（`claim` 只接纳一次）、
`store/` 的 `dedupe` 表给了持久化（`{ at, status, resultRef? }`，容量 10000、TTL 24h）。
但**没有任何东西调用它们** —— 带幂等键的请求重发就会被原样执行两次，
而那正是不变量 I8 要防的"第二条消息 / 第二次授权"。

接它的时候有三个问题必须先答，且三处都不能"顺手写"：

1. **失败的应答要不要记？** 记了，重发永远得到同一个答案（包括失败）；不记，
   一次瞬时故障之后重发还有机会成功。
2. **桥接崩在"执行到一半"怎么办？** 表里没有成功记录，重发会再执行一次 ——
   是接受它，还是 fail-closed 让手机先去刷新状态？
3. **同一个键的两次请求同时在飞怎么办？** 拒绝（成熟做法给 409），还是合流？

## Decision

- **只记成功**（`ok:true`）。失败不进表，也不留 `pending` 行。
- **崩溃窗口里重新执行**：见下面的论证，带键的每个方法都有下游保障。
- **同键并发合流**：两个调用接到同一个 promise 上，只执行一次，两边拿到同一个应答。
- 只对 `IDEMPOTENT_METHODS` 里的方法生效；只读方法即使带了键也不进表（拿旧数据回答第二次读是糊弄人）。
- 表本身没有定时器，收敛点取"挂载"与"超容量"两处；**TTL 是惰性执行的语义**（读到一个过期条目就当未命中并清掉），
  清扫只是回收空间，而且**单次有界**（`DEDUPE_SWEEP_LIMIT = 500`）。

准入门槛（可机械判定）：

1. 同键第二次调用**不执行**（断言执行次数，而不是断言返回值相等 —— 执行两次也可能返回一样的值）。
2. 失败不进表：第二次仍会真的执行；且 `rows.size === 0`。
3. 执行抛异常时飞行表必须收干净（否则这个键会永远合流到一个失败的 promise）。
4. 写表失败**不影响应答**（操作已经生效），但必须留声。
5. 坏行当未命中处理并清掉；坏行里的未知错误码归一成 `internal`（§3.1 的表是封闭的）。
6. **过期条目一律按未命中处理**，且单次清扫不超过 `DEDUPE_SWEEP_LIMIT` 条
   —— 后者是介质逼出来的：域表写入走**单写链**，一次清一万条就是一万次串行落盘，挂载会卡住几十秒。
   所以"正确性靠惰性过期、空间回收靠有界清扫"，两者不能互相替代。

## Alternatives considered

1. 失败也记（Stripe 的 idempotency key 就是这么做的）
   - 最强的理由：语义统一 —— 同一个键永远得到同一个应答，"重发"这件事不需要调用方分情况思考；
     而且它顺手解决了"写已经生效但应答丢了"这一种形状。
   - 为何被否：风险与收益在这里不对称。缓存一次**瞬时**失败，等于把一个"再试一次就好"的故障
     变成 24 小时的确定性死路；而重复执行的代价，我们为每个带键方法逐个核过下游保障：
     `session.prompt` 由 DSH 自己按 `requestId` 去重（`dsh/sessions.ts` 的注释、`types.ts:333-335`）、
     `settings.update` / `credentials.set|unset` 写同一个值天然幂等、
     `interaction.respond` 再答一次会被 DSH 以 `interaction/not-pending` 拒掉。
     **必须如实说清前提**：这套论证依赖"带键方法就这四个"，将来新增带键方法时要重新核一遍下游。
2. 崩溃窗口 fail-closed（写 `pending` 行；重发时若见 `pending` 而本进程没有在飞，就回错误让手机刷新状态）
   - 最强的理由：绝不重复生效，是这里最保守的一档；表结构里 `pending` 这一档本来就是为它准备的。
   - 为何被否：它把"桥接崩过一次"变成用户可见的失败，而下游本来就能安全重放（见第 1 条）；
     另外每次请求多一次落盘，且 `pending` 行要靠 TTL 清 —— 一个只在崩溃后才可能被读到的行，
     平时纯粹是写放大。表结构保留 `pending` 这一档：真要改 fail-closed 时它才需要被写。
3. 同键并发回一个"正在处理中"的错误（Stripe 的 409 形状）
   - 最强的理由：实现最简单 —— 见到在飞就拒，不必维护合流表。
   - 为何被否：Stripe 这么做是因为它的键跨机器、单点无法知道对端状态；而这里的执行**就在本进程里**，
     合流能给出确定答复。让手机去判断"要不要重试"是把电脑侧的内部状态泄漏成协议负担，
     而手机侧的判据本来就只有"有没有收到应答"。
4. 表里只存结果的**引用**（`resultRef` 这个字段名暗示的做法）
   - 最强的理由：表保持很小，大结果不进 KV。
   - 为何被否：带键的四个方法结果都极小（`{accepted:true}` / ack / `{}`），
     为它们再造一层对象存储不划算。**这条依赖"只有小结果的方法带键"**，将来若有大结果方法要带键，
     得把这条重新评估 —— 所以写在笔记里而不是埋在代码里。
5. 把幂等做进每个 handler
   - 最强的理由：就近、n 个方法各管各的，不必在方法面加一层。
   - 为何被否：四处重复同一段逻辑，漏一处的症状是"那一个方法可以被重放两次"——
     正是最难发现、后果最实在的一类 bug。放在方法面只有一处，且能被一组单测覆盖。
## Consequences

- 收益：I8 的最后一段有了可执行判据（单测断言执行次数、e2e 断言真实重发只生效一次）；
  "哪些方法吃幂等"由 `IDEMPOTENT_METHODS` 一处决定；过期语义与空间回收分开（前者惰性、后者有界），
  挂载不会被一万条删除卡住。
- 代价：每个成功的带键请求多一次落盘；方法面多一层分支；`resultRef` 里存的是整个应答 JSON
  （当前都极小，前提同上）；空间回收是"每次有界、需要就再来一次"，极端情况下会多跑几轮。
- **仍然没被真实方法用到**：`session.prompt` / `settings.update` / `credentials.set` /
  `interaction.respond` 这**四个带键方法都还没实现**（handler 表里目前只有 `repo.info` 与
  `devices.list`，两个都不带键）。所以本轮交付的是"管道 + 判据"，e2e 用的是假 handler。
  这一点在 `memory.md` 里如实写着，不许读成"发消息已经幂等了"。
