# Agent Note: 没有 `sid` 的帧一律按绑定路由 —— 否则设备的第一帧 `hello` 会被丢掉

Status: implemented（`relay/src/core.ts` 的规则收敛 + `relay/tests/core-nosid.test.ts`）

## Problem

第 45 轮打通了"设备经中转抵达连接器"之后，下一步是让**握手**也走中继。
而推理一步就能发现一个缺口：**握手三帧没有 `sid`**（`{v,t:'hello', id, box}`），
而中转的 `sid → 连接器` 归属表是**按会话**学的 —— 设备的第一帧 `hello` 在会话存在之前发出，
归属表帮不上它。原实现只特判了 `pair` 一种帧，于是 `hello` 会走 `routing.fromDevice` →
`undefined` → **丢弃**。

症状会很隐蔽：配对成功、连接也在，但**永远握不上手**，而中转日志只说"这个 sid 还没有归属"
（`sid` 是空串）。这与"配对没做"的表现完全不同，却同样指向错误的方向。

## Decision

把规则从"特判 `pair`"**收敛成一条判据**：**`sid` 为空就按 ticket 绑定路由；有 `sid` 才查归属表。**

- **设备侧**：`sid === ''` → 投给它 ticket 绑定的连接器；同时记住 `id → 设备`（不管它是
  `pair` 还是 `hello`）。没有绑定时丢弃并计数（不投给"随便谁"）。
- **电脑侧**：`sid === ''` → 靠 `id` 回到发起方。原来只认 `pair-ack`，现在同样适用于
  `hello-ack` / `confirm` —— 它们都是"没有 `sid` 的回帧"。
- 变量名从 `pairingByRequestId` 改成 **`noSidByRequestId`**：名字里带着"只用于配对"的话，
  下一个人读到 `hello-ack` 走这条路时会以为它是巧合。

这条判据与 I10 的关系也顺了：`id` 之所以在中转的可见字段里，正是因为**没有 `sid` 的帧要靠它回程**
（第 28 轮把 `id` 加进 I10 时给的理由就是这个，本轮只是把适用面从配对扩到全部无 `sid` 帧）。

准入门槛（可机械判定）：3 条新用例 ——
`hello` 按绑定投给连接器 + `hello-ack` 靠 `id` 回到设备；没有绑定时 `hello`/`pair` 都被丢弃且计数；
设备断开后那条 `id` 关联不再指向任何东西。

## Alternatives considered

1. 继续逐个特判（`pair`、`hello`、`hello-ack`、`confirm`…）
   - 最强的理由：改动最小，语义最"显式"。
   - 为何被否：那是把**同一条规则**按帧类型抄四遍，而漏掉任何一个的症状都是"某一帧静默丢失"。
     判据本身只有一句（"没有 `sid` 就没有会话可查"），值得只写一次。
2. 让设备在换票时就把 `sid` 报给中转（给握手帧也编一个 `sid`）
   - 最强的理由：那样归属表能覆盖所有帧，规则只有一条（查表）。
   - 为何被否：握手发生在**任何会话被打开之前**（设备刚扫码，还不知道要聊哪个会话）——
     没有 `sid` 可报。硬编一个（例如用设备 id 当 `sid`）等于伪造会话别名，
     而重放窗口、限流、审计全都按 `sid` 分组（第 28 轮否掉"给 `pair-ack` 伪造 `sid`"时同一个理由）。
3. 让设备侧无 `sid` 帧广播给所有连接器
   - 最强的理由：不必维护绑定，实现最短。
   - 为何被否：多连接器时等于把一台设备的握手材料发给所有人 —— 那是把授权边界交给"谁会收到"，
     而不是交给"谁被绑定"。

## Consequences

- 收益：**握手可以走中继了**（设备的第一帧不再被丢）；判据从"按帧类型特判"变成"按有没有 `sid`"，
  未来新增的无 `sid` 帧（保活等）自动落在正确的路上。
- 代价：`id` 关联表现在承担两种用途（配对 + 握手），所以它的清理点必须覆盖两种终止
  （设备断开已覆盖 ✓）。
- **仍未做**：把这条规则用进三方 e2e —— 带票升级的设备替身跑**握手**与 **`session.prompt` 往返**。
