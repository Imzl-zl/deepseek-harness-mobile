# Agent Note: 方法面只做接线 —— `req` → 分发 → `res`，`fc` 与封箱一概不碰

Status: implemented

## Problem

方法面的骨架（`protocol/methods.ts`：22 个方法名的封闭集、幂等键强制、分发器从不抛）落地很久了，
但**没有任何东西消费 `req` 帧**：插件的收帧分支对除四类连接层帧之外的一切都只打一行
"尚未实现的方法面帧"告警。于是手机问一句会得到"发出去了没反应"，而电脑侧一片安静。

接它的时候有三处必须先定清楚，否则写出来一定是散的：

1. **关联**：`res` 必须回带请求的 `id`（还有 `sid`）。丢了它，手机永远等不到回应 ——
   而症状与"电脑没处理"完全一样。
2. **两个 `ok`**：`res` 帧头有 `ok`（§3 的联合），信封里也有 `ok`（`ResponseEnvelope`）。
   两处说法不一致时，手机按帧头分支、按信封显示，会出现"显示成功但内容是错误"。
3. **"我们会哪些方法"这个信号没有单一出处**。手机要据此置灰按钮（不用错误码试探），
   而任何手抄的清单都会在下一次加方法时忘掉同步。

## Decision

- **`src/method-face.ts` 只做接线**：解信封 → 交给分发器 → 把结果封成 `res`。它
  **从不抛**（所有失败都是 `ok:false` 的信封）、**从不分配 `fc`、从不封箱** ——
  那两件事的单一收口在连接层（`fc` 是 nonce 来源，必须与封箱挨着分配）。
  返回值收窄成 `ResFrame`：这一层在类型上就没有能力产出别的帧。
- **`ok` 只在 `resFrame()` 里被同时写一次**（帧头 + 信封同源），别处不许拼 `res`。
- **`src/handlers.ts` 是"我们实现了什么"的唯一出处**：`repo.info` 报的是**这张表的键**
  （`Object.keys(handlers)`），不是手抄清单；加一个 handler 就自动多一行。
- **能力位与已实现方法是两件事**：`caps` 说"服务在不在"（宿主决定），`methods` 说"我们接没接上"。
  手机置灰按钮靠后者。
- **本轮只接两个就地能答完的方法**：`repo.info`、`devices.list`。其余一律回
  `connector/unsupported`（分发器自带），需要新 DSH 服务或跨会话副作用的留到各自的轮次。

准入门槛（可机械判定）：

1. `res.id` 等于请求的 `id`；请求带 `sid` 才回带 `sid`（它是中继路由字段，凭空加会让路由错）。
2. 帧头 `ok` 与信封 `ok` 恒相等（同一个函数写出来的）。
3. 结构化错误（未知方法、漏幂等键、载荷不是 JSON、handler 抛错）**不关连接**：回 `ok:false`
   的信封，连接留在 `serving`（e2e 断言关闭列表为空）。
4. `repo.info` 的 `methods` 恒等于 handler 表的键集合。

## Alternatives considered

1. 把 `req` → `res` 直接写在 `index.ts` 的收帧分支里
   - 最强的理由：少一个文件、少一层间接，装配文件本来就是"把零件接起来"的地方。
   - 为何被否：关联与错误信封会散进装配代码，而装配代码**离不开 DSH 运行时**——
     于是"id 有没有回带"这类判据只能在真机上验，进不了单测。抽出来之后，
     方法面的九条单测全是纯函数，e2e 只负责证明它确实接在真 socket 上。
2. 把 `Connection.send` 直接交给方法面（而不是返回"待发帧"）
   - 最强的理由：少一次编排，handler 想出帧就出帧。
   - 为何被否：那会让方法面在"还没 `fc`、还没封箱"的层面上碰帧，而这两件事的单一收口在连接层；
     同时"应答发不出去"会变得不可观测 —— 现在它是一条显式的 `false` + 指标 + 日志。
3. 把重复的 `ok` 删掉一个（只留帧头，或只留信封）
   - 最强的理由：消除重复是这个仓库一贯的取向，两处写同一个事实迟早漂移。
   - 为何被否：两者都有存在理由 —— 帧头是明文（中继与手机可以不拆箱就分支、路由），
     信封在箱里（§3 明说错误也要封箱，错误码属于应用层）。正确做法不是删一个，
     而是让它们只有一处**写入点**（`resFrame`）。
4. `repo.info` 手写方法清单
   - 最强的理由：读代码的人一眼能看到全部能力，不必追到 handler 表。
   - 为何被否：它在"加一个 handler"时不会自己更新，而症状是"按钮能点但永远转圈"。
     变异校验（把清单写死成 `['repo.info']`）证明这条判据真的会红。
5. 本轮一次把 22 个方法都接上
   - 最强的理由：方法表是封闭集，一次接完就没有"半实现"的中间态。
   - 为何被否：其中大多数要新依赖（`sessionQuery` 才能列会话）或跨会话副作用（`devices.revoke`
     要写存储并踢掉在线会话）。一次接 22 个，"哪部分真的被验证过"就答不上来了 ——
     而本项目的取舍一贯是"先把闭环走通再铺开"。

## Consequences

- 收益：手机第一次能真的问一句、拿到一句（e2e：两侧各自实现容器/AAD/方向密钥，双向跑通）；
  "哪些方法实现了"有了单一出处，且它随代码自动更新；`id` 关联、`ok` 同源、结构化错误不断连
  三条判据各有一组断言；方法面九条单测不需要 DSH 运行时。
- 代价：多一层文件与一次编排（`handleFrame` 里 `void face.handle(...).then(...)`），
  以及一条异步边界 —— 收帧路径不能等 handler（同一条 socket 上还有 `credit` 与保活要走）。
- **尚未做的**（都如实写进 `memory.md`）：其余 20 个方法；**幂等表尚未接线**
  （`protocol/dedupe.ts` 与 `store/` 的 `dedupe` 表都已就绪，但 `session.prompt` 这类
  写操作还没有"命中即回上次结果"的路径）；`session.list` 需要新接 `sessionQuery` 服务；
  `devices.revoke` 需要写存储 + 清在线会话。`repo.info` 目前**不报插件的 semver**
  （从打包后的 `lib/` 读 `package.json` 会把构建形状带进运行时；协议版本才是兼容性判据，
  等手机真的要比较版本时再定）。
