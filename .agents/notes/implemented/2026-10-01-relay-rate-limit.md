# Agent Note: 中转移流 —— 令牌桶（还没有调用方，接线在下一轮）

Status: implemented（`relay/src/rate-limit.ts` + 5 条用例）· **HTTP 面已接线**（`server`/`main` 的配置装配仍未做）

## 接线进展（同日）

`http-face.ts` 已接：`HttpFaceOptions.rateLimit?: (key) => {allowed, retryAfterMs}`，
在**认证之后**调用，被拒回 **429** + `{error:'rate-limited', retryAfterMs}`。4 条用例钉住行为，
其中两条是安全/方向性的：**被限流时一张票都不发**（429 之后仍发出的票本身就是凭据，
而它会被记进客户端日志）、**桶键是身份而不是 IP**（用例断言键就是 `'dev-1'`），
以及"令牌不对时回 401 而非先被限流掩盖"（未认证的请求没有身份，桶键无处安放）。

**仍缺**：`server.ts` / `main.ts` 把容量与速率做成配置并建一个 limiter 传进去 ——
在此之前，**运行中的中继还没有限流**（这个模块在 HTTP 面有调用方，但产品装配还没接）。
WS 升级路径也还没用同一个 limiter。

## Problem

契约 §12 的滥用对策里写着"按设备限流与审计"，§3.1 的错误表里有 `rate-limited` ——
而中转**什么都没限**：一台设备可以无限刷 `/ws-ticket`（每个请求都会读凭据面、查登记表、写票），
也可以无限升级 WS。

## Decision

`createRateLimiter({capacity, refillPerSecond, now?, log?})` —— **令牌桶**，不是"每分钟最多 N 次"：

- 固定窗口在**边界**上允许 2N 次突发（这是它被绕过的经典方式）；令牌桶把"突发上限"与
  "长期平均速率"分成两个参数，各自有意义。
- **惰性补充**：没有定时器，每次取用时按 `(now - at) * refillPerSecond` 结算，
  **封顶在容量**（否则闲置越久攒出的突发越大 —— 那正是"歇一会儿再来"绕过限流的形状）。
- **被拒也写回结算**：不写回的话下次判断会重复补同一段时间，`retryAfterMs` 就会算错
  （用例专门钉了"距上次拒绝已过 600ms → 只剩 400ms"）。
- **按身份分桶**（`key` = 设备 id / 连接器 id），不是按 IP：中转在代理之后时 IP 会把所有人
  归成一个 —— 那是最糟的形态（一个人把大家限住）。用例钉了"一台设备被限住不影响别人"。
- **时钟注入**：真实时间会让测试变成"睡一会儿再看"（又慢又脆）；注入之后四条语义
  （突发/补充/封顶/重试时间）都能被精确断言。
- `sweep()`：完全补满的桶与"从没出现过"等价，可以清掉（否则空闲键永远占内存）。

准入门槛（可机械判定）：5 条用例全绿；`pnpm typecheck` 0 错；relay 48 → **53 条**。

## 接线设计（下一轮，已想清楚但**没有落进代码**）

这一轮**没有调用方** —— 我知道那是个坏味道（等于"写了一半的功能"），所以把接线设计写在这里，
而不是让它留在我的脑子里：

- `http-face.ts`：给 `HttpFaceOptions` 加可选的 `rateLimit?: (key) => {allowed, retryAfterMs}`，
  在**认证之后**调用（键一定是身份），被拒时回 **429** + `{error:'rate-limited', retryAfterMs}`
  （HTTP 上对应 `Retry-After`）。**所有端点一视同仁**（换票最容易被刷）。
- `server.ts` / `main.ts`：把容量与速率做成配置（`{rateLimit: {capacity, refillPerSecond}}`），
  装配时建一个 limiter 传进去；WS 升级路径也用同一个（升级比 HTTP 更贵）。
- **未认证的洪水不在这一层**：拿"错令牌"刷请求时我们还没有身份可用，桶键无处安放。
  那属于边缘/前置治理（反代限流、连接数上限），**如实记下**而不是在这里假装解决。

## Alternatives considered

1. 固定窗口（"每分钟 N 次"）
   - 最强的理由：实现最短，配置最直观。
   - 为何被否：窗口边界允许 2N 次突发 —— 而中继的滥用场景正是"卡着边界猛刷"。
2. 按 IP 限流
   - 最强的理由：未认证的请求也能限（那时还没有身份）。
   - 为何被否（**在这一层**）：中转在代理后时所有请求的 IP 相同 ⇒ 变成全局限流 ✗。
     按 IP 的正确位置是边缘（反代），那里能看到真实来源。
3. 用定时器周期补充令牌
   - 最强的理由：语义直观，`tokens` 永远是"现在有多少"。
   - 为何被否：每个键一个定时器（或一个全局 tick 扫全表）都是持续开销，
     而惰性补充在取用时算一次、O(1)、无后台任务；配 `sweep()` 就够。

## Consequences

- 收益：限流的**语义**已定且被测（突发/平均速率/封顶/重试时间/按身份）；接线时有明确落点。
- 代价：**还没有调用方**（下一轮接线）；多实例部署时"进程内一张表"会变成每个实例各限一份
  —— §12 的完整形态要求共享存储或边缘限流，这一条也如实记下，现在不引依赖。
- **仍未做**：上述接线；手机端 Dart 客户端；每连接状态那个岔口；真机联调。
