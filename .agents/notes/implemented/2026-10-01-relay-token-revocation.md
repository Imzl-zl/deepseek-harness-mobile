# Agent Note: 令牌吊销 —— 软吊销（行留着），重签即轮换

Status: implemented（`revokeTokenInConfig` + `--revoke-token` 入口 + 3 条用例）

## Problem

上一轮补齐了签发，吊销那一半还缺。而"吊销"有一处**必须按契约来**的选择：
§12 的中转表里那一列叫 **`revoked_at`** —— 也就是说它是**软吊销**（行留着、标时间），
不是"把行删掉"。

这条区别不是洁癖：删掉行会让"这个身份曾经存在、某时刻被吊销"这条事实消失，
而将来要把"你被吊销了"与"这个令牌没见过"分开告诉设备时（今天两者都是 401），
**能力留着比补回来便宜**。

## Decision

- `TokenDigest` / `TokenConfigEntry` 都加 `revokedAt?: number`；
  `createDigestAuthenticator` **跳过已吊销的条目**（它留在配置里是为了可辨识，不是为了还能用）。
  今天"已吊销"与"不存在"对客户端都是 401 —— 那是有意的（下一步动作相同）。
- `revokeTokenInConfig(configPath, {kind, id}, now)`：标 `revokedAt`，**保留原行**；
  **幂等**（已吊销过不刷新时刻）；**身份不存在返回 `revoked: false` 而不抛**
  （"什么都没改"是事实，不是错误 —— 但也别假装成功）。
- 入口加 `--revoke-token <device|connector> <id>`：吊销并打印结果；身份不存在时以码 2 退出
  （脚本里能据此判断"我吊销的这个到底在不在"）。

**签发与吊销合起来构成轮换**：同一 `(kind, id)` 重新签发会**替换**整条（新摘要、无 `revokedAt`），
所以"从吊销恢复"只有这一条路径，而且它是原子的（一次读-改-写）。

准入门槛（可机械判定）：3 条用例 ——
吊销后认证不通过 + 行还在 + 落盘；幂等与未知身份（不刷新时刻、如实回 `false`）；
重新签发清掉吊销、旧令牌失效、新令牌可用。

## Alternatives considered

1. 硬删除（把行从配置里去掉）
   - 最强的理由：更彻底（"不存在"就不会有任何残留），实现也更短。
   - 为何被否：契约那一列是 `revoked_at` —— 规格要的是软吊销；而且删掉会丢掉
     "曾经存在过、何时被吊销"这条审计事实，将来要告诉设备"你被吊销了"时无从判断。
2. 让已吊销的条目留在表里但认证时单独返回一个"已吊销"结果
   - 最强的理由：客户端能据此显示更准确的提示（"设备已被移除"而不是"认证失败"）。
   - 为何被否（**暂时**）：`http-face` / `server.ts` 今天把两种都当 401，而**这个能力现在没有消费者**
     （手机端还没写）。等真要分开时，改的是 `authenticate` 的返回类型 —— 数据已经在了
     （这正是软吊销留住的那点信息）。
3. 吊销时不校验身份是否存在（静默成功）
   - 最强的理由：脚本更省事（幂等）。
   - 为何被否：那会让"我拼错了设备 id"变成一次看起来成功的操作。改为回 `false` + 以码 2 退出：
     幂等仍成立（重复吊销同一条不报错 ✓），但**拼错**能被发现。

## Consequences

- 收益：§12.2 的两半（签发 / 吊销）齐了；轮换语义明确且被测；软吊销的形状与契约一致。
- 代价：配置里会留下已吊销的行（人工可清理）；与签发同样，写回是**读-改-写无锁**
  （低频人工操作，如实记下）。
- **仍未做**：手机端 Dart 客户端；每连接状态那个岔口（监听面/多设备）；
  真机联调（Tailscale / WSS 证书）与 cookbook 第 5 节实跑。
