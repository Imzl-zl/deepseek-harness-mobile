# Agent Note: 多地点端点保留 + 记住上次 + 同网段优先（端点是一等公民，续）

Status: implemented

## Problem

用户的真实场景：**同一台手机 + 同一台电脑，在家一个 WiFi、在公司一个 WiFi**，
两个网段的 IP 不同。他要把"换地点之后不用重新扫码"做出来，并顺手管理地址。

现状有两处会把这个场景打断，而它们各自都有"看起来合理"的来源：

1. **换地点会把另一个地点的地址删掉。**
   `AppModel.mergeDiscoveredEndpoints` 的剪枝是"连接器没报 + 本机拨过且失败 → 删"。
   在 A 地连上后 `endpoint.describe` 只报 B 地的地址，A 地那条拨过且失败 → 删。
   回 A 地就得再扫一次码。而这条规则本身是为了治另一个真问题（见备选 1）：
   连接器的 IPv6 隐私地址每次轮换都是新条目，旧的永远留着，冷启动每个等满超时
   —— 2026-10-17 实测三个死地址合计 30 秒，用户原话"退出软件怎么就连不上了"。
   两个诉求直接冲突，而当时的判据分不出"轮换垃圾"与"另一个地点"。

2. **用户排好的首选会被自动发现冲掉。**
   `mergeEndpoints` 对**新发现**的 `direct` 无条件插到第一个 `relay` 之前。
   于是"用户在设置页把中转设为首选"会在连接器报出一个新直连时被悄悄挤到第二位。
   该函数的 docstring 写着"用户一旦手动重排，后续合并只更新字段、不再挪位"——
   **代码没实现这句话**，只对"已知端点"成立。

另外发现一个**既有 bug**（不是这次引入的，但直接妨碍"发现立刻生效"）：
`main.dart` 把捕获的 `endpoints` 列表交给 `EndpointTransport`，而 `AppModel`
每次改动都**换一个新 list**。捕获的是旧引用 ⇒ 发现结果只有**重启 App** 才生效。
`tools.md` 那句"引导完重开 App 它就会改用直连"其实就是这个别名 bug 的症状，
当时被当成了设计意图。

## Decision

**一、剪枝判据换成"这条地址对这台手机还有没有意义"，而不是"上一次通没通"。**

- **手填的（`Endpoint.manual`）永不自动删** —— 那是用户的意图。
- **成功过的永不自动删** —— 它只是"此刻不在那个网络"。
  新增 `Set<String> succeededEndpointIds`：记的不是"上次成功"，是"曾经成功"。
- 只删"连接器不再报 + **从没**成功过 + 这次拨过并失败"——IPv6 轮换垃圾正是这一类。
- 再加一条**上限保险丝**（`maxEndpoints = 12`）：超了从**末尾**淘汰"从没成功过、
  且不是手填"的条目。末尾是因为新发现的追加在末尾，而用户排在前面的顺序是意图。
  用户自己的删除永远优先于它。

**二、新发现的端点追加到末尾，不再按 kind 插队。**

"同一 WiFi 优先直连"这个意图改由 **`dialOrder` 在拨号时**按真实网段判断 ——
比插入位置精确（只在该网段真的匹配时优先），也不会动量用户的排序。

**三、拨号顺序：记住的那条先试 → 同网段的次之 → 其余按用户排的顺序。**

顺序的理由就是用户的原话：IP 一般不换，先试上次那条最省；**只有它拨不通**
（= 换了地点）才值得去查本机 IP 看网段。所以 `myLanIpv4` 是**缓存 + 失败时刷新**，
不是每轮都读：

- `reportActiveEndpoint` 顺带记住它（`rememberedEndpointUrl`）；
- `reportEndpointAttempt` 在 `ok == false` 时触发 `refreshMyLanIpv4()`；
- 下一轮重连的 `dialOrder` 就有新网段了。

**四、"同网段"判为同一 /24（前向匹配 ≥ 3 个八位组），不用 /16。**

这台机器同时有 `192.168.1.4`（WiFi）与 `192.168.2.41`（以太网）。按 /16 会把它们
判成同一网段，于是"在 WiFi 上却先去拨以太网那条"—— 正好是这套排序要避免的事。
公司网若是 /16 会拿不到这个加成，代价只是顺序不理想：那条仍然会被试到。

**五、用户管理：删自报端点 = 进隐藏集。**

否则下次 `endpoint.describe` 又加回来，删了白删。手填的直接从表里去掉
（没有"会被报回来"的问题）。`unhideEndpoint` 放回来。

## Alternatives considered

1. **保留"一次失败就删"，让用户靠重新扫码换地点**
   - 最强的理由：零新概念，而那条规则已经在治一个真问题（IPv6 轮换垃圾）。
   - 为何被否：它把"轮换垃圾"与"另一个地点"判成同一件事，而两者从数据上不可分。
     用户的核心诉求恰是"不要每次换地点都扫码"—— 保留它等于不解决问题。
   代价如实记：改判据后表会变长，所以配了上限保险丝；而长表本身不再有害，
   因为 `dialOrder` 把不通的排后面（这才是治 30 秒问题的地方）。

2. **用失败原因分类（`Network is unreachable` = 换网段 → 留；`timed out` = 电脑不在 → 删）**
   - 最强的理由：不需要 `succeededEndpointIds`，也不需要上限。
   - 为何被否：`EndpointAttempt.reason` 是**给人看的一句话**，各平台措辞不同
     （Android / iOS / 不同 WS 实现），按它分支就是第二套判据，而它迟早漂。
     而且"超时"既可能是电脑关机，也可能是跨网段被防火墙丢包 —— 分不开。

3. **在连接器侧过滤虚拟网卡地址（`listener.ts` 按网卡名筛）**
   - 最强的理由：junk 从源头就没了，手机侧一行不用改。
   - 为何被否：`listener.ts:134-138` 已经写明"过滤虚拟网卡靠名字匹配，又脆又漏"，
     而真正的答案在顺序。这条仍成立 —— 但**PC 端的显式隐藏**留给下一期：
     那不是"猜"，是用户点名（见 Consequences 的未做项）。

4. **把"用户钉死某一个端点"做成 hard pin（拨不通也不换）**
   - 最强的理由：表达"我说了用这个"最直接。
   - 为何被否：用户明确否掉了这个语义 —— 他的原话是"连接不上会自动试其他的不是"。
     硬钉死会让"我说了用中转"变成一处静默的卡死，而用户以为会自动兜底。
     "手动选择"在本仓的解释就是**排顺序**（`preferEndpoint`），失败照样顺延。

## Consequences

- 收益：家 ⇄ 公司换地点不再需要重新扫码（成功过的地址留着、记住的那条先试、
  失败后同网段那条自动排上来）；用户的首选不会被自动发现冲掉；
  删掉的端点不会被 describe 加回来；IPv6 轮换垃圾仍会被清掉且不再拖慢冷启动。
- 收益（顺带修掉既有 bug）：端点发现结果**立刻**影响下一次拨号，不必重启 App。
- 代价：`core/endpoint.dart` 多四个概念（`manual` / `subnetScore` / `dialOrder` /
  `EndpointMeta`），`data/` 多三个持久化键（`dsh.endpoint_meta` 里的 remembered /
  hidden / succeeded）。都**不含秘密**（就是地址与集合）。
- 代价：`Endpoint.manual` 只在手机自己的落盘里出现 —— 连接器不知道也不该知道
  （它是"这台手机信不信这个地址"，不是"电脑有没有这个地址"）。所以
  `endpointToJson` 与 `endpoint.describe` 的形状**仍然共用**，协议一行没改。
- 观测点：
  - `app/test/endpoint_switching_test.dart` 的 `dialOrder` 两条（含
    "192.168.1.x 与 192.168.2.x 不算同网段"与"手填标记在合并后保留"）；
  - `app/test/endpoint_discovery_test.dart` 的「多地点」三条与「用户管理」两条。
  - 变异校验：去掉"成功过就留着"的豁免，**恰好**「成功过的地址留着」那一条变红，
    还原后全绿。
- 未做（下一期）：设置页的删除 / 手填 / 来源徽标 UI；PC 端的管理面
  （隐藏虚拟网卡地址、追加要上报的地址如 Tailscale）。两者都不需要改协议。
