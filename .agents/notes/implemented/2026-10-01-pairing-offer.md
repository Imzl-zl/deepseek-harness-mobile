# Agent Note: 出码核心 —— 登记不成就**不出码**

Status: implemented（`src/pairing-offer.ts` + 3 条用例；命令接线与令牌读取见"仍未做"）

## Problem

出码是 §12.1 的第 1 步，而它有一个**顺序**上的判断，写反了不会报错、只会让人排查错方向：

1. 生成码；
2. 把 `codeHash` **登记到中转**（§12.1 的出码登记，中转的 `POST /pairing/register`）；
3. 把二维码给操作者。

如果按"先生成、登记失败只记日志"来做，操作者会拿到一张**扫了也配不上**的二维码：
手机侧的失败表现是"配对码不对/请重新出码"，人自然会怀疑手机或码，而真因是电脑侧那条日志。

## Decision

`src/pairing-offer.ts` 把这段判断单独成层，登记做成**端口**（`register: (codeHash) => Promise<void>`，
失败要抛）：

- **登记失败 → `{ kind:'error' }`，且结果里不夹带任何码/载荷**。
  "不出码"是明确的（文案里直说"这次没有出码，重新执行即可"），
  而不是给一个"看起来成功"的二维码。
- **登记用的哈希必须与给出的码同源**（用 `offer.codeHash`，不让调用方自己算）——
  否则中转登记的是 A、二维码里是 B，症状同样是"扫了配不上"。
- 这一层**不 import DSH**：返回值写成 `{kind:'success'|'error', text}`（与 `CommandResult` 同形），
  于是它可以脱离插件与网络测（3 条用例，几十毫秒）。

准入门槛（可机械判定）：3 条用例 ——
① 登记成功才出码，且载荷里含 `relay` / `pcPubEd` / `code`，登记用的哈希与码一致；
② 登记失败 → `kind:'error'`，文案含"没有出码"，且**正则扫不出任何 22 位 base64url 串**、不含载荷片段；
③ 两次出码登记两次、哈希不同。

## Alternatives considered

1. 先出码、登记失败只记日志（或回一个"稍后会自动重试"）
   - 最强的理由：操作者总能立刻拿到二维码，体验更顺；登记可以异步补。
   - 为何被否：那张码**注定配不上**，而失败的可见面在手机侧（"码不对"）——
     那是把电脑侧的基础设施故障伪装成用户输错码。宁可让操作者重跑一次命令。
2. 在这一层直接 `fetch` 中转（不用端口）
   - 最强的理由：少一层间接，链路更短。
   - 为何被否：那就必须起 HTTP（或打桩全局 `fetch`）才能测"登记失败时不出码"这条关键判断。
     端口化让这条判断几十毫秒可测，而真正的网络调用留在装配层。
3. 把命令的接线也放在这一层（`ctx.commands.register` 直接写在这里）
   - 最强的理由：一个文件搞定出码，读起来集中。
   - 为何被否：这一层就要 import DSH 的命令类型，于是它从"纯判定"变成"装配"，
     测试要挂载插件（本仓目前没有那种夹具）。

## Consequences

- 收益：出码的**判断**就绪且被测；"扫了配不上"这一类最难排查的失败在结构上被挡住。
- 代价/仍缺（**下一轮的第一步是一次查证，不是编码**）：
  1. **连接器令牌怎么读**：登记调用要带 `Authorization: Bearer <连接器令牌>`，
     而令牌在 `ctx.credentials` 的具名记录面里（契约 §12.2）。`credentialKey('<包名>','<id>')`
     的签名与记录结构**我还没查证过**，所以本轮**没有**写这个调用 —— 按项目规则（禁止猜）宁可不写。
     查证之后：`register` 的实现 = 读令牌 → `POST ${relayUrl}/pairing/register`（带 `codeHash`）。
  2. **命令接线**：`ctx.commands.register({ name:'dsh-mobile-pair', description, handler })`
     → `handler: () => offerForScanning({...})`（API 已在第 22 轮查证：`register(definition)`、
     `CommandDefinition{name,description,handler}`、`CommandResult{kind,text}`）。
  3. 装配层的那次登记调用接上之后，"电脑出码 → 手机扫码 → 中转转发 → 电脑落设备行 → 回执"
     这条完整配对链就只剩手机端 Dart 客户端了。
