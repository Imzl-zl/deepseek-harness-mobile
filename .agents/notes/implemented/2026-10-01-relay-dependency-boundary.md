# Agent Note: `relay/` 的依赖边界 —— 第一个运行时依赖是 `ws`，而且它在包内被验证

Status: implemented（`relay/package.json` 的依赖与安装；`ws` 的**使用**见"仍未做"）

## Problem

`relay/` 此前只有测试、没有依赖（测试跑在 Node 的类型剥离上，零依赖）。网络层一到，
两件事必须当场定清，否则会在后面变成"说不清为什么这样"：

1. **中转要不要运行时依赖？** 连接器**没有**运行时依赖：它只拨号，用 Node 自带的 `WebSocket`
   客户端。而中转要**接受**连接，而 Node 的内建只有客户端 —— 服务端实现必须自己写 WS 握手与分帧
   （不讨论）或引入 `ws`。
2. **依赖加在哪一层？** 是让整个中转工程都依赖 `ws`，还是只让"真的碰 socket 的那一层"依赖它？

## Decision

- **引入 `ws` 8.18.3 作运行时依赖，`@types/ws` 作开发依赖。** 理由是事实而非偏好：
  Node 22/24 的全局 `WebSocket` 只有客户端（`connector` 的生产代码就靠这一点，所以它零依赖）。
  自己实现 RFC 6455 的握手、掩码与分帧是几百行安全敏感代码，没有任何收益。
- **依赖只落在"碰 socket"的那一层。** 中转的判定层（路由 / 登记 / 大脑 / 票 / HTTP 面）
  至今**零依赖、可脱离网络测**（33 条几十毫秒的用例），这个性质要保住：
  `ws` 只允许出现在未来的 `ws-face.ts` / `main.ts` 里，判定层不许 import 它。
  这是"在边界注入依赖"的具体落法，也让将来的多实例/替代传输不必动判定层。
- **装了就在包内验证**：`pnpm install`（7.5s + 3.2s，基本从 store 复用）→
  `pnpm test`（33 条全绿）→ `pnpm typecheck`（0 错）→ `node -e "require('ws')"` 确认能加载。
  不把"依赖装上了但没用过"留到下一轮才暴露。

## Alternatives considered

1. 不引依赖，自己实现 WS 服务端
   - 最强的理由：中转保持零依赖，部署只需 node。
   - 为何被否：RFC 6455 的握手、掩码、分帧、控制帧与关闭握手是几百行**安全敏感**代码，
     而它换来的是"省一个纯 JS 依赖"。这与"连接器用 Node 自带客户端"不矛盾 ——
     客户端有内建、服务端没有，这是平台事实。
2. 把 `ws` 加进判定层的依赖（例如让 `core.ts` 直接收发 socket）
   - 最强的理由：少一层间接，读起来"一步到位"。
   - 为何被否：那会让 33 条判定用例从"几十毫秒、零依赖"退化成"要起 socket"，
     而它们盯住的恰是最容易静默出错的部分（窗口裁剪、归属学习、失效规则、状态码）。
3. 用 `http` + `ws` 之外的东西（如 unix socket 或 mohttp）做中转入口
   - 最强的理由：少一个协议栈。
   - 为何被否：契约 §2 的拓扑写的是 **WSS**；而且手机端（Dart）走 WebSocket 是最省事的路径。

## Consequences

- 收益：中转的依赖边界清晰 —— 判定层零依赖、`ws` 只落在传输层；依赖装好并当场验证过。
- 代价：`relay/` 现在需要 `pnpm install`（连接器同款代价）；`ws` 成为第一个运行时依赖。
- **仍未做（下一轮）**：`ws-face.ts` / `main.ts` 的接线 ——
  - HTTP：`POST /ws-ticket`、`POST /pairing/register`（转给 `http-face.ts` 的判定）；
  - WS：两个入口（连接器带 `Authorization: Bearer <令牌>`；设备带 `?ticket=...` 换票），
    升级成功后 `attachConnector` / `attachDevice`，消息走 `core.onLine` 并把投递写回目标连接，
    断开时 `detach*`；
  - **冒烟用例**：起服务器（port 0）→ `POST /ws-ticket` 拿票 → 两个 WS 连上（设备 + 连接器）
    → 设备发一行 → 断言连接器收到 —— 那是"中转真的能转发"的第一条端到端证据。
