# Agent Note: 通道评审结论落成契约修正 —— 三条会静默丢数据的缺口 + 三条被驳回的外部反馈

Status: implemented

## Problem

通道契约在落盘时把三件 DSH 的真实形态当成了别的东西,而这三处都不会在本地测试里变红:

1. **实时流式帧被默认能塞进 `seq` 空间**。DSH 的逐 token 输出走的是 opt-in 的 `assistantStream` 流(`start` 带 `startedAfterSeq`、有独立 revision 水位),**不推进会话 `seq`**;而信封里 `ev` 必带 `seq`。后来者只有两种选择——要么污染"修订号 = 会话事件 seq"这个唯一真值基础,要么让"流式打字"这个明确的体验目标没有数据来源。
2. **基线快照被当成原子整体**。契约里 `SyncSnapshotRequired` 只有 `sid` + `reason`,参考实现的 `snapshotItems()` 一次给全、没有页概念;而 DSH 的开场快照本身就是 `maxMessages`(默认 50)+ `hasMore` 的有界页。缺 `asOfSeq` 的后果是:快照基于 seq=1000 生成、`since=1050` 的请求在快照之后到达时**静默丢一段**,丢的可能正好是任务终结或审批。
3. **待审批/待回答被归入"瞬时事实"**。它们其实随会话日志持久化(ask 与 outcome 成对落盘,且要求 turn 打开),悬空形态是"有 ask、无 outcome"。归类错误的后果写在契约里:桥接进程重启后集合就空,重启前悬空的审批在手机上再也不会出现——**而这不是 DSH 的限制,是没去读日志**。

同时三处事实判据需要更硬:插件兼容性判据是 `peerDependencies`(不是 `engines.dsh`,后者不被任何加载器强制)、会话落盘格式当前为 v4、上传既无预检上限也无配置的请求体上限。另有一处**声称与实测不符**:契约称两处变异"分别被 fixtures 与回环抓住",实测只有 fixtures 抓住,回环因自行取 transient 而绕过了被测路径。

外部调研还送来三条会改变动作的反馈,其中两条经核实是**误伤**(见下)。

## Decision

评审结论分三层落盘:**现状事实与接口契约进 `docs/`**(`channel-review-notes.md` + `subsystems/remote-channel.md` 同步修正),**因果与否决理由进本篇**。契约层直接补三条缺口(live 帧、快照三要素、待审批的持久投影)并显式化两条规则(接收端 seen-seq、ack 兼作流控窗口)。

准入门槛(可机械判定):

1. 契约里每条 DSH 行为断言必须带 `packages/...:行号`;查不到就写「未找到」。
2. 文档不得出现"某个不被强制执行的字段决定行为"的表述(`engines.dsh` 是唯一已知实例)。
3. 恢复语义相关的新增条款必须同时给出 fixture,或在评审文档里明确标注"未覆盖"。
4. 变异校验的声明必须与实测一致:声称被两层抓住的,必须真的两层都变红。
5. "瞬时事实"集合只允许两项:电脑在线态、能力位。带 `seq` 的事实一律按持久条目处理(进快照、upsert、可从日志重建)。

## Alternatives considered

1. 只把结论留在对话里,不改文档
   - 最强的理由:方案已定稿,改契约文档要承担"文档与实现漂移"的风险,而评审看起来是一次性的。
   - 为何被否:项目规则是"原型即事实、文档是基线",对话里的结论不会被执行;下一会话会重新推断出同样的假限制——这正是 Problem 里描述的模式,把结论写进对话等于没写。
2. 把六条缺口一次写成完整协议定稿(含全部帧字段与最终算法)
   - 最强的理由:一次到位,后来者不需要再决定任何事。
   - 为何被否:其中两条依赖尚未做的实测(手机端小帧 AEAD 基准)与尚未做的产品决策(审批仲裁三选一)。写成定稿等于把未验证的假设固化成契约,而契约的成本正是"改它要同步两侧实现"。因此只把**不依赖实测的部分**写死(live 帧的语义、快照三要素、seen-seq、流控),把算法与仲裁留成显式待定项。
3. 评审整体写进 `.agents/notes/`,不新增 `docs/` 分析文档
   - 最强的理由:评审本质是"为什么这样取舍",看起来天然属于笔记。
   - 为何被否:评审里大部分内容是"DSH 现在是什么样"的现状事实与行号,按 `.agents/notes/AGENTS.md` 的边界这些属于 `docs/`;混进笔记会让两边都不可检索,而且笔记不该随行号漂移更新。
4. 直接改写 `.agents/notes/proposed/2026-09-30-remote-channel-reverse-ws-e2ee.md`
   - 最强的理由:那是通道决策的正本,改它最省事、不用新增文件。
   - 为何被否:笔记契约规定"已经发生的决定不能删";该篇的 Alternatives 与结论经核实仍成立(它描述的"参考实现服务端持久化会话 meta 与 timeline 并分配持久序号"是对的)。需要修正的是 `docs/` 里的现状事实,不是决策记录。

### 被驳回的三条外部反馈

1. **"插件里跑长连接这条路线不成立"**(依据:sandbox 把 `fetch`/`setInterval`/`require` 全部 trap、无 WebSocket、`ctx.web` 只有一次性请求)
   - 最强的理由:这段源码确实成立,而它确实让"动态 Cordis 包开长连接"不可能。
   - 为何被否:契约 §2.1 第一条本来就要求**做成 npm bundle、不能用动态包**,引的正是这段源码——它是方案的论据,不是反例;运行位置(`dsh-desktop-host` 子进程)亦已核实。把"动态包不可行"读成"插件不可行"会推翻一个已经被出货实现验证过的形态。
2. **"`ctx.storage` 没有修订号 → 方案需改设计"**
   - 最强的理由:storage domain KV 确实只有 unit `version`,没有自增 revision;而契约 §2.1 写过"修订号必须落在插件自己的持久化存储里"。
   - 为何被否:修订号的定义在 §6——直接取 DSH 的会话 `seq`,插件不分配。但这条反馈**戳中了一处真实矛盾**:§2.1 与 §6 不能同时成立。已按"增量缓冲与去重表落插件存储、修订号不落"拆开重写。
3. **"附件 MIME 字段实名应统一为 `mediaTypes`"**
   - 最强的理由:在 DSH 源码里检索 `allowedMimeTypes` 一无所获,DSH 侧的实名确实是 `mediaTypes`(`ImageMediaType` 联合)。
   - 为何被否:被引的那句描述的是**AA 契约层**,AA 真的以 `allowedMimeTypes` 把它写进 capability metadata 并由其客户端消费。两层名字不同是事实,已在 §2.2 与 §9 各点明一次,避免后来者互相检索。

## Consequences

- 收益:契约里每条 DSH 断言都可按行号复核;三条会"看起来对但静默丢数据/丢审批"的缺口写进了契约而不是留在对话;"瞬时事实"被收窄到两项,带 `seq` 的事实有统一处理方式;变异校验的覆盖空洞被记录并给出补法;`connector/` 的工程形态有了可抄的样板(参考插件清单:`dsh.bundle.patch` + 精确版本 `peerDependencies` + 4 行 `cordis.patch.yml`)。
- 代价:两侧实现面变大——手机端要多实现一条易变流(revision 重置)与快照分页拼接,电脑侧要多维护流式帧的转发与快照水位;`connector/` 的 `peerDependencies` 必须随 DSH 版本更新,否则插件被**静默跳过**(`skippedBundles`),升级流程因此多一步;评审文档引入三档证据等级,并把约二十处 DSH 行号引用纳入"DSH 升级时重核"的既有维护负担。
- 未消除的代价(如实记录):AEAD 算法与 nonce 策略、审批仲裁路径、鸿蒙设备私钥 channel 都仍是待定项,**三端同期交付仍有真实风险**;本批改动只保证"契约不再骗人",不保证实现一次成功。
