# Agent Note: seam e2e 改成子进程形态 —— 过渡件退休，顺带多测到两件事

Status: implemented（`tests/relay-transport-seam.test.ts` 改成起真进程；`tsconfig.e2e.json` 已删）

## Problem

第 40 轮把跨工程 e2e 写成**跨工程 import**（连接器的测试直接 import `relay/src/server.ts`），
并在当时的笔记里**明确记下它是过渡方案**：进程形态更接近生产，而且连接器不必为了测试去解析
中转的源码。它还带来一个副作用 —— 要用 `.ts` 后缀导入 relay 源码，于是多了一份
`tsconfig.e2e.json` 与一条脚本（主配置还得 exclude 那一条用例）。

第 41 轮有了 `relay/src/main.ts`（可运行入口）之后，这个过渡就可以退休了。

## Decision

这条 e2e 现在**起一个真的中转子进程**（`node relay/src/main.ts --config <tmp>`），
把端口写进配置（`port: 0`）并从它打印的启动行里读回实际端口；用例结束时 `SIGTERM` + 清临时目录。

结构上的收获：

- **过渡件全部撤掉**：`tsconfig.e2e.json` 删除、`typecheck:e2e` 脚本删除、
  主 `tsconfig.json` 恢复成 `include: ["src","tests","tsdown.config.ts"]` 的干净形态。
  连接器的类型门禁重新只有一条命令。
- **顺带多测到两件事**（跨工程 import 的形态测不到）：
  1. **入口本身**：能读配置、把摘要表建起来、把监听地址打印出来 —— 第 41 轮新加的入口
     在这里第一次被真跑；
  2. **配置错误在启动时失败**：给一份只有 `port` 的配置 → 进程以码 **2** 退出
     （第 41 轮那条判断现在有了会红的证据）。
- 断言的口径随之调整：子进程里读不到 `core.stats`，所以"中转认得这条连接"改成从**本侧**观察
  —— 连接层进入 `handshake`（说明升级被接受）与令牌不对时进入 `backoff`。
  这是同样信息的另一侧读法，而且更像真机（真机上我们也只能看自己这一侧）。

准入门槛（可机械判定）：3 条用例 —— 带令牌升级成功、令牌不对进入退避、配错以码 2 退出；
`pnpm exec tsc --noEmit` 0 错（单配置）、`pnpm test` 259 项全绿。

## Alternatives considered

1. 保留跨工程 import（不回退到子进程）
   - 最强的理由：不需要临时文件与进程管理，用例跑得更快（省一次 node 启动，约 200–400ms）。
   - 为何被否：它测不到入口（配置解析、摘要表装配、监听、退出码），而那正是第 41 轮新增的部分；
     而且它要求连接器的测试去解析中转源码 —— 两个工程在测试上也耦合，方向不对。
     速度差可以接受：这三条用例总共约 1 秒。
2. 用固定端口而不是 `port: 0` + 解析输出
   - 最强的理由：不必解析打印文本（那看起来脆）。
   - 为何被否：固定端口在并行跑测试或本机已有服务时会**随机失败**（最难查的一类）。
     解析一行稳定的输出是可接受的代价 —— 而且那行输出本身也在被验证（入口真的打印了地址）。
3. 让子进程通过 stdout 输出 JSON（便于解析）
   - 最强的理由：比解析人类可读的文本更稳。
   - 为何被否：那行输出是给人看的（操作者启动服务时唯一的指引）；为了测试把它改成 JSON，
     等于让产品为人让步。测试解析一个固定形状的地址是可接受的。

## Consequences

- 收益：e2e 与生产同形（中转是独立进程），过渡件清零，并且多测到入口与退出码两件事。
- 代价：用例慢约 1 秒；测试依赖"启动行"的文本形状（改那行文案要同步改用例 —— 已在此写明）。
- **仍未做（下一步）**：
  1. **三方 e2e**：中转（子进程）+ 连接器（fixture 的连接层）+ 手机替身跑通"配对 → 握手 → 发一句"；
  2. 令牌签发/吊销（§12.2 的另一半）；手机端 Dart 客户端；每连接状态那个岔口。
