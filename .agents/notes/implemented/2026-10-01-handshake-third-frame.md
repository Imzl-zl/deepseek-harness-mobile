# Agent Note: 握手的第三条消息在帧联合里根本不存在 —— 补一个 `confirm` 帧类型，而不是把它塞进第一条业务帧

Status: implemented

## Problem

契约 §4.1 写着握手三条消息，第三条是手机 → 电脑的 `confirm { sigA, transcriptHash }`；
而 §3 的帧联合里只有 `hello` 与 `hello-ack`，`confirm` **一个类型都没有**。同一节末尾还留着两句话：
「`confirm` ← 即第一条业务帧」与「收到对方第一条能解开的 AEAD 帧即确认」——它们与 §2.2 的
「未完成握手的连接只接受握手帧，其余帧一律 `protocol/bad-frame` 并关闭」直接冲突。

在把驱动器接上连接之前，这个洞**没有任何东西会红**：`handshake-frames.ts` 只产出 `box` 不产出帧；
`assertHandshakePhase` 的白名单是 `['hello','hello-ack']`；fixtures 与向量都不碰握手帧。
一旦接上，应答方收到 `confirm` 会判成"握手期收到业务帧"、按 `protocol/bad-frame` 关掉连接 ——
症状是"手机永远停在握手"，而电脑侧看起来一切正常。

## Decision

`confirm` 是帧联合里的**独立类型**（`{ v: 1; t: 'confirm'; id: string; box: string }`），
握手期白名单是完整的三元组，`confirm` 的 `box` 与另两帧一样是**明文编码容器**。
§4.1 的两句含糊表述换成两侧各自的完成判据（发起方验 `sigB` 通过即完成；应答方验 `sigA` 且摘要比对一致即完成）。

准入门槛（可机械判定）：

1. §3 的联合里有 `confirm`，§2.2 的白名单与它逐字一致；`HANDSHAKE_FRAME_TYPES` 与 `KNOWN_FRAME_TYPES` 都含它。
2. 握手期收到业务帧仍然一律关闭：驱动器在场也不例外（连接级 e2e 断言关闭码 4002 + `protocol/bad-frame`）。
3. 握手三帧不带 `fc`、不带 `sid`（e2e 断言线上形状；连接层负责不盖计数器）。
4. 跨端向量里的 transcript 由**字段重拼**得出，而不是重签向量里存好的那串字节。

## Alternatives considered

1. 把 `confirm` 塞进第一条业务帧（§4.1 原文"即第一条业务帧"）
   - 最强的理由：省一个帧类型，而且"第一条能解开的 AEAD 帧"天然顺带验证了密钥可用 —— 少一条独立的往返。
   - 为何被否：与 §2.2 的硬规则冲突。那条规则的价值恰恰在于它是一条**纯帧类型的白名单**，
     能在解码处判定；放行 `confirm` 就必须改成"第一条业务帧可以进来，但得看它载荷里是不是 confirm"，
     而载荷是加密的 ⇒ 判定点从解码处掉进业务层，`assertHandshakePhase` 退化成摆设。
     另外 `confirm` 本来就不该被加密：它承载的是抗中间人的签名，而"密钥可用"此刻尚未确认。
2. 用 `hello-ack` 类型反向承载 `confirm`
   - 最强的理由：零协议改动，现有白名单原样可用。
   - 为何被否：语义反向（ack 是应答），且白名单再也表达不了"谁在第几步" —— 同一个类型出现两次，
     驱动器只能靠状态猜，而猜错的症状是随机断连。
3. 规格不动，让连接层为 `confirm` 开个特例
   - 最强的理由：改动最小，只影响 TS 侧。
   - 为何被否：手机端（Dart）还没写，规格是它唯一依据。代码里的特例在移植时 100% 会丢，
     而丢掉的表现是"另一侧永远连不上"。

## Consequences

- 收益：握手三帧在帧联合里齐了；「握手期只收握手帧」重新成为可机械断言的白名单；
  §4.1 的完成判据从两句互相矛盾的话变成两条各自可测的规则。
- 代价：§3 多一个类型（中继路由视图不变：它只看 `t` / `sid` / `seq` / `fc`）。
- 顺带修掉一处更早的漂移：跨端向量签的还是**旧定义**（"两帧 `box` 拼接"），而 §4.1 早已改成从字段拼 ——
  Dart 侧照向量实现会实现一个循环定义的旧版本。现在 `verify-vectors.mjs` 会从字段重拼再重签：
  **只重签存好的字节拦不住"顺序写反"**，那正是这次要防的错。
