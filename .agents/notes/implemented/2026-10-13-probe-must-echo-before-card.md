# Agent Note: 审批探针必须先等自己的回读，再等卡片

Status: implemented

## Problem

真机两轮都白跑在同一处：审批探针发出去，手机上没有卡，3 分钟后用例红。但
**"prompt 根本没被电脑侧受理"和"模型没有调那个工具"在测试上长得完全一样** ——
都是"等了 3 分钟没有卡"。

根因是契约形状：`session.prompt` 是带幂等键的写操作，`SyncClient.call` 对它
**不建在途等待**（§5.6：结果由会话流收敛），所以被拒时手机侧拿不到任何信号；
而连接器侧 `idempotency.ts` 的 `abandon()` 会把 pending 行**删掉**，于是
"请求到了但被拒"（例如挑到的会话 agent 已 disposed → `session/not-found`）
与"请求根本没到"在连接器存储里同样不留痕迹。2026-10-13 两轮真机就是这样：
帧离开了手机（诊断面上的明文信封），连接器 dedupe 表没有行，任何会话日志里
没有探针文本 —— 从外部无法区分这两种解释。

## Decision

审批探针发出后，**先等它自己作为 `user/message` 落回来**（与步骤 ④ 同一个判据：
事件里含探针的特征文本），再等审批卡。同时两个失败点都打全诊断
（`_dumpDiagnostics`：连接态、关闭码、半开、已发方法序列），并给传输包一层
`_RecordingTransport` 记下每次 `send()` 的返回值。

准入门槛（可机械判定）：

1. 探针的回读断言在卡片断言**之前**，且判据是"事件里含 `dsh-probe.txt`"——
   不 import 连接器常量，避免"把契约字符串改坏"在两边一起变绿（恒真式）。
2. 两个失败点（回读、卡片）都调 `_dumpDiagnostics`；诊断里必须有
   `send 返回值(按序)`，否则分不开"帧没出手机"与"帧死在路上"。
3. 变异校验：把回读断言挪到卡片断言之后，回读失败时的诊断必须消失
   （即它确实只在回读失败时打）。

## Alternatives considered

1. **只把等待窗口再调长**
   - 最强的理由：一行改动，且"免费渠道一个轮次轻易超时"是真事。
   - 为何被否：窗口长短不改变"两种失败分不开"这个事实，只是等得更久。
2. **让带键写操作也等在途 `res`**
   - 最强的理由：失败立刻可见，还能拿到错误码。
   - 为何被否：§5.6 的契约原话就是"队列发出去了，但结果要等 `res`；不建在途
     等待，结果由会话流收敛"。改它要动契约与连接器两侧，而回读判据已经能
     拿到同一个事实（电脑侧确实受理了）。
3. **挑一个"已知活着"的会话当靶子**
   - 最强的理由：从根上避免挑到 agent 已 disposed 的会话。
   - 为何被否：手机侧只知道 `session.list` 的 `running`，判不出 agent 是否
     disposed；而回读判据把这类失败变成"3 分钟内一条指向明确的红"，比"猜
     哪个会话活着"可靠。挑号规则的隐患（`idle.first` 会叫醒别人的会话）
     另记在用例注释里，本期不改。

## Consequences

- 收益：两类失败分开。下次红的时候，红在回读 = 电脑侧没受理（查目标会话 /
  查投递），红在卡片 = 受理了但模型没调工具（查渠道 / 查权限档）。
- 收益：诊断输出第一次能分开"帧没出手机"（`send` 回 `false`）与"帧死在路上"
  （连接后来才断）—— 前者靠 `_RecordingTransport`，此前 `core/_write` 把
  `send()` 的返回值丢掉了，这一半证据根本不存在。
- 代价：通过时多一次回读等待（几秒）；用例多一个测试专用传输包装。
- 未修（如实记录）：`core/_write` 仍然丢弃 `transport.send()` 的返回值。
  它只在"socket 已死而状态机还没察觉"的窗口里咬人，且后果由重连自愈；
  修它要决定"发不出去"是抛、还是把队列项留在 outbox 里等重连 —— 那是产品
  决策，不在本次测试改动里顺手做。
