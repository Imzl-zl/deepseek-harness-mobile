# Agent Note: 会话列表按页要，而不是整表搬

Status: implemented（2026-11-01）

## Problem

上一批（`2026-11-01-list-row-payload.md`）把每行的投影块从 ~4 KB 裁到 ~1 KB 之后，
一次标题变更仍然要 **252 000 B**，而它改的是**一行里的一个字段**。剩下的大头是**行数**：
本机 351 行，屏幕上只有十来行。

同一批里也量清了判据：**可见 ⇒ 必须准；不可见 ⇒ 打开时才拉**。会话列表属于"可见"，
所以它不能被懒掉；但"可见"不等于"整表都要"——用户滚到哪儿才需要哪儿。

## Decision

`session.list` 加**分页**：请求 `{limit?, offset?}`，应答加 `hasMore`。

- **不传 `limit` = 整表**（`hasMore: false`）：老客户端一个字都不用改，行为逐字相同。
- **`hasMore` 按宿主那份可见清单算**（`offset + limit < 总数`），不是"`limit` 的倍数"——
  会话数随时在变，手机要的是"还有没有下一段"。
- **切在分配别名之前**：没发出去的行不进别名表。否则每翻一页都给整表铸一遍别名，
  分页省了字节、CPU 又还回去了（别名表还是有上限的）。
- 手机侧：一页 `kSessionRowPageSize = 50`；首屏只要一页；**刷新问的是"已加载窗口"**
  （`limit = max(已加载行数, 50)`）—— 一条通知不该把用户翻过的页打回第一页；
  **加载更多**从 `offset = 已加载行数` 接着要，**按 `sid` 去重**（宿主按活动排序，
  两次翻页之间会话会移动，重复一行比少一行更难看）。
- UI 在**两个**列表表面都有一行"加载更多会话"（首页内联列表 + 抽屉），
  因为两边看的是同一份 `AppModel.sessions`；**显式一行而不是"滚到底自动拉"**：
  `ListView` 会为即将进入视口的内容预构建，自动触发会在首帧把后面几页一起吞下来
  —— 那等于把分页又变回整表，只是没人看得出来。

## Alternatives considered

1. **游标分页（`after: {updatedAt, sid}`）而不是 offset**
   - 最强理由：活动排序下 offset 会漂（新会话插到最前面，后面的整体后移），
     游标不受影响。
   - 为何被否（暂不）：漂移的后果是"跨页重复一行"，而手机**按 `sid` 去重**已经兜住了；
     真正会丢的情形（一行从第 1 页被挤到第 2 页）只在"同时翻页 + 恰好有活动更新"时出现，
     而那条更新本身会触发一次"刷新已加载窗口"。游标版本要给连接器加排序键比较、
     还要让手机存游标；先付这些复杂度换不到可见收益。**若哪天实测到重复率高到碍事，再换。**
2. **让宿主分页（`sessionController.list({limit})`）**
   - 最强理由：少搬一次全量（连接器本来也要拿全表才能切）。
   - 为何被否：**宿主的 `list` 请求是 `_request` 空对象**（`api/session-controller/src/index.ts:274-282`），
     它不提供分页参数；而且我们是插件，不能改宿主接口。
   - 顺带：连接器拿全表在**进程内**（没有线上字节），切完只序列化 50 行 ——
     线上收益与"宿主分页"相同,CPU 那点开销在噪声里。
3. **不裁行、只分页**
   - 最强理由：只有一处改动（`limit`）。
   - 为何被否：排序与体积是两件事。上一批已经量过：不裁行时 50 行里 94.5% 是投影块
     （每行 ~4 KB），一页 50 行仍是 ~200 KB；两个改动各自独立可验，缺一个都不成立。

## Consequences

- 收益（真机，同一条 `session/rename` 探针）：
  - 一次标题变更出站：**1 943 515 → 252 000 → 47 507 B**（裁行 −87%，分页再 −81%；
    相对最初 **−97.6%**）。其中 `session.list`：1 941 638 → 250 122 → **45 630 B**。
  - 首次连上的整包 landing 从 ~2.1 MB 降到 **918 263 B**（同一账号 351 个会话）。
- 代价 1（用户要翻）：超过一页的会话要滚到底点一下"加载更多"。**这是有意的**：
  以前是"每次改标题都替用户把 351 行全搬一遍"，现在是"用户要才搬"。
- 代价 2（跨页重复）：见备选 1 —— 靠 `sid` 去重兜住；重复率没实测到，真碍事再上游标。
- 代价 3（契约改动）：`session.list` 的请求/应答形状变了 ⇒ 契约 §5.7 那一行、
  金样（`wire-shapes.json`，真实清单驱动）、App 的 `wire/rpc/session.dart` 同批改；
  老客户端不受影响（不传 `limit` 拿整表）。
- 代价 4（分页只在 App 侧生效）：**新 App 才带 `limit`**，所以真机验收要先装 APK
  （`flutter build apk --debug` + `adb install -r`，配对不丢）。
