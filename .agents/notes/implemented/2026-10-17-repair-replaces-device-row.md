# Agent Note: 重新配对替换旧设备行 —— 记录的单位是手机，不是每次扫码

Status: implemented

## Problem

2026-10-17 真机：同一台手机扫了 5 次码，电脑侧设备表攒了 5 条同名"我的手机"。
用户原话：「为啥每次扫都是一个新设备说是为了安全？扫码是交互凭证吧？你记录凭证，
禁用凭证不好了，为啥要用手机做单位？」

先读 DSH 源码核实了"凭证"与"设备"在这套协议里的关系，再动手：

- 二维码载荷（`connector/src/pairing.ts:181-200` 的 `offer()`）= `{v:2, relay, pcId,
  pcPubEd, pcPubDh, offerId, code}`。`offerId` 登记到中转，`code` 只存 SHA-256 在电脑侧、
  **不登记中转**（`pairing-v2.md` §3）。手机侧密钥对是扫码那一刻才生成的
  （`app/lib/ui/pairing_page.dart:207`）。
- 授权三要素（`pairing-v2.md` §5）：二维码固定的电脑身份 + 候选持钥证明 + 秘密校验。
  设备身份（密钥对）是配对行为的**产物**，不是二维码的内容。

所以用户说得对：**扫码是一次性交互凭证**（ bearer 秘密 + 公开邀请），授权的是
"这一次配对行为"；而电脑侧把每次行为的产物各写一行，行的单位就成了"每次扫码"。
上一轮 `.agents/notes/implemented/2026-10-15-new-identity-per-pairing-is-intentional.md`
定的是"每次配对新身份是有意设计"（覆盖种子泄露场景）—— 那条**继续有效**，本次不改
身份模型；要改的是**记录的单位**：同一台手机重复扫码应该替换旧行，而不是攒行。

## Decision

**`pair-commit` 的密文载荷加一个可选 `previousPairingId`，电脑侧据此替换旧行。**

1. **字段形状与位置**：`{v:2, offerId, code, previousPairingId?}`（43 字符 base64url，
   与 `pairingIdOf` 的输出同形）。它**只进 `pair-commit` 的密文**（I10：中转只看得见
   帧类型与路由元数据）；换票请求是匿名的，绝不能放。形状不合法 → 拒（`invalid`），
   **不静默忽略** —— 忽略会让"替换"悄悄退化成"又攒一行"而用户看不到原因。
2. **它不是凭据，是行定位符**。授权在 `pairing.accept` 里已经完成：先验一次性二维码
   秘密与候选身份，才 accept（`connector/src/pairing.ts:208-233`）。`pairingId` 由一次性
   code 经 HKDF 派生（`:85-87`），不参与任何授权判定；中转换票认的是设备令牌摘要
   （`relay/src/device-registry.ts:176-183`），光有 pairingId 换不到票、握不上手。
3. **替换动作**（`connector/src/pairing-endpoint.ts` 的 `commit()`）：按 pairingId 找到
   旧行 → **先删旧行再写新行**（换密钥 ⇒ 换 devId ⇒ 旧行必须消失）→ 新行的 `pairedAt`
   **保留旧行的值**（首次配对时刻）→ 名册照常重发。没有旧行（首配、手机凭据丢过、
   被管理面清理）就只写新行，与从前逐字一致。**停用的旧行也允许被替换** —— 重新扫码
   本身就是恢复路径（2026-10-15 定的语义），新行天然不带 `revokedAt`。
4. **手机侧的钩子**：`main.dart` 注入 `previousPairingIdOf`，取值按二维码的 `pcId`
   过滤（换一台电脑扫它是 null）。凭据还在时现算；被"重新配对 / 断开重来"清掉之前
   抓快照（`ConnectionRecovery.repair` 先清凭据再开配对页，不抓就永远没有）。
   确认卡多一行"会替换那条记录，不会新增一行"—— 记录行数变化是用户看得见的后果。
5. **写库顺序选"先删后写"**：反过来（先写后删）崩在中间会留下两行，且旧令牌在中转侧
   仍然有效（名册是全量快照，两行都报）；这个顺序崩在中间只是"这次配对没成"，
   手机重扫一次就好（旧行已删，不攒行）。代价见 Consequences。

**中转名册本来就支持"同一设备换密钥"**（研究的第 ② 问）：名册按 devId 键、
电脑侧每次上报**全量快照、差集即删除**（`relay/src/device-registry.ts:124-138`、
`:162-166`），所以旧 devId 行在下次 publish 时自动消失、旧摘要同步失效；I7（中转重启后
设备自己回来）靠电脑侧重放名册（`connector/src/index.ts` 的 `publishDevices` +
`relay-link.ts` 的 `onConnected`），新 devId + 新 tokenHash 照样回来。 roster 里
"同一 id 换摘要"（`device-registry.ts:156-159`）管的是另一回事（同 devId 换令牌）。

**管理面的单位**（研究的第 ③ 问）：DSH 插件管理器表达"凭据"的形状是
`setBundleEnabled(name, enabled)` —— 一个具名实体 + 一个布尔
（`packages/boot/plugin-manager/src/index.ts:476`），我们的 `setEnabled(devId, enabled)`
已照抄；DSH 凭据面的只读语义是 `describe` 只回 `{configured, source?, writable}`、
**从不回值**，`set`/`unset` 单向写（`packages/api/settings-controller/src/credentials.ts:
82-118`，投影在 `:45-51`，"Secret values cross in one direction only" 在 `:60-65`）。
可借的形状 = 管理面显示**状态**、永不显示秘密 —— 我们的设备行本来就只显示
revoked/online。所以管理面**不需要新端点**：`pairNote` 文案改掉（"每次扫码都生成
新记录" → "重新扫码替换旧记录"），"配对于"列的语义变成"这部手机首次配对该电脑的时刻"。

## Alternatives considered

1. **主种子持久化，后续配对一律复用（一台手机 ↔ 一条记录）**
   - 最强的理由：零协议改动（devId 不变，`putDevice` 天然覆盖旧行）；电脑侧永远
     一台一行。
   - 为何被否：① 它**取消了身份轮换** —— 2026-10-15 定的"重扫换新覆盖种子泄露场景"
     没了，而用户这次的抱怨是记录数，不是身份轮换；② 跨电脑复用种子 = 未计划的多电脑
     语义（同一密钥对出现在多台电脑）；③ `putDevice` 整行覆盖会**抹掉 `revokedAt`**，
     被停用的设备扫个码就自己活了（2026-10-15 笔记明确记过这个坑）。本方案在
     2026-10-15 已被否，这次前提没变，继续否。
2. **UI 层兜底：默认折叠历史记录 + 一键"保留最新一条"**
   - 最强的理由：零协议改动、零真机风险；列表确实会变干净。
   - 为何被否：它回答的是"怎么把行藏起来"，而用户问的是"为啥单位是手机"——
     **行还在攒**，只是看不见；管理面清理能力从"有了更好"变成"必须定期大扫除"。
     任务书明确"不许用'将就一下'收尾"，且研究结论是协议层可以安全地改。
3. **按设备名去重（同名即同一台）**
   - 最强的理由：电脑侧零改动，连协议都不用动。
   - 为何被否：名字不是标识符 —— 两台手机可以都叫"我的手机"，而重命名功能不存在；
     按名字合并会**把别人的行并掉**。这是用展示字段当主键。
4. **停用的旧行不允许被替换（过滤 `revokedAt`）**
   - 最强的理由："停用"看起来更接近永久禁令，语义更强。
   - 为何被否：2026-10-15 定的恢复路径就是"重新扫码换新身份"，过滤会让停用后的
     重扫退化成"又多一行停用记录"，用户看到的是"我重扫了怎么还连不上"（要再跑一趟
     管理面点启用）。而访问权上两者等价：不替换时攻击者扫个码照样得到新行。

## Consequences

- 收益：同一台手机反复扫码电脑侧**只有一行**（2026-10-17 真机 5 行的症状消失）；
  身份轮换保留（种子泄露仍可靠重扫更换）；"配对于"变成有意义的"这部手机从何时
  在这台电脑上"；中转侧零改动（全量快照天然收敛）。
- 代价：
  - **协议多一个可选字段**：`pair-commit` 载荷形状变了（TS/Dart 两侧 + 规格
    `pairing-v2.md` §5/§6/§7、`remote-channel.md` §12.1）。选"可选"而不是必填，
    就是为了旧回执/首配形状不受影响；fixture 与向量**无漂移**（486·26·49 不变，
    已实测重跑 `gen-pairing-vectors.mjs` 无 diff）。
  - **崩在两步之间的窗口**（删了旧行、没写成新行）：这次配对没成，用户要重扫一次。
    选了"先删后写"就是因为它的坏结局是"没成"而不是"多一行 + 旧令牌还有效"。
  - **凭证刷新时刻没有单独记录**：行里只有首次 `pairedAt`，"什么时候换的凭证"看不出来
    （不为它加 schema v3 —— 一行手机的凭证轮换时间没有消费者）。
  - **旧 pairingId 泄露的重放**：攻击者仍需一次有效扫码（物理接触电脑屏幕），而能扫码者
    本来就能配对（今天他会得到一条新行）；`previousPairingId` 只把"新增一行"变成
    "替换旧行"，效果是旧手机被踢下线（401 → 清凭据 → 回配对页，可恢复、管理面可见）。
  附带的好处：受害者会**察觉**（今天的静默新行反而发现不了）。
  - 手机侧多一个注入缝（`previousPairingIdOf`）与一条装配不变量断言；漏接它不报错，
    只是静默退回"又攒一行"—— 所以那条不变量写进了 `assembly_invariants_test.dart`。
