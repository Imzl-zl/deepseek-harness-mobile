# 配对链的引导凭据与设备归属:首配用配对码换票,重连用设备令牌

- Status: implemented
- Date: 2026-10-02

## Context

`docs/cookbook/next-session-pairing.md` 把「配对 → 换票 → 升级 → 握手 → 发一句/回一句」定为交付目标,并把缺口归成三条:App 拨的是裸 relay 地址、App 没有换票这一步、没有设备令牌(两端都没签发)。

按代码核实后发现**三条都真,但都在一个环的下游**:`pair` 帧要经中转到达连接器,而中转的 `/ws/device` 升级**必须要一张票**(`relay/src/server.ts:150-157`),票要凭据换,而凭据(设备令牌)按 §12.1 是**配对第 3 步的产物**。首配因此无入口 —— 提示词里"这一步现在就能通"的判断与代码不符(`relay/src/http-face.ts:85-91` 认证在路径分派之前;`relay/tests/core-nosid.test.ts:37-45` 已经断言了没换票时 `pair` 被丢弃)。

同时 App 侧比提示词写的更空:`app/lib/` 里**没有任何一处发送 `pair` 帧**,配对页只做本地派生(算出 SAS 就交给上层)。

所以这次要定的不是"设备令牌怎么签"(提示词的方向是对的),而是**首配拿什么换第一张票**,以及**已配对设备的重连走哪条路**。

## Decision

**首配凭配对码换票(方案 A);已配对设备凭设备令牌走同一个端点重连。**

- `POST /ws-ticket` **两种形态**:body 带 `codeHash`(无令牌,票绑一次性临时身份 `pending:<…>`)与 body 不带 `codeHash`(设备令牌,票绑真实设备 id)。升级入口只有一条(`/ws/device?ticket=`),不新开路径。
- **设备令牌由连接器签发,中转只存摘要**:连接器生成 `deviceToken + refreshToken`,把两者的 sha256 交中转(`POST /devices`),并在明文 `pair-ack` 里带上明文。
- **归属落中转的 `devices` 投影,且靠电脑侧重放名册重建**:连接器每次连上中转(`connecting → handshake`)就把整份名册重放一遍。这是 I7「中转可被清空后重启,已配对设备仅凭电脑侧数据收敛」的机制。
- **`pending:*` 永不落表**:它是首配那一跳的临时身份,只让 `pair` 帧能进门;配对成功后手机改用令牌路径。

## Alternatives considered

### A. 配对码换票(采纳)

**最强的理由**:二维码载荷一字不改(仍然只有 `{v, relay, pcPubEd, pcPubDh, code}`),中转仍然**只见 `codeHash` 不见码**,而且它天然与"重连走令牌"共用同一张 `devices` 表 —— 一个端点、两种凭据、一条升级路径,没有第二套入口要单独设计鉴权与限流。

**被采纳的原因**:它是唯一一个既闭合了首配环、又不引入新的常驻凭据载体(二维码仍是短命的带外秘密)、也不需要第二个网络入口的方案。代价见下面 Consequences 第一条。

### B. 令牌随二维码下发(电脑侧出码时预生成)

**最强的理由**:`/ws-ticket` 的语义完全不用动(永远"令牌换票"),而且首配那一刻就是双向认证的 —— 不必引入"临时身份"这个中间概念。

**为何被否**:二维码会变成**长期凭据的载体**。二维码是会被拍照、截图、贴进聊天窗口的东西,而它一旦带上设备令牌,这张图的有效期就不再是"5 分钟",而是"直到有人轮换令牌"—— 而轮换流程本期没有实现。要收口就得同时做轮换端点,那比方案 A 的工作量与攻击面都大。

### C. 新增免票的配对 WS 路径(`/ws/pair?codeHash=…`)

**最强的理由**:把"匿名连接"严格限制在一条只放行 `pair` / `pair-ack` 的短连上,配对完成即关闭 —— 从"最小暴露面"看这是最干净的形状。

**为何被否**:中转多一个入口,而那个入口的鉴权就是"配对码"本身 —— 于是限流、连接数上限、审计都要在它上面单独设计一遍(现有的限流按身份取桶,而这条路上没有身份)。方案 A 复用已有的升级路径与限流面,代价是 `pending:*` 这个临时身份概念。

### 重连:另开一条只认设备令牌的升级路径(否)

**最强的理由**:首配与重连的凭据形态完全不同,分成两条路可以让每条都只认一种凭据,不必在 `/ws-ticket` 里做分支。

**为何被否**:`/ws-ticket` 加一个分支只是十几行,而第二个升级入口要在中转的 upgrade 处理里再走一遍"读票 → 消费 → 限流 → handleUpgrade"—— 那一段(以及它的 429 语义、票被拒的那次**消耗掉票**这个有意的副作用)已经在 `server.ts` 里有一份。两份迟早不一致,而不一致的表现是"某一条路能绕过限流"。

## Consequences

- **`pending:*` 引入了"临时身份"这一档**。它的代价是中转侧多一个概念,而它的安全性建立在"配对只可能成功一次"这条事实上 —— 认领即消费(`pairing-registry.ts:76-88`)+ 配对成功后手机改用令牌。**未收口的部分如实记录**:临时身份在配对完成后不会被显式回收,它只是一张 60 秒的票用完后自然消失。
- **凭码换票不吃限流桶**。限流按身份取桶(§10:按 IP 会在反代后面把所有人归成一个),而首配那一刻没有身份。这是**有意的**:它的上界由配对码自身给出(一次性 + 5 分钟 + 认领即消费)。代价是"拿一堆过期 codeHash 刷换票"这条洪水不在限流面上,属于边缘治理。
- **`devices` 投影仍是进程内表**。I7 靠连接器重放名册成立,而不是靠中转自己持久化。换成 SQL 是部署侧的事,接口不变 —— 但**如实记录**:中转重启到连接器重连之间有一个窗口,那段时间设备换不到票(它的退避会覆盖过去)。
- **收益**:首配这条链第一次**真的跑通**了 —— `connector/tests/pairing-e2e.test.ts` 用真中转进程 + 真 HTTP + 真 WS 跑完了"出码 → 凭码换票 → 升级 → `pair` → 令牌 → 凭令牌换票 → 升级 → 真握手 → 双向 AEAD",以及"中转清空重启后设备只凭名册回来"。
- **刷新令牌的轮换流程未实现**。中转侧已有 `refresh_hash` 的落点与索引,但没有暴露端点;`refreshToken` 现在只被存下来。

## 三处被这一轮抓到的真问题(证据)

1. **`pair` 帧路由不到电脑侧**:首配的票绑 `pending:*`,而中转的设备侧无 `sid` 帧按 `binding` 路由 —— 认领时若不把 `pending:*` 也绑上,`pair` 会被当成"未换 ticket"丢弃。修法是首配换票走 `core.claimTicket(pendingId, codeHash)`(先写绑定再发票),而不是只认领不绑定。
2. **摘要必须先于回执到达中转**:手机拿到令牌会**立刻**拿它换票,而那时中转还不知道这台设备 → 401。这是竞态,症状是"偶尔第一次连不上、重试就好"。修法是 `pairing-endpoint.ts` 的顺序固定为 `putDevice → announce → reply`,并用一条顺序断言钉住。
3. **e2e 里 `pairingId` 必须由手机自己算**:回执里**没有** `pairingId`(契约 §12.1 只说它是码的 HKDF 输出,两端各自算)。e2e 的替身最初传了 `undefined`,于是**握手照样成功**(签名只覆盖 transcript),而 AEAD 永远解不开 —— 正是本项目记为"最坏的一类错"的形态(两侧各自看起来都正常)。
