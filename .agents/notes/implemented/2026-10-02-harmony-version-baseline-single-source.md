# Agent Note: 鸿蒙版本基线的唯一来源是一手仓库,不是规划表

Status: implemented（2026-10-02 查证并修正三处文档;证据在 `channel-review-notes.md` §1.9 与 §5）

## Problem

### 一、文档把"华为维护"当成了事实,而它是错的

`design-and-tech-plan.md` §3 写"鸿蒙走**华为维护**的 Flutter OHOS fork"。这个说法影响的是**风险评估**:
"华为维护"读起来像有商业主体兜底,而实际维护方是 **CPF-Flutter** ——
OpenHarmony 跨平台框架 PMC 下属 **Flutter SIG** 主导的**开放社区组织**。
一手证据是 CPF-Flutter `docs` 仓 `OrganizationDescription.md` 原文:"由 CPF-Flutter 团队维护"。

这个区别不是措辞问题:社区组织的**响应速度、版本承诺强度、长期存续性**与商业团队不是一回事,
而这三项正是 §11 风险表要评估的东西。

### 二、版本线三处互相矛盾,且都过期了

| 文件 | 原说法 |
|---|---|
| `design-and-tech-plan.md:77` | 锁 `3.41.10-ohos-X.X.X`(占位写法) |
| `app-platform-boundaries.md:87` | "当前稳定分支基于上游 **3.35.7**" |
| `channel-review-notes.md` §5 | 并列两条线,无"哪条是最新"的结论 |

按 `AGENTS.md` §6 的"三处不许各自漂移",这是三处来源。而**没有一处说得准**:

- 一手查证(AtomGit API v5 tags + 官方 `OrganizationDescription.md`):**最新稳定线是 3.41.9**,
  tag `3.41.10-ohos-1.0.1`(2026-08-17)与 `3.41.9+ohos-1.0.2`(2026-09-24);
- 3.35.7 只是**上一档**,`app-platform-boundaries.md` 那句已经过期;
- 官方规划表写"3.44 于 2026/09 发布",而 **3.44 至今(2026-10)只有 canary**
  `3.44.9+ohos-0.0.1-canary1`(2026-08-21)—— 规划表**未兑现**。

### 三、一个容易踩的命名坑

同一条适配线有**两种 tag 格式并存**:`3.41.10-ohos-1.0.1`(旧)与 `3.41.9+ohos-1.0.2`(新)。
官方页面自己混用。将来写 `pubspec.yaml` 的 Git 依赖时,按实际存在的 tag 写,不要按格式推导。

## Decision

**版本基线的唯一来源是 CPF-Flutter 的一手仓库(tag 列表 + 官方 `docs` 仓),不是规划表、不是二手转述。**

1. `design-and-tech-plan.md` §3 与 §11:"华为维护" → "CPF-Flutter(Flutter SIG 主导的开放社区组织)";
   版本线改成"当前最新稳定基于上游 3.41.9",并写明两种 tag 格式并存。
2. `app-platform-boundaries.md` §4:版本闸门从"基于 3.35.7"改成"基于 3.41.9",并补上
   "3.44 截至 2026-10 仍只有 canary"这一事实。
3. `channel-review-notes.md` §5:版本线一行改成带精确 tag 与日期的结论,新增"维护方"一行;
   新增 §1.9 记录四个鸿蒙上架案例;§9 登记新的一手/转述来源。
4. `connector-and-relay.md` 里程碑 12 与 `channel-review-notes.md` P2 第 13 条:占位写法
   `3.41.10-ohos-X.X.X` 换成实际 tag。

准入门槛(可机械判定):

1. 全仓(排除 `node_modules`)grep `华为维护` → 0 命中。
2. grep `3.35.7` 只能出现在"上一档"的语境里,不得作为"当前稳定线"。
3. 引用版本号时,`channel-review-notes.md` §5 必须同时给出 **tag 全名与日期**(无日期的版本号
   无法判断是否过期)。

## Alternatives considered

1. **只改"华为维护"这个词,版本线不动**
   - 最强的理由:改动最小,而且版本号会随上游更新自然过期,不必追。
   - 为何被否:版本线是**跨文件契约**(三处引用),而三处当时互相矛盾 ——
     不统一的话,下一次有人按 `app-platform-boundaries.md` 去锁 3.35.7,会直接踩坑。
     "会自然过期"恰恰是必须现在写清"哪条是最新"的理由。
2. **照抄官方规划表(3.44 排 2026/09),认为 3.44 已是稳定版**
   - 最强的理由:规划表是官方出的,看起来最权威。
   - 为何被否:实测**未兑现** —— 3.44 只有 canary,而 3.41/3.35/3.27 三线在 2026-09-24 仍有新 tag。
     这正是本次要立规矩的原因:**规划表是意图,不是既成事实**。按规划表锁版本会让项目卡在一个
     不存在的 SDK 上。
3. **不写具体版本号,只写"锁最新稳定线"**
   - 最强的理由:永远不会过期,零维护成本。
   - 为何被否:那就等于把"哪条是最新"的判断推给每个后来者 —— 而这次踩坑的原因正是
     没人去核一手来源。写具体 tag + 日期,至少让"是否过期"可判断(有日期才能算滞后多久)。
4. **把案例调研(§1.9)单独开一份文档**
   - 最强的理由:`channel-review-notes.md` 已经很长(约 1,950 词),再加一节会继续膨胀。
   - 为何被否:这四个案例的用途是**为本文档的版本闸门与能力包设计提供外部实证**,
     放进 `docs/` 会变成一份"业界观察"而失去与决策的绑定关系;而它仍在 5,500 词预算内。
     若将来继续膨胀,再按 `docs/AGENTS.md` 的"下沉迁移"顺序处理。

## Consequences

- 收益:版本基线**三处统一**且有日期可判断是否过期;"维护方"从"华为"纠正为 CPF-Flutter,
  让 §11 的风险评估建立在真实主体上;"3.44 无稳定版"这一事实被写下来,下次不会有人按规划表
  当既成事实用;新增的 §1.9 给出了"三端各写各的 vs 一套跨平台"的分界线,以及跨平台路线的
  真实代价清单(与本文档的能力包设计互相印证)。
- 代价:版本号**仍然会过期** —— 这次修正只保证"截至 2026-10-02 准确",不保证长期有效。
  上游发 3.44 稳定版后,三处仍要手工同步(与 `connector-workspace-shape.md` 记的
  "DSH 每次发 rc 要手工同步十三处版本号"是同一类维护负担)。
- 代价:`design-and-tech-plan.md` 本就超出 `docs/AGENTS.md` §7 的 3,000 词预算(改动前约 3,400 词,
  本次只增约 190 字符)。本次没有借机精简 —— 那是独立的一件事,混进来会让这次修正的 diff 失去焦点。
- 遗留:§1.9 的四个案例是**转述**(官方稿/媒体稿,附 URL),未逐字复核;
  微信"必须从零重写"与海底捞适配清单为腾讯/华为官方口径,可信度较高。
