# Agent Note: DSH 0.2.2-rc.3 体检 —— 跑着的宿主已经比类型基线新，而依赖面零变更

Status: implemented

## Problem

「DSH 更新了，要不要为 rc.3 适配 / 要不要抬线」这件事有三层事实来源，混在一起就会得出错答案：

| 层次 | 事实来源 | 这一轮的取值 |
|---|---|---|
| 用户在用的宿主 | `tools.md` §「DSH 升级后的固定动作」量**实际安装的**版本 | **0.2.2-rc.3** |
| 我们能装到的最新宿主 | npm `next` dist-tag | **0.2.2-rc.3** |
| 参考源码仓库 | `D:\sudy\github\deepseek-harness` 的 master | `dsh-v0.2.2-rc.3` 之后 **608 个提交** |

**上一轮的结论已经过期**：`implemented/2026-11-12-dsh-022-rc2-audit.md` 写「本机安装的宿主仍是
0.2.2-rc.1（= 我们的 pin）」，而本机宿主在 **2026-11-13 15:30** 自己升到了 rc.3
（`D:\soft\DeepSeek Harness\resources\app.asar` 的 `LastWriteTime`）。

于是今天的形态与上次相反：**类型基线（rc.1）比跑着的宿主（rc.3）旧**。上次拒绝抬线的理由是
「类型比运行宿主新会掩盖问题」，那条现在反过来指向「该抬了」—— 所以这次必须重新判，不能照抄结论。

还有一条会误导人的前提要先纠正：**rc.2 的 13 条 breaking topic 并不在 rc.3 上**（见下面第 5 小节）。
把它们当成「已到期的破坏」会白改一遍代码。

## Decision

**rc.3 不需要改代码；这一轮也不抬线（`devDeps` / `engines.dsh` 都不动）。**

理由一句话：体检结果是「rc.1 → rc.3 在我们依赖的每一个面上零删除、零改名」，所以现有的
`engines.dsh: ">=0.2.2-rc.1 <0.2.3-0"` 这条 claim **是被证实的**；而抬线会把它收窄成一条更窄、
且要重新做真机 e2e 才能再证实的 claim —— 用证据换一个更小的承诺，不划算。

### 5. rc.2 的 13 条 breaking topic：**一条都不在 rc.3 上**

先纠正前提：`docs/upgrade-guide/v0.2.2-rc.2/` **只存在于 master**，
`git ls-tree dsh-v0.2.2-rc.2 docs/upgrade-guide/` 与 `... rc.3 ...` 都**没有**这个目录
（两个标签下最新都只到 `v0.2.2-rc.1`）。也就是说：**rc.3 是在 rc.2 之上的一次补丁发布，
而那 13 条破坏是 rc.3 之后才落到 master 的下一批**。

六条独立实测（每一项都在 rc.3 上**还在**、在 HEAD 上**已被改掉**）：

| 主题 | 证据（rc.3 → HEAD） |
|---|---|
| `package-export-cleanup` | `packages/jobs/jobs/package.json` 的 `"./brand"` 子路径 rc.3 在、HEAD 换成 `"./types"` |
| `shared-search-filter` | `rankByName` 在 `packages/client/ui-primitives`：rc.3 **17 处** → HEAD **0 处** |
| `cordis-root-and-intercept-metadata` | `vendor/cordis/src/service.ts:25` rc.3 仍是 `resolveConfig`；HEAD `:28` 已换 `resolveIntercept` |
| `connection-page-peer` | `authorizeIndex` 在 `packages/client/connection/src`：rc.3 **2 处** → HEAD **0 处** |
| `python-ptc-removal` | `ptc-runtime-python` 在 `packages/`：rc.3 **2 处** → HEAD **0 处** |
| `shell-fs-tool-error-codes` | `JOB_BACKGROUND_DISABLED` 在 `packages/jobs`：rc.3 **2 处** → HEAD **0 处** |

其余七条（`session-status-package` / `client-module-metadata` / `cua-*` 三条 /
`deepseek-files-timeout` / `experimental-tool-error-codes`）同样核过，且**我们都没有对应依赖**：
`rankByName`、`searchMode` / `PopupSearchMode`、`SessionStatus`、`JOB_ERROR_CODES` / `JobErrorCode`、
`filesApiTimeoutMs`、`HarnessError`、`ui-primitives` / `popupSelect` 在 `connector/`（含 `client.js`

的一句注释里出现（讲 `approval` 卡片是"CUA 应用授权那种固定动作卡片"的样式来源，不是包依赖）。
`client.js:120` 的 `window.__ModuleLoader__.load({id, factory})` 在 rc.3 的类型里就是
`{id, chunk?, factory}`（`packages/client/modules/src/client/manifest.ts:363-371`，无 `meta`），
与指南说的「rc.3 之后才可选带 `meta`」一致 —— 即两边都合法。

**结论：13 条全部「不影响」，且都还没到期。** 它们真正发版那天，抬线就从「可选」变成「必须」，
那时按 `docs/cookbook/release.md` §3 的 playbook 走。

### 6. rc.2 → rc.3 到底改了什么（没有 guide，只能 git 核）

- `git rev-list --count rc.2..rc.3` = **6 个提交**：1 笔新功能（新包
  `@deepseek-ai/dsh-deepseek-chat-import`，把 DeepSeek 官网对话导出导入成会话）、
  2 笔修复（桌面版 release 的 restart-status/cwd、CI 的 bubblewrap 归档缓存）、
  1 笔发布版本号（`4c1cf20cb1`：380 个 `package.json`，每个 `1 1`），余下 2 个是 merge 提交。
  **没有一笔动服务、方法、事件或投影契约。**
- `packages/` 下：**374 个 `package.json` 有差异，其中 373 个是 `1 1`（只改版本号）**，
  唯一例外是上面那个新包（`133 0`）；**非 `package.json` 的改动只有 90 个文件**，全部落在
  11 个包里（新包 + 客户端 slot/picker 重构 + 生成物）。**零删除、零改名。**

  `@deepseek-ai/dsh-deepseek-chat-import`（`packages/util/official-bundles/src/bundles.ts:72`）。
  我们的插件页按行渲染，多一个包名不需要改代码。

## Alternatives considered

1. **把 `devDeps` + `peerDependencies` + `engines.dsh` 一起抬到 rc.3**
   - 最强的理由：让「编译基线 = 实际跑的宿主」，形态最干净；上一轮拒绝抬线的理由
     （类型比宿主新）在今天已经反过来，看起来正是该抬的时刻。
   - 为何被否：`connector/tests/manifest-compat.test.ts:60-64` 强制
     **`engines.dsh` 的下界必须等于钉住的版本**，所以「抬 devDeps」不是单纯换类型 ——
     它连带把支持范围从 `>=0.2.2-rc.1` 收窄成 `>=0.2.2-rc.3`，即**放弃 rc.1 / rc.2 宿主**。
     而这次体检恰恰证明了那一段范围是**真的能用**（零删除、零改名，且连接器在 rc.3 上真跑过）。
     抬线还要按 `docs/cookbook/release.md` §3 第 4 步补一轮真机 e2e（投影 / 子代理 / 审批三条链），
     那是独立的一批动作，不该混在「体检」里做完。真正该抬的时刻是那 13 条破坏发版之后 ——
     那时 claim 才真的变假，抬线才从「形态洁癖」变成「必须」。
2. **只抬 `devDeps`，`engines.dsh` 不动**
   - 最强的理由：既跟上类型，又不放弃 rc.1 / rc.2 宿主，看起来两头都占。
   - 为何被否：这正是上一轮警告的「类型基线比宿主新」。类型声明会开始 claim 一些旧宿主没有的
     形状，而 `tsc` 再也不会替我们拦住 —— 且 `manifest-compat.test.ts` 当场红，
     那条用例存在的全部意义就是禁止这个形态。
3. **把 13 条 topic 当作已到期的破坏，先按指南适配一遍**
   - 最强的理由：指南已经写出来了，照着改最省心，也显得「跟得紧」。
   - 为何被否：它们**不在 rc.3 上**（第 5 小节六条实测）。照着改会改出对当前宿主毫无意义的代码，
     而且很可能改错方向（例如把 `./brand` 换 `./types`，在 rc.3 上反而 import 不到）。
4. **什么都不做，也不写这篇**
   - 最强的理由：rc.3 上我们没有失败证据，代码一行不用改，写笔记是额外成本。
   - 为何被否：上一轮的笔记已经因为宿主升级而**部分过期**（它写「本机宿主仍是 rc.1」）。
     不写这篇，下一次被问「rc.3 要不要适配」时，人会去读那一篇并得到错答案；
     而「13 条不在 rc.3 上」这个反直觉事实必须留痕，否则下一个人会重新推一遍、甚至推错。

## Consequences

- 收益：**「rc.3 不用改代码」现在有证据**，不是「我觉得没事」：21 个服务键、16 个服务的方法、
  6 组事件形状、投影键集合、13 条 topic 逐条核过，且连接器已经在 rc.3 宿主上真跑过。
- 收益：纠正了一条会让人白改一遍代码的前提 —— rc.2 指南的 13 条破坏**不在 rc.3 上**，
  它们是 rc.3 之后 master 上的下一批。这条同时说明「没有 guide ≠ 没有变更」的反面也成立：
  **有 guide ≠ 变更已经进到你用的那一版**。
- 收益：抬线的时机被写清楚了（13 条发版之后），而不是留成「以后再说」。
- 代价：类型基线（rc.1）继续落后于跑着的宿主（rc.3）。方向是安全的（旧类型 + 新宿主，
  rc.1→rc.3 零删除），代价是我们**看不见** rc.3 新增的 API —— 目前没有任何一处需要它们。
  这条代价会在 rc.4 之后变大：那时若仍不抬，「没用到新 API」这个前提要重新核一遍。
- 代价：这篇和 rc.2 那篇一样**不是门禁**，靠人照着做。机械化需要读仓库外的 DSH checkout
  （CI 上没有），做进去就是一条永不作废的假绿 —— 理由见 rc.2 那篇的 Alternatives 2。
- 未做：真机 e2e（投影 / 子代理 / 审批三条主链在 rc.3 上的结构化验收）。现有证据是
  「宿主 15:30 升级、连接器 22:06 仍在写落盘点」这种**被动**证据，不是主动跑一遍。
- 未做：`docs/design-and-tech-plan.md:602` 里还写着 `engines.dsh` 是
  `>=0.2.1-rc.5 <0.2.2`（两轮之前的旧值）。它本来就已过期，与本次决定无关，
  但下次动那份文档时该顺手改成指向真文件（`docs/subsystems/connector-and-relay.md:16` 已有「下界 = 被测版本」的规则表述）。
