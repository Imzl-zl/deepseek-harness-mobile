# Agent Note: 通道协议以 fixtures + 参考实现为唯一规格源

Status: implemented

## Problem

协议这类东西天然会变成「文档写一遍、两个实现各写一遍」的形状：子系统文档用 TS 描述帧与恢复语义，电脑侧插件会用 TS 再实现一遍，手机端会用 Dart 再实现一遍。三处描述同一件事，而真正危险的错误恰恰不会在各实现自己的测试里暴露——「少发几条也算补上了」「游标超前时静默截断」「瞬时事实忘了回带」在两侧各自看来都自洽，合起来才不收敛。另一个隐患是把适配层混进语义测试：一旦恢复语义的验证依赖 WebSocket 握手、TLS 或 AEAD 实现，改一处密码学细节就红一片，久而久之没人再跑它。

## Decision

通道协议的可执行规格只有一份：`protocol/fixtures/` 的场景序列 + `protocol/verify-fixtures.mjs` 的判定规则；`protocol/reference/` 只是让这批 fixtures 跑得通的参考实现，**不是产品代码**。两侧实现（TS 插件、Dart 手机端）各自对着同一批 fixtures 跑，任何一侧都不得自留一份协议说明。

准入门槛（可机械判定）：

1. 新增一条恢复语义 → 先加或改 fixture（含期望结果），再改实现；fixtures 全绿之前不得合并实现。
2. 每个恢复应答必须落在「完整增量」或「带原因的基线快照」两者之一；出现第三种取值即失败。
3. 期望必须覆盖该会话的**每一次**恢复应答：次数不符即失败，不允许只断言第一次。
4. 语义层不依赖密码学：`protocol/` 下不得 import 任何加密实现，封箱在参考实现里是可逆占位。
5. 适配层（WS 握手、TLS、AEAD、推送投递）不进本层测试，由各落地端自测。
6. 改动 `protocol/` 后 `verify-fixtures.mjs` 与 `verify-loopback.mjs` 必须全绿；改断言时必须做一次变异校验，确认断言不是恒真。

## Alternatives considered

1. 用 JSON Schema 校验帧格式，恢复语义只写在文档里
   - 最强的理由：格式校验交给成熟工具链自动做，不用自己维护断言；文档描述语义最灵活、改起来最快。
   - 为何被否：格式对而语义错正是本层最危险的失败模式（「少发几条」「游标超前不报错」），Schema 一条都抓不住；而且文档无法执行，回归时没有任何东西会变红。
2. 两侧共享一份 TS 实现（Dart 侧走 FFI 或代码生成复用）
   - 最强的理由：同一份代码只有一个真值源，连 fixtures 都不需要，永不漂移。
   - 为何被否：Dart 复用 TS 恢复引擎要引入跨语言桥接和它自己的一致性风险；而恢复引擎本体只是「状态机 + 有界缓冲」，两侧各写一遍成本很低，真正贵的是语义分歧——那正是 fixtures 要解决的。
3. 只做端到端回环，不写单元级 fixtures
   - 最强的理由：回环最接近真实拓扑，一测就是全链路。
   - 为何被否：回环失败时定位成本高，且难以精确构造「窗口外」「游标超前」「会话不存在」这类边界；fixtures 让每条不变量单独可跑。两者都保留：fixtures 管语义，回环管接线。

## Consequences

- 收益：协议只有一处可执行真值；不变量（两种结果、条目 upsert、瞬时事实无条件回带、中转可被清空）全部有断言绑住，并已用变异校验证明断言不是恒真；语义测试不依赖密码学与网络，改一条不变量能立刻看出破了哪条。
- 代价：多维护一层参考实现——它不是产品代码，不能直接搬进插件或 App，两边都得照它重写；每加一条语义要先写 fixture，短期比直接改代码慢；Dart 侧还需要自己接一套 fixtures 运行器（目前尚不存在）。
