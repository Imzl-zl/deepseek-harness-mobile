# Agent Note: 出码登记接上了 —— 电脑侧配对链闭合

Status: implemented（`src/pairing-register.ts` + 命令接线；端到端 e2e 与手机端见"仍未做"）

## Problem

到上一轮为止，出码的**判断**（登记不成就出不了码）与**令牌读取**都已就绪，
但两者之间还缺一次真正的网络调用，以及"谁来触发"：

- 登记是 `POST /pairing/register`，而配置里给的是 **WSS 地址**（连接层用它拨号）；
- 命令要注册到 `ctx.commands`，而那个服务**可能不在**（它是可选服务）。

## Decision

`src/pairing-register.ts`：`createPairingRegistrar({ relayUrl, tokenSource, fetchImpl })`。

- **地址派生显式成函数**（`httpBaseOf`）：`wss→https`、`ws→http`，并**丢掉路径**——
  WS 那条路径（`/ws`）不是 HTTP 端点的路径。这件事写错的表现只是"配对总是失败"，
  所以它值得一条测试（而不是在装配处手改字符串）。
- **非 2xx → 抛，并把状态码带进消息**：`401`（令牌不对）与 `409`（配对登记不可用）的
  下一步动作不同，所以消息里必须看得出是哪一个。
- **不重试**：出码是人工触发的一次动作，失败时操作者能立刻再点一次（文案也这么写）。
  自动重试会在中转短暂不可用时给出"稍后才生效"的假象。
- **`tokenSource` 是函数而不是字符串**：令牌在凭据面里且 `readRelayToken` 有意不缓存
  （第 37 轮的判断），函数形态让"操作者换了令牌"立刻生效，**也省得为一个只在出码时用到的值
  安排装配顺序**（这正是本轮第一次接线时踩到的：先接线、后声明，`tsc` 当场报
  "used before its declaration"）。

命令接线（`index.ts` 的 `start-transport`）：

- `commands.register({ name:'dsh-mobile-pair', description, handler })`，
  handler 就是 `offerForScanning({ pairing, register, log })` —— **登记失败即不出码**；
- `commands` 不在时**只留声**（`logger.warn`）：那只是少了一条触发入口，插件本身仍然工作；
- 注销进 dispose 步（`unregisterPairingCommand`），与既有的 `unregisterInteractions` 同一处理。

准入门槛（可机械判定）：4 条用例 —— 地址派生三种形态、成功路径（URL/方法/头/体逐项断言）、
非 2xx 抛且消息含状态码、网络错误照原样抛。装配胶水仍未被测（同上两轮记录的已知缺口：
本仓没有挂载整个插件的夹具）。

## Alternatives considered

1. 让登记走连接层那条 WSS 连接（发一个方法面方法，不另开 HTTP）
   - 最强的理由：少一个端点、少一次鉴权，中转侧的 `/pairing/register` 也可以不要。
   - 为何被否：登记发生在**出码时**，而那时连接可能刚好不在（中转没起来、或正在重连）——
     于是"出码"会依赖"连接健康"，而它本来是一件本地动作。HTTP 让它独立于长连状态。
     另外契约 §12.1 的第 1 步是"电脑侧生成身份并编二维码"，第 2 步才是"经中转转给电脑"，
     登记属于第 1 步的准备工作，不该挂在第 2 步的传输上。
2. `relayUrl` 里直接配置一个 HTTP 地址（不做派生）
   - 最强的理由：少一处转换，配置更直白。
   - 为何被否：那会让**同一个中转**在配置里出现两次（WSS 地址 + HTTP 地址），
     而它们必须是同一台机器 —— 两处配置迟早会不一致。派生只有三种形态，且被测。
3. 登记失败也在命令行里给出二维码（并在文案里提示"稍后自动重试"）
   - 最强的理由：操作者总能立刻看到码，体验顺。
   - 为何被否：那张码**注定配不上**（第 36 轮已论证），而失败面会出现在手机侧。

## Consequences

- 收益：**电脑侧配对链闭合** —— 出码（带登记）→ 手机扫码 → 中转转发 → 落设备行 → 明文回执。
  证据：连接器 256 项（252 + 登记 4）全绿、`tsc` 0 错、`pnpm build` OK、protocol 门禁 486/49/26/17。
- 代价：装配层多一次 HTTP 调用（出码时）；`fetchImpl` 可注入以免测试碰网络。
- **仍未做（下一步，按价值）**：
  1. **端到端 e2e（本机回环）**：中转 + 连接器 + 手机替身三方一起跑通"配对 → 握手 → 发一句"。
     现在每一段都有测试，缺的是**拼起来**的那一条 —— 它会同时验证中转的登记/换票、
     连接器的出码/收码/落行、以及握手在配对之后成功。
  2. **手机端 Dart 客户端**（需要 Flutter 工程；本仓目前只有主题层）。
  3. 每连接状态那个岔口（监听面/多设备）仍未决定。
