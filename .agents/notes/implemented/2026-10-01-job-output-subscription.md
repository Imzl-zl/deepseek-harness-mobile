# Agent Note: 任务输出订阅 —— 每个任务至多一条流，背压一次只压一帧

Status: implemented

## Problem

上一轮把任务输出的**传输形状**定好了（`job` 帧、载荷三帧、满窗恢复信号），这一轮要把它接成
手机真的能用的东西：`job.follow` / `job.unfollow`，以及它们背后的订阅注册表。四个问题必须答：

1. **同一个任务重复订阅怎么办？** 面板重开、重连后重订都会再来一次 `job.follow`。
2. **换起点（`from` 不同）怎么办？** 手机明确要求从别处开始。
3. **满窗时那些帧放哪？** 任务输出是高频流，不能无限缓冲，也不能丢。
4. **订阅活多久？** 手机断线、插件卸载时，宿主流还在跑，谁去中止它？

## Decision

- **每个 `(sid, jobId)` 至多一个订阅**。重复 `follow`（`from` 相同或没给）**幂等**返回当前起点，
  不再开流；`from` 不同则先终止旧的再起新的。
- **`abort` 是终止的唯一机制**：替换、`unfollow`、`stopAll`、连接离开服务态四个入口都走它；
  转发循环靠"迭代器在 `next()` 里就中止"收工。**不额外加"我还是不是当前那一个"的判据** ——
  变异校验证明它在当前结构下不可达（附在下面）。
- **背压一次只压一帧**：`send` 满窗回 `'paused'` → `await waitWritable()` → 重发**同一帧**。
  转发循环是"取一帧 → 发出去 → 再取下一帧"，压住消费端就自然压住宿主流，**不需要缓冲队列**。
- **挂起的承诺必须被兑现**：`follow` 要等宿主的 `opened` 帧才能回答起点；
  若在这之前被替换/收起/断开，那个承诺**被拒绝**（回 `internal`）——否则方法面永远挂着，
  手机的 `req` 永远等不到 `res`，比一个错误难查得多。
- **订阅跟着连接活**：连接离开服务态即 `stopAll()`（手机收不到任何东西；它重连后自己按 `from` 重订）。

准入门槛（可机械判定）：

1. 同一任务重复 `follow` **不重开流**（宿主流只有一条），回同一个起点。
2. 换起点：旧流被中止，且**旧循环的收尾不许删掉新条目**（不然新订阅静悄悄地没了）。
3. 满窗：重发同一帧 —— 条数与顺序都不变。
4. 宿主流抛错 → 发一帧 `error`（设计要求手机显式渲染中断）；流结束却没给 `status` → 也要发 `error`。
5. 连接离开服务态 → 订阅清空、宿主流被中止。

## Alternatives considered

1. 允许同一个任务有多条订阅（谁爱订谁订）
   - 最强的理由：实现最短，注册表退化成"一个数组"；手机重复请求本来也是它自己的事。
   - 为何被否：**输出帧没有去重键** —— 它的"修订号"是字节偏移，同一段输出推两遍时两帧看起来一模一样，
     手机只能渲染成重复内容。要么手机去重（它得自己拼偏移窗口，等于把注册表的活挪到客户端），
     要么服务端只留一条流。选后者。
2. 满窗时在注册表里排队缓冲
   - 最强的理由：转发循环不必停下来，宿主流可以一直拉，实现上"像流一样"顺。
   - 为何被否：任务输出可以到几 MB（ring 256 KiB、结算后裁到 16 KiB），缓冲没有上界就是内存风险；
     而**宿主流本来是按需拉的 AsyncIterable**，停在这里天然把背压传回宿主 ——
     一句话：不需要发明缓冲，只需要不拉。
3. 不做订阅，手机改用 `job.list` + 定期读输出（轮询）
   - 最强的理由：不必维护订阅生命周期，方法面只有请求/应答两种形态，简单得多。
   - 为何被否：宿主 ring 会淘汰（`gapBefore` 就是这么来的），轮询要么丢内容要么把频率提到很高；
     而 DSH 自己的桌面端就是"展开即订阅，收起即关"（`docs/plugin-and-jobs-notes.md` §B.4 第 3 条），
     手机没有理由走一条更差的路径。
4. 订阅被终止时不兑现挂起的承诺（让调用方自己超时）
   - 最强的理由：少一处错误路径，`follow` 只在成功时 resolve。
   - 为何被否：那会让一个 `req` 永远等不到 `res`（手机侧表现为"点了没反应"），
     而真相是"这次订阅被替换了"。错误至少能被显示与重试。

## Consequences

- 收益：任务输出这条路从"帧类型"变成"手机能用的能力"：幂等、可换起点、有背压、跟着连接活。
  背压那套（一次一帧 + `whenWritable`）是**通用的**，会话订阅（`session.subscribe`）可直接复用。
  同时把 `job.list` 的响应行收敛到适配器那一个投影（此前方法面又抄了一遍字段）——
  `job.list`、`opened`、`status` 三处现在同一个形状，不可能漂移。
- 代价：注册表是有状态的（每个 `(sid, jobId)` 一条），所以它必须与连接同生共死；
  终结路径有四个入口却只有 `abort` 一个机制 —— 这一点靠"四条入口都 abort"的约定维持，
  新增入口时容易漏（已在代码注释里点名）。
- **仍未做**：会话订阅与翻页（`session.subscribe` / `session.page` / `session.unsubscribe`）、
  `session.prompt` 等带键的写方法、配对流程（§12.1）。方法面当前 **7/22**。

## 变异校验查出的一处不可达代码

给"只允许当前订阅出帧"写了一个外层判据（每帧出帧前 `if (!isCurrent()) return`），
变异（把它关掉）**没让任何用例红**。追下去：替换/收起/`stopAll` 三个入口**都会 abort**，
而宿主流迭代器在 `next()` 里就中止了 —— 于是"被替换之后旧循环还在转"这件事根本不会发生，
那个判据不可达。按"不留不可达的防御代码"删掉，同时：
- 保留 `finally` 里**承重**的 `if (isCurrent()) entries.delete(key)`，并补断言钉住
  （变异：无条件 `delete` → 新订阅被误删，1 项红）；
- 补一条**可测**的等价场景：正卡在 `waitWritable` 上时被收起 → 那一帧不许补发。

于是终结机制只剩一条（abort），每一处都对应一条会红的用例 ——
而不是一个看起来更安全、实际永远不执行的判据。
