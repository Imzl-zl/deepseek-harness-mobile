# Agent Note: 流控接线 —— `credit` 的 `fc` 是它自己的序号，被确认的序号在箱里

Status: implemented

## Problem

接流控（§4.3 的 W=128 窗口 + "收到即回 `credit`"）时，三处语义在纸面上说得通、落到线上就自相矛盾：

1. **`credit { fc }` 里的 `fc` 到底是谁的序号**。帧头的 `fc` 是**发送方向**的计数器，
   它同时是 nonce 的来源与对端重放守卫的依据（§4.2）；而 `credit` 要表达的是"我收到了**你**的第几帧"。
   同一个字段不能有两个意思 —— 若按后者，`credit` 就成了唯一一个 `fc` 语义例外的帧，
   nonce 派生与重放守卫都得为它开洞。
2. **"每收到一帧立即回 `credit`" 字面上包含 `credit` 自己**。照字面实现，两端会互相刷 ack 停不下来。
3. **满窗时"暂停发送"没有说暂停谁**。全部暂停会死锁：手机在等 `res`，而 `res` 因为窗口满发不出去。

## Decision

- **`credit` 的载荷是 `{"ack": N}`（累计确认"我已收到 `[0, N]`"），帧头的 `fc` 仍是它自己的序号。**
  这与 QUIC 同形：ACK 帧承载确认信息，而它所在的包有自己的包号。
  顺带把伪造堵住 —— 不经认证的 ack 能让对端误以为窗口已放开。
- **`credit` 不回 `credit`**（同 QUIC 的"ACK 帧不是 ack-eliciting"）。
- **满窗只压可补的两类**（`ev` / `live`）；`req` / `res` / `credit` / `persisted` 照发并照常计入 `unacked`。
- **暂停不是丢弃**：满窗时 `send()` 对可补帧如实返回 `false`（调用方据此暂停），
  已经在攒批队列里的帧重新入队、等 `credit` 到达再放。

准入门槛（可机械判定）：

1. `canSend(t)` 是窗口的唯一判据，且它自己包含优先级规则（不占额度的与不可暂停的恒为真）。
2. 窗口检查在**分配 `fc` 之前**：没发出去的帧不消耗序号。
3. `elicitsCredit(t)` 是"要不要回执"的唯一判据，且**只表达一次**（见下面 Consequences 的第一条）。
4. 满窗后 `send('ev')` 为 `false`、`send('res')` 与 `send('persisted')` 为 `true`，且后者真的到达对端（e2e）。

## Alternatives considered

1. 让 `credit` 的帧头 `fc` 直接表示被确认的序号（照 §4.3 的字面读法）
   - 最强的理由：帧更小（不必封一个 JSON 载荷），实现最直接，文档原文就是这么写的。
   - 为何被否：`fc` 会随帧类型变意思。它是 nonce 的唯一来源（§4.2），也是接收端重放守卫的输入 ——
     为一种帧开例外，等于让"每个 `fc` 只封一次箱"与"窗口严格递增"两条铁律都出现豁免路径，
     而这两条一旦放宽，症状分别是 AEAD 被破与连接被自己人反复关闭。
2. `ack` 放在帧头（另加一个字段，如 `{ fc, ack }`）
   - 最强的理由：不必封载荷，且 `ack` 仍在 AAD 里、同样被认证；比放进箱里更省。
   - 为何被否：**中继的路由视图是"只有 `t` / `sid` / `seq` / `fc` 四个字段"**（I10）。
     新增明文头字段会扩大中继可见面，而它不需要知道 ack；放进箱里则中继一无所知。
3. 满窗时暂停一切（含 `res`）
   - 最强的理由：窗口的语义最纯粹 —— 只要未确认就一个字节都不再发。
   - 为何被否：会死锁。`res` 是对端在等的应答，`credit` 是松开窗口的唯一手段；
     压住它们，双方都停在"等对方先动"。契约的"优先暂停"本来就要求区分这两类。
4. 满窗时直接丢弃可补帧（不重新入队）
   - 最强的理由：实现最简单，且 `ev` 本来就有重放窗口与快照兜底，丢了也能恢复。
   - 为何被否：契约说的是"暂停发送"而不是"丢弃"；丢帧会把一次瞬时拥塞放大成"手机少看几条、
     要靠下一次快照/补齐"，而代价只是把队列多留一小会儿。队列仍有界：满窗时 `send()` 不再接收新帧。

## Consequences

- 收益：通道有了背压。满窗时发送方停下来、并在对端确认后自动继续；`res` 与水位不被压住，
  不会出现"双方互等"；`ack` 被认证，伪造的信用松不开窗口。
- 代价：`credit` 多一个 JSON 载荷与一次 AEAD（每收到一帧回一个，逐帧成本，但控制帧本来就小）；
  契约 §3/§4.3 各改了一处措辞。
- **一处被变异校验抓出来的重复逻辑**：最初写成"`frame.t === 'credit'` 时提前 `return`"+
  "`elicitsCredit(t)` 判回执"，于是"`credit` 不回 `credit`"在两处各表达了一遍，
  谓词成了死逻辑 —— 把它改成恒真，**没有任何测试会红**。改成两个并列的 `if`（记账 / 回执）后，
  规则只剩一处，同一个变异立刻命中「credit 自己不再回 credit」那条 e2e。
- **尚未做的**：方法面 22 个 handler 仍未实现（`connector/unsupported`），配对流程未落地 ——
  也就是说"能安全收发、有背压"，但还没有一个方法能真的干活。
