# Agent Note: 配对凭据按电脑分槽（一台一个槽 + 一个 active）

Status: implemented

实现 `proposed/2026-10-29-one-phone-many-computers.md` 落地顺序第 2 步（凭据）。
第 1 步（端点身份 / UI 状态分桶 / 电脑名）见
`implemented/2026-10-30-endpoint-and-ui-state-host-scoping.md`。

## Problem

凭据层是**一张平铺的键表**（13 个 `dsh.<field>`）加一个 `deleteAll()`：

- `save()` 把整组键重写 ⇒ 配第二台电脑 = **覆盖第一台**；
- 没有"当前是哪台"的概念，`load()` 只能回一份；
- `clear()` 是 `deleteAll()` ⇒ "这台电脑不再认我"与"这台手机撤销所有配对"是同一个动作。

而连接终态失败（身份被拒）的第一反应就是清凭据 —— 多机之后那会把别的电脑一起删掉，
用户下次还得为一台电脑重新扫码全部。

## Decision

### 1. 键的形状：`dsh.pairing.<hostId>.<field>` + `dsh.pairing.active`

`hostId` = 那台电脑的 Ed25519 公钥（`pcSignPubHex`，配对时钉死、不可改）。
配对第二台是**新增一个槽**，第一台的键一个不动；`active` 记住当前那台。
端点表与路由记忆（`endpoints` / `endpoint_meta`）也在槽里：它们回答的是"怎么拨到这台"，
换电脑不该混用（第 1 步已让端点 id 带归属，这里把存储也分开）。

### 2. 写：完整槽在前，`active` 最后

`save(credentials)` 先写这个 `hostId` 的所有字段，最后才把 `active` 指向它。
崩在中途时半个槽永远不会被选中（`active` 还指着上一台，或不存在）——
这与"半份凭据比没有更糟"是同一条。

`saveEndpoints` / `saveEndpointMeta` 变成 `required hostId`：它们只写**那一台**的槽。
装配层（`main.dart`）用当前凭据的 `pcSignPubHex` 定位，不存在"从 storage 反查当前"
的第二次真值。

### 3. 读：`load({hostId})`，不给就读 `active`；必填缺一个回 null

给 `hostId` 是为了"切回另一台"与用例读指定槽，它**不改变 `active`**。
槽里必填字段缺一个就回 `null` —— 与升级前同一条（缺 `pairingId` 算不出 master，
缺 `deviceToken` 换不到票，部分可用会把失败推到很后面）。

### 4. 迁移：首次读取时搬旧平铺键，一次性、槽优先

判据是"旧键在、且这一台还没有槽"。旧数据只可能属于这一份凭据的那台电脑
（`dsh.pc_sign_pub` 就是它的公钥），所以读的那一刻就是唯一正确的归属点。

- 逐字段搬；**槽里已有的字段不覆盖**（半迁移时以槽为准）；
- `active` 最后写；
- 搬完逐个删旧键 ⇒ 第二次 `load()` **一次写都不产生**（判据是写次数）。

### 5. 清：`clear()` 删这一台，`clearAll()` 撤销全部

- `clear({hostId})`：现扫前缀 `dsh.pairing.<hostId>.` 删键（将来加字段不会漏删）；
  删的是**当前那台**时顺手清 `active`，**不自动激活另一台**。
  "谁接管"是用户决定（决策 9），自动挑一台会变成"手机自己换了个电脑"。
- `clearAll()`：`deleteAll()`，给"撤销所有配对"。
- 调用点分工：连接终态失败 → `clear()`（只清被拒的那台）；设置页"清除配对" →
  `clearAll()`。

### 6. 测试缝：`SecureStore` 接口 + `pairingStore` 单例

系统密钥库在纯 Dart 单测里没有实现（`MissingPluginException`），而"写次数"与
"槽隔离"正是这一步的判据。所以把本文件用到的四个操作收成 `SecureStore`
（`readAll` / `write` / `delete` / `deleteAll`），真实现是 `FlutterSecureStore`；
`pairingStore` 是装配层与真机用例共用的那一份，单测自己造内存实现。

### 同批修正：端点元数据 id 的判别看开头

第 1 步用"值里含不含 `://`"区分旧 id（裸 url）与新 id（`hostId|url`）。
**新 id 里也有 `://`** —— 于是每次 `save` 之后再 `load`，`remembered` 会被再补一次前缀
（`host|host|url`），症状是"记住的那条"永远匹配不上。判别改成**开头**：
`ws://` / `wss://` = 旧形状，否则原样保留。这一步的槽往返用例
（`app/test/pairing_store_test.dart`）第一次把它抓出来。

准入门槛（可机械判定，均已跑过）：

1. **两个槽互不影响**（准入门槛 1）：配对 A → 配对 B 后，`load(hostId: A)` 的
   `deviceToken` / `masterSeed` / 端点表逐字未变，`active == B`
   （`app/test/pairing_store_test.dart` 的「配对 A → 配对 B」）。
2. **迁移幂等**（准入门槛 2）：旧平铺键 → `load()` 与原值逐字相等、旧键消失；
   第二次 `load()` 的写次数不变（同文件「旧平铺键 → 槽」）。
3. **半迁移槽优先**：槽里已有 `relay_url` 时不被旧键覆盖，旧键仍被清掉
   （同文件「新槽已有值时不覆盖」）。
4. **清只删这一台**：`clear(hostA)` 后 A 读不到、B 与 `active` 不动；
   `clear()` 删当前那台并清 `active`，不自动顶另一台；`clearAll()` 全空
   （同文件「清理」三组）。
5. **端点表按槽隔离**：给 A 写一条直连，B 读到的仍是它自己的种子端点（同文件）。
6. 既有门禁不变：`flutter test` 全绿；连接恢复的用例（清凭据 → 回配对页）
   仍走同一条缝（`app/test/connection_recovery_test.dart`）。

变异校验（一次性，条数写进提交）：
- `clear()` 改回 `deleteAll()` → 恰 2 红（「clear(hostA) 不动 B」与「clear() 不自动顶另一台」）；
- 迁移不删旧键 → 恰 2 红（迁移幂等 + 半迁移「旧键仍要清掉」）；
- id 判别改回"含 `://`" → 恰 3 红（配对 A→B、槽隔离、clear(hostA) 里那三处 `remembered` 比对）；
- `save` 把 `active` 放到最前 → 无对应用例（可见的只有崩溃窗口），属**未覆盖**，如实记在此。

## Alternatives considered

1. **继续用一套平铺键，另存 `dsh.active` 只记当前**
   - 最强的理由：改动最小，读路径完全不变，只多一个键。
   - 为何被否：平铺键只有一份 —— "配对 B"必然覆盖 A 的令牌与主种子，
     记个 active 只是让覆盖后的那份看起来像 B，A 再也回不来。
2. **加一个 `dsh.pairing.hosts` 索引键列出所有槽**
   - 最强的理由：切回时不用扫整份存储，一步拿到名下有哪些电脑。
   - 为何被否：索引与槽本身是同一个事实的两处表达，任一处漏写就会漂
     （症状是"槽在、切不回去"）。`readAll()` 已经能按前缀枚举槽，等切换那一步
     真要展示列表时再抽一个派生函数，不预存。
3. **`clear()` 删当前那台后自动激活另一台**
   - 最强的理由：用户不会卡在"没配对"的界面，名册里明明还有别的电脑。
   - 为何被否：那是替用户决定"用哪台"，与决策 9 明写的"宿主没有自动挑一台"冲突；
     自动切过去还会让界面从"未连接（原因）"跳到另一台的数据，
     正是要防的"在 A 的名字下面看 B 的数据"。
4. **保留 `clear()` = `deleteAll()`，另加 `clearSlot()`**
   - 最强的理由：名字不变，旧调用点零改动。
   - 为何被否：`clear()` 的调用点恰好是"身份被拒 → 清凭据"，那时只该清被拒的那台；
     保留 deleteAll 会让一台电脑的故障把其他电脑的配对一起删掉。
     反过来"撤销所有配对"是用户明确动作，叫 `clearAll()` 才说得清。
5. **继续用静态方法，加一个 `@visibleForTesting` 的全局存储槽位**
   - 最强的理由：call site 一个不用改（main 与四个真机用例）。
   - 为何被否：那是把可测性塞成全局状态，测试之间会互相污染；
     而 `PairingStore` 本身就是个薄适配器，实例化 + 一份 `pairingStore` 单例更直接。
6. **迁移放进离线脚本 / 数据迁移段**
   - 最强的理由：运行时没有两种形状的分支。
   - 为何被否：凭据在系统密钥库（不是 sqflite 的 `meta` 表），没有现成的迁移钩子；
     旧数据归属哪台电脑只有读凭据的人知道。

## Consequences

- 收益：配对第二台不再覆盖第一台；身份被拒只清被拒的那台；"忘掉这一台"与
  "撤销所有配对"第一次是两个动作。
- 收益：端点表与路由记忆跟着凭据走，切回某台时不必从一张混装的表里筛。
- 代价：`load()` 每次要 `readAll()`（安全存储没有前缀查询）；键名多一段，
  排错时手看存储要按 `dsh.pairing.<64 位公钥>.` 前缀找。
- 代价：`active` 被清后即使别的槽还在，`load()` 也回 `null`（界面显示未配对）——
  这是有意的（不自动挑）；切换那一步必须提供"选另一台"的入口，否则那些槽在 UI 上够不着。
- 代价：真机用例与 `main.dart` 的调用点从静态方法改成 `pairingStore.*`；
  `assembly_invariants_test` 的源码断言跟着换字符串（它守的是"清凭据前先抓快照"）。
- 未覆盖：`save` 的"active 最后写"只有崩溃窗口的意义，没有用例能稳定模拟
  （已在变异校验里如实标注）。
- 未覆盖：多槽的**展示与切换**（列出已配对电脑、手机侧改名、同名短码）——
  那是第 4 步的界面部分。
