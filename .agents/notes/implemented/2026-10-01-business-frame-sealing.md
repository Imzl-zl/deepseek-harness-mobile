# Agent Note: 控制帧也必须封箱 —— 未认证的 `fc` 不许驱动重放窗口

Status: implemented

## Problem

握手接上之后，通道能谈出密钥，却**一帧业务数据都发不出去**：`box` 从来没有被加解密过。
把这一层补上时，帧联合里的三处问题同时暴露出来：

1. `ping` / `pong` / `credit` / `persisted` **带 `fc` 却没有 `box`**。`fc` 出现在 AAD 里，
   也驱动接收方的重放窗口 —— 于是未认证的数字可以直接改对端状态：注入一帧
   `credit{fc: 10^9}` 就能把 `maxFc` 推高，此后**所有合法帧都被判成重放**（连接被自己人反复关闭）；
   `credit`（放宽发送窗口）与 `persisted`（允许裁剪增量缓冲）本身就是状态变更，不经认证即可伪造。
2. **箱的容器格式没有定义**。`seal()` 产出 `{ciphertextHex, tagHex}` 两个字段，而线上 `box` 是一个字符串 ——
   没有规定怎么拼。两端各写各的（一个 hex、一个 base64、一个加分隔符）在单侧测试里全是绿的，
   只有真机互通才断，症状是"解不开"。
3. **AEAD 认证失败没有协议错误码**：`crypto.open` 把 `node:crypto` 的
   `Unsupported state or unable to authenticate data` 原样抛出去，调用方按 `instanceof ProtocolError`
   分类时会把它当成"未知内部错误"，而 §3.1 的封闭错误码里它应当是 `protocol/bad-frame`。

## Decision

- **除握手三帧与 `presence` 外，每一种帧都带 `box`**，控制帧封的是空载荷。
  封箱在这里买到的不是保密而是**认证**：`fc` 因此被绑进 AAD，"改状态的控制帧"也变成不可伪造。
- **箱 = `base64url(密文 ‖ tag)`，无填充**；长度由总长减 16 得出，不需要分隔符。
- **重放窗口只在认证通过后推进**（先验后进）；`fc` 不单调的重放预检只读不写。
- **封箱是连接层出帧/收帧路径上的单一收口**：`write()` 里"分配 `fc`"与"用这个 `fc` 封箱"紧挨着；
  `handleFrame()` 里"过握手门禁"与"解箱"紧挨着。上层看到的 `box` **永远是明文载荷**。
- **`secure` 把「握手」与「密码器」绑成一个对象**：配了就必须有密码器，也就没有"握手过了但帧是明文"的连接；
  不配 `secure` 的连接是**明文通道模式**（测试与 fixtures 词汇层用它，那里 `box` 是可逆占位）。
  配了 `secure` 却拿不出密码器时**宁可不发**，也不明文上线。

准入门槛（可机械判定）：

1. `needsBox(t)` 是"该不该封箱"的唯一判据；`hasBox(frame)` 是"字段在不在"的唯一判据，
   两者不一致时**抛错**而不是静默发出去。
2. 握手成功后第一帧业务帧的 `fc` 仍是 0（握手帧不占计数器）；同一 `fc` 想封第二次直接抛。
3. 伪造的 `fc`（认证不过）之后，紧跟着的合法帧必须照常解开 —— 这直接检验"先验后进"。
4. 跨端向量里每条 AEAD 用例都带 `box`，两端各拼一遍再比对。

## Alternatives considered

1. 只给数据帧封箱，控制帧保持明文
   - 最强的理由：省掉每个控制帧 16 字节标签与一次加解密，心跳与逐帧 `credit` 的开销归零；
     而且这几个帧"没有内容"，看不出有什么可保密的。
   - 为何被否：它们的**元数据**有权威 —— `fc` 驱动重放窗口，`credit` 与 `persisted` 改对端状态。
     QUIC（RFC 9000）里除 Initial/Retry 外所有包都受 AEAD 保护、ACK 帧在保护包内，TLS 1.3 同理；
     成熟协议没有"握手后的明文控制帧"这一档。
2. 让中继单独对控制帧做认证（连接级 MAC）
   - 最强的理由：不动载荷格式，客户端实现最省事。
   - 为何被否：那要求中继持有密钥，而中继的全部设计前提是**哑转发、对内容盲**（I10）。
     为了认证几个控制字段把密钥交给中继，等于用一个小问题换掉整个威胁模型。
3. 箱用十六进制
   - 最强的理由：与向量里的 `ciphertext` / `tag` 字段直接对应，两端都不需要 base64 库。
   - 为何被否：十六进制把载荷体积翻倍，而 8 MiB 单帧上限是按**编码后的行**算的 ——
     翻倍等于把可用载荷预算砍半（§5.3 的 1 MiB refetch 阈值随之失真）。
4. 封箱放在连接层之上（独立的 `SecureSession` 装饰器）
   - 最强的理由：`connection.ts` 保持"只管 socket 与定时器"，密码学独立成层更好测。
   - 为何被否：`fc` 由连接层分配、又正是 nonce 的来源。"分配"与"封箱"分处两层，迟早出现
     两者不一致或同一 `fc` 封两次 —— 而重用 nonce **直接破掉 AEAD**，属于不可挽回的一类错。
     契约 §4 本来就把"握手、密钥、计数器、流控"划给连接层，这一层是它的一部分。
5. 重放窗口要求"恰好 +1"（更严）
   - 最强的理由：任何丢帧都会立刻暴露，而不是被"严格大于"悄悄放过。
   - 为何被否：两个方向各有独立计数器，而"严格大于"同样拦得住重放；更严的版本会把
     将来任何一次有意的跳号（比如按优先级裁帧）变成断连，代价与收益不成比例。

## Consequences

- 收益：通道终于能收发业务帧，且**两侧各写一遍实现**能对上（手机侧替身直接拿 `node:crypto`
  拼 nonce 与 AAD、自己拼 base64url 容器，不 import 产品的 `box.ts`）；
  重放、篡改、缺 `box` 三种形状各自有关连接的错误码可断言。
- 代价：每个控制帧多 16 字节标签与一次加解密；箱的容器格式成为又一处跨端约定（已进向量）；
  `secure` 把两个配置绑成一个（想只配一半会编译不过）。
- 顺带修掉的漂移：AEAD 失败现在转成 `protocol/bad-frame`（原来漏的是 `node:crypto` 裸错误）；
  `HANDSHAKE_FRAME_TYPES` 收敛到协议层一处（之前 `frame.ts` / `codec.ts` 各有一份判据）。
- **尚未做的**：`credit` 的流控窗口（W=128）还没有接到发送路径上，方法面 22 个 handler 仍是
  `connector/unsupported` —— 也就是说业务帧的**通道**通了，**内容**还没有。文档与 `memory.md` 都如实这么写。
