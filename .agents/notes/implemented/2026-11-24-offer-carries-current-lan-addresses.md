# Agent Note: 出码地址 = 此刻枚举到的全部局域网 IPv4（不再猜一条）

Status: implemented

## Problem

用户 2026-11-24（手机连着却一直报「连接不上」，电脑开着代理 TUN）：

> 出码不应该出当前网络的地址和端口，怎么从现有的凭证中出，然后连不上就报错？
> 你出码一般就是第一次链接肯定没有啊？你要是有复用没问题，但是你不应该出码就是当前的吗？
> 我怎么看报错连不上啥的？？
> ……我只需要局域网地址就行吧，什么网卡，虚拟网卡啥的，用不上吧？

三件事其实是同一条判据的三次变形：

1. **地址是旧快照**。`listener.urls` 在监听面启动那一刻枚举一次 `os.networkInterfaces()`
   就冻住（`connector/src/transport/listener.ts` 的 `startListener`），出码前只刷新
   `lanHint` 这个标量、不重枚举网卡（`connector/src/index.ts` 的 `offerPairing`）。
   换 WiFi / DHCP 换段之后，码里写的还是旧 IP ⇒ 手机拨旧 IP ⇒ 红字「连接不上」。
2. **哪条进码是猜的**。2026-11-06 起"只报一条"，于是必须先回答"哪条对"：先按默认路由
   （2026-11-06），再按 MAC OUI 排除虚拟网卡（2026-11-20）。两次都猜错：TUN 抢走默认路由
   时上报 `198.18.0.1`，或者 hint 匹配不上时一条都不报（出码直接失败）。
3. **"能不能出码"挂在中转上**。中转那条腿要"控制面已连上 + 凭据里有令牌"，首次配对
   本来没有；两者都缺时 `planPairingOffer` 直接抛错 —— 用户看到的就是"连不上就报错"。

## Decision

**出码那一刻重枚举网卡，把此刻的全部局域网 IPv4（RFC1918 三段）原样写进码；电脑不再
替手机挑一条，也不再用网卡名 / MAC / 默认路由做判据。**

准入门槛（可机械判定）：

1. **成员集合只由地址段决定**：`endpoints.ts` 的 `autoAdvertisedUrls` 收 `isLanAddress`
   为真的全部候选（`10/8`、`172.16/12`、`192.168/16`），`hide` 删、`extra` 追加。
   TUN 的 `198.18/15`、CGNAT 的 `100.64/10`、IPv6、回环一律不进默认集合。
   改判据后 `tests/tun-default-route.test.ts` 必须红（那条用例钉的就是"全部局域网 IPv4"）。
2. **地址现取**：`Listener.urls` 是 getter，每次读都重新 `os.networkInterfaces()`；
   端口用**实际绑定**的那个（`server.address().port`），不是配置字面值。
   `tests/listener.test.ts` 用两份假枚举证明"同一台监听面的地址跟着枚举变"。
3. **默认路由只当排序**：`lanHint` 命中的那条排第一（手机先拨最可能通的），
   其余按 `192.168 → 172.16 → 10` 段序；**不参与成员判定**。
4. **中转是可选腿**：`relayAvailable = 控制面 connected`；登记失败且有 `lan` ⇒ 照出码并标
   `lanOnly`；没有 `lan` 才拒绝出码。拒绝的理由只有四档事实（监听未启动 / 没枚举到地址 /
   没有局域网 IPv4 / 被 `hide` 删空），由 `noLanAddressReason` 一处给出。
5. **面板能肉眼核对**：`/connection` 的 `direct` 带 `lanUrls`（与出码同一份判据），
   出码卡显示「此刻可拨：ws://192.168.x.x:8790」。

## Alternatives considered

1. **保留"只报一条"，把判据换成"地址段 + 去掉明显拨不通的网段"**
   - 最强的理由：手机端点列表干净，一条就够（2026-11-06 用户原话："能用的就是主机的 IP
     地址吧？这不是多余？"）；出码文案也短。
   - 为何被否：只报一条就必然要回答"哪条对"，而**哪条对只有手机知道**（AP 隔离、
     双网卡、VMware host-only 都存在）。这条判据在 2026-11-06 / 11-20 / 11-24 三次
     真机上都猜错过，每次的错法都是"码里地址拨不通"或"明明有局域网却说没有"。
     列表干净的问题在展示层解决（配对成功后端点表只留拨通那条 + 中转），不该让
     出码去猜。
2. **出码时让电脑自己拨一遍自己报的地址，只留下拨得通的**
   - 最强的理由：电脑侧实测最接近"手机能不能拨通"，能直接删掉死地址。
   - 为何被否：本机回环拨自己**必然成功**（listen 在 0.0.0.0 上），证明不了任何事；
     要真的从外部视角拨，得借第二台机器 —— 那是手机本来就会做的事。
     代价（每条地址一次超时）与收益（省一条候选）不成比例。
3. **把局域网地址放进持久化配置，出码读配置**
   - 最强的理由：一次配置长期用，出码路径最短。
   - 为何被否：配置是"上次填的"，不是"此刻的"。用户报的就是这件事：
     「怎么从现有的凭证中出」。地址会变，判据必须读现况。
4. **继续用 MAC OUI 判虚拟网卡**
   - 最强的理由：VMware / TUN 的 MAC 前缀确实是分配事实，比猜网卡名可靠。
   - 为何被否：它解决的是"列表里多一条"，代价是把"地址段"这一条事实变成两条判据，
     而且在 TUN 抢默认路由时仍要配合"默认路由"来用 —— 两次事故都出在组合上。
     把虚拟网卡的 `192.168.x.1` 报出去只会让手机多拨一条；把它藏起来则可能藏掉
     用户真正在用的那条（Hyper-V 外部交换机就是 `00:15:5d`）。

## Consequences

- 收益：出码不再依赖任何"上次的状态"（网卡快照、默认路由、配置里的地址）；
  首次配对在没有中转、没有令牌、开着 TUN 的机器上照样出码。
  `isVirtualMac` 与 `defaultDirectUrls` 整段删除，判据从两处（地址段 + MAC）收成一处。
- 代价：码里的 `lan` 从 1 条变成 2–4 条（VMware host-only、双网卡），端点表里也会多几条。
  手机侧已有的两道机制吸收这个代价，不需要电脑侧挑：拨号是 Happy Eyeballs（
  `app/lib/core/endpoint_transport.dart`：错开 250 ms、单条 3 s / 10 s、总预算 15 s，
  `totalBudget` 到点给结论），端点表对"从没成功过且这次拨过失败"的条目剪枝、
  另有 12 条上限保险丝（`app/lib/data/endpoint_book.dart` 的 `_boundedByCap`）。
  配对阶段则是**并行拨**、先通先用（`app/lib/core/pairing_flow.dart`）。
- 代价：`lanHint` 仍是内核选路的结果（`lan-address.ts`），只用于排序。它不精确时
  顺序会不理想，但不再改变"报哪几条"。
- 被取代：`.agents/notes/archived/2026-11-20-advertise-by-address-not-by-default-route.md`
  与 `.agents/notes/archived/2026-11-06-default-advertise-main-ip.md`。它们"只报一条"
  的结论不再成立；"判据看地址段、不看默认路由"这半条仍然成立，并被本篇保留。
