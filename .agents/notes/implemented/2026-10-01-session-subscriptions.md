# Agent Note: 会话订阅 —— 抽出共享骨架，快照必须逐条补课

Status: implemented（`session.subscribe` / `session.unsubscribe`；`session.page` 与 `persisted` 水位见"仍未做"）

## Problem

任务输出订阅做完之后，会话订阅是同一类东西：一条上游流 + 逐帧转发 + 背压 + 终止 + 跟连接活。
如果照抄一份 `job-subscriptions.ts`，那套**最难的机制**（满窗压一帧、承诺必兑现、
收尾只清自己那一格、终止只靠 abort）就会有第二份实现 —— 而它们全是"写错不会报错、
只在真机上偶发"的类型。所以先抽骨架，再接会话面。

会话面自己还有四处必须定清楚：

1. **开启帧怎么发？** 宿主的第一帧是 `snapshot`，带 `cursor`（包含式日志切点）、
   `records`（补课事件）、`hasMore`。
2. **`live` 的 `stream` 从哪来？** 契约术语表说它是「**电脑侧分配**的、会话内单调的流 id」，
   而宿主的帧里带的是 `attemptId`（不透明字符串）。
3. **`live` 的 `rev` 用什么？** 手机侧的读法是 `rev == last + 1` 追加、**跳跃即丢流**。
4. **中断时补不补一帧 `error`？** 任务输出那边补了（ring 会淘汰，沉默等于骗人）。

## Decision

- **抽出 `subscriptions.ts`**：键、开流、帧展开、起点、终止帧、收尾帧全部由调用方给，
  骨架只负责机制。任务输出与会话订阅各自变成薄薄一层。
- **开启快照的 `records` 逐条展开成 `ev`**（一条上游帧 → N 条出站帧，所以骨架的
  `outOf` 返回数组），并把 `{ since: cursor, hasMore }` 作为 `subscribe` 的应答 ——
  手机据此重订与决定要不要 `session.page`。
- **`stream` 由电脑侧分配**：`attemptId → number` 的映射，**只增不减**
  （手机判据是"号变大 ⇒ 换流"，回收旧号会让新尝试接进旧累加器）。
- **`rev` 用宿主的 `index`**：`chunk` 帧自带尝试内递增的块号，正好满足"+1"，
  不必自己造修订号（契约 §5.1：修订号是 DSH 的，插件不分配）。
- **中断不补 `error` 帧**（与任务输出刻意相反）：会话内容一定还有**持久副本**，
  手机按 `since` 重订一次就补回来了（§5.1 的恢复语义）；而任务输出的 ring 会淘汰，
  沉默等于骗人。**判断依据是"这份内容还能不能重新拿到"**，不是"哪边更省事"。

准入门槛（可机械判定）：

1. 快照的补课事件**条数与序号**都对（少一条就是恢复时丢一条事件；单测 + e2e 各一条）。
2. 换尝试必须换 `stream` 号（只增不减）。
3. `rev` 在同一尝试内 +1 递增。
4. 中断时**不产生**任何新帧，且条目清掉。
5. 重复订阅幂等；`since` 不同则先终止旧的再起新的。

## Alternatives considered

1. 复制一份任务输出的订阅实现
   - 最强的理由：两边的"键/终止帧/展开"都不一样，硬抽一层多一次间接；而且任务输出那份刚写好、
     有测试，复制过去立刻能用。
   - 为何被否：复制的是**机制**而不是业务 —— 背压、承诺兑现、收尾判据、终止机制四处都要抄对，
     而它们正是"写错不报错"的那类。抽骨架后两边的差异只剩四行判据，机制只有一处。
2. 把宿主的 `assistant-stream` 帧**原样**转发（把 `attemptId` 当 `stream`）
   - 最强的理由：零映射，宿主加字段也不用改我们。
   - 为何被否：契约明说 `stream` 是**电脑侧分配的数字**且会话内单调，而 `attemptId` 是不透明字符串；
     更要紧的是手机的判据是"号变大 ⇒ 换流"，字符串 ID 之间没有大小关系，换尝试时它就判断不出来。
3. `rev` 用宿主的 `revision`
   - 最强的理由：那是宿主自己的"修订号"，语义最正。
   - 为何被否：`revision` 是**尝试级**的，同一尝试内的多个 `chunk` 共用一个值 ——
     手机侧看到 `rev` 不变就会当成重复帧丢弃（或按跳跃丢流）。`index` 才是块内递增的那个数。
4. 每次订阅从 1 开始分配 `stream`
   - 最强的理由：号段短、看日志方便。
   - 为何被否：手机重订后看到号**变小**，会把新尝试当回旧流（"号变大才换流"）——
     表现是流式文本接到上一段后面。所以计数器跨订阅保留。

## Consequences

- 收益：会话订阅通了（`ev` + `live`），并且**两条订阅流共用一套机制**；
  抽骨架时原有测试**保住了行为**（199 项一条不改地绿），其中一条还抓到重构中的语义合并：
  我一开始把"宿主抛错"与"有序结束却没终止帧"合并成同一条 tail 帧，
  而两者给手机显示的话不一样 —— 于是骨架加了 `onError`，与 `onEndWithoutTerminal` 分开。
- 代价：骨架比两份专用实现多一层间接（`outOf` 返回数组、`reuse` 谓词）；
  `session.page` 还没接，所以"补课事件 + 翻页"里只走通了前一半。
- **仍未做的两件，按顺序**：
  1. **`persisted` 水位的来源尚未查清**（手机侧的"水位已对齐"依赖它）。已核实的事实：
     `SessionPersistenceSnapshot` 只有**不透明** `revision` 与可选的 `eventCount` / `sizeBytes`
     （`packages/session/session-persistence/src/index.ts:50-59`），**没有 seq 水位**；
     而 session store 的约定是"持久化是插件的事：订阅 `session/event`、在 `session/flush` 上 drain"
     （`packages/core/session/src/index.ts:3-4,82-86`）。所以它是独立一块，需要先查清
     `session/flush` 与 `eventCount` 能不能给出可信水位 —— **不许猜**。
  2. `session.page`（用开启帧的 `cursor` 当 `throughSeq`，大结果走 `chunk`）。
