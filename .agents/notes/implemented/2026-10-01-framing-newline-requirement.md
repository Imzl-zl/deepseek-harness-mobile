# Agent Note: 行级分帧的换行要求 —— 从"查了一轮"到"写进规格"

Status: implemented（`docs/subsystems/remote-channel.md` §3 与 `docs/subsystems/app-channel-client.md` §2 各加一条）

## Problem

第 45 轮排查三方链路时，根因是**测试侧漏了帧尾的 `\n`**：协议是行级分帧，连接器的出帧会补
`encodeFrame` 的换行，而我让设备替身直接 `ws.send(JSON.stringify(frame))` ——
分帧器于是把那一行当作"还没结束的一行"永远攒着，`onFrame` 永不触发。

那次排查先怀疑并逐个排除了：中转的归属表、连接层的攒批器、socket 写出、重放守卫。
**症状的特征是"两侧看起来都正常、对端什么都没收到"** —— 中转日志说已转发、连接器状态正常、
连接也是通的。这三种"正常"叠在一起，让人很难想到"标点"。

而契约 §3 只写了"行级 UTF-8 JSON"——**"行级"隐含了换行，但没有明说**。
手机端（Dart）实现要照着这套规格写，如果作者对"行级"的理解与连接器不一致
（比如按 WebSocket 消息边界分帧），就会在真机上重演同一轮排查。

## Decision

把这条要求写成**显式的当下事实**（不是变迁叙述 —— 那属于笔记）：

- `docs/subsystems/remote-channel.md` §3：行级 UTF-8 JSON 那句后面补
  「**每帧以 `\n` 结尾**：分帧器只在读到换行时交出一帧，漏掉它的表现是「两侧都正常、
  对端什么都没收到」」。
- `docs/subsystems/app-channel-client.md` §2 开头：同一条要求 + **Dart 侧要落在唯一的出帧口**
  （`encodeFrame`）而不是让每个调用点各自记得。

写"表现"而不只写"规则"，是因为规格的读者将来会在**症状**里找答案：他遇到"对端什么都没收到"
时，不一定会回头读 §3 的那一行。

## Alternatives considered

1. 只在 `.agents/notes/` 里记（不碰 `docs/`）
   - 最强的理由：这是实现细节，规格里那句"行级"已经够了。
   - 为何被否：手机端是**另一个作者、另一种语言**（Dart）按规格实现 —— 规格没写死的地方
     就是两端理解分叉的地方，而分叉的症状要到真机才出现（第 45 轮已经付过一次这个成本）。
2. 在 `encodeFrame` 的文档注释里写（不碰 `docs/`）
   - 最强的理由：离代码近，改代码的人一定看得到。
   - 为何被否：Dart 侧还没有 `encodeFrame`（手机端尚未落地），规格才是它唯一的输入。
3. 把"漏换行"变成协议层的显式错误（例如收到不含 `\n` 的数据就关连接）
   - 最强的理由：把静默攒着变成大声失败。
   - 为何被否：**做不到**——分帧器看到的是一段字节流，它无法区分"这条消息还没结束"
     与"对端忘了换行"（这正是行级分帧的代价）。既然无法检测，就只能写进规格。

## Consequences

- 收益：两端对"行"的定义写在规格里；手机端实现时有一个明确的落点（唯一出帧口）。
- 代价：两份 `docs/` 各多一句话（`docs/AGENTS.md` 的字数预算内）。
- **仍未做**：三方路径剩下的两段（握手在配对之后成功、`session.prompt` 经中转往返）。
