# Agent Note: 会话翻页与单条目补取 —— 一对不能拆开做的东西

Status: implemented（`session.page` / `session.refetch`）

## Problem

手机要能往上翻历史。契约 §5.3 把这件事和另一条规定绑在一起：

> 单个条目的封箱后字节 > **1 MiB**：不推内容,推 `refetch { itemId }`,由手机按需拉取(同一方法复用)。

于是 `session.page` 与 `session.refetch` **是一对**：没有翻页就没有标记，没有补取标记就是死信。
而 DSH 侧两条事实决定了实现形状：

- `page` 是**消息对齐**的（"cold-safe, message-aligned Session history page"），
  返回 `{ records, hasMore }`；
- `throughSeq` 的语义被写死在类型注释里：**"Inclusive log cut obtained from the corresponding
  follow opening frame"** —— 它必须来自开启帧。

## Decision

- **水位只认开启帧**：订阅面把每次开启帧的 `cursor` 缓存起来（`cursorOf`），
  **退订之后仍然记着** —— 手机收起面板、或断线重连之前想翻历史时，用稍旧的切点翻更早的历史是安全的
  （只会少算新事件，不会算错旧事件）。拿不到水位就回 **`session/window-missed`**
  （§3.1 给它的客户端行为正是「走快照刷新」），**绝不猜一个切点**：猜出来的会让手机拿到
  "看起来对、其实少一段"的历史，而那种错没有任何症状。
- **超过 1 MiB 的条目换成 `{ kind:'refetch', seq, bytes }`**：`seq` 是补取的凭据，
  `bytes` 让手机能显示"这条很大"。阈值可注入（测试不必真造 1 MiB 载荷）。
- **补取回来的东西仍然超过 8 MiB 单帧硬上限时回 `internal`**：手机明确要这条，
  但发出去会被对端按 `protocol/bad-frame` 关连接（§3 的规则是"发送侧**不得发出**"）。
  制造一次必然的断连比一个错误坏得多。
- 两个参数（`beforeSeq` / `maxMessages`）与 `seq` 统一按**非负整数**校验：
  它们都是下标或条数，接受不合法值只会让它一路走到 DSH 里再以更难懂的方式失败。

准入门槛（可机械判定）：

1. 没水位 → `session/window-missed`，且**根本不读盘**（读了也是白读）。
2. 超过阈值的条目变成 `refetch`，且标记带 `seq` 与真实字节数。
3. 补取按 `seq` 对齐到它所在的消息（`beforeSeq = seq + 1`、`maxMessages = 1`），
   且切点取"水位与 `seq` 的较大者"（不能超过水位）。
4. 补取仍超硬上限 → `internal`；取不到 → `session/not-found`。

## Alternatives considered

1. 只做 `session.page`，不做 `refetch`（先放着）
   - 最强的理由：翻页是用户看得见的功能，补取只在超大条目才用得上；分两轮更小步。
   - 为何被否：那就必须**关掉**阈值替换，否则手机收到一个点不动的标记；
     而关掉替换意味着大图（base64 内联在 `assistant/message` 里）会把一帧撑到硬上限，
     对端收到就关连接。**两者要么一起做，要么都不做** —— 没有"只做一半还正确"的形态。
2. 没有水位时自己开一条 `follow` 取一个
   - 最强的理由：让 `session.page` 独立可用（手机不订阅也能翻历史），少一个错误路径。
   - 为何被否：那是"为了少一个错误码，多一次宿主流的开关"。而错误码本身是**有出路的**
     （`session/window-missed` → 手机重新订阅 → 拿到快照与水位 → 再翻就正常），
     也就是这条路径并不需要新的机制。真机上如果发现"翻历史前从不订阅"，再改不迟 ——
     而那时改的判据会更清楚。
3. 阈值/上限写成常量，不留注入点
   - 最强的理由：契约就是这两个数，注入点看着像过度设计。
   - 为何被否：测试要造 1 MiB 载荷才能覆盖这条分支，而 8 MiB 那条根本造不动。
     注入点让两条边界都能被真实断言（不是因为"将来可能改"，而是因为**今天要测**）。

## Consequences

- 收益：手机能往上翻历史，且大条目有明确出路（标记 + 按需补取）；
  水位来源与契约一致（开启帧），翻页不会自己造切点。
- 代价：订阅面多了一张 `sid → 水位` 的缓存（进程内、随会话数增长，可忽略）；
  `session.refetch` 每次都要读一次盘（`page` 一次），没有缓存 —— 大条目本来就是低频的。
- **仍未做 / 需在手机端落地时确认的**：
  1. 翻页结果的**分片**：一页里若有多条接近 1 MiB 的条目，整帧仍可能超过 8 MiB。
     目前只按"单条目"替换，没有按"整帧总量"再兜一层。真机上如果一页能撞到，
     要补的是**整页预算**（例如累计到 4 MiB 就提前结束并置 `hasMore`）。
  2. `session.prompt` 等带键的写方法；配对流程（§12.1）。
