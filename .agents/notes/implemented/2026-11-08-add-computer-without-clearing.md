# 加一台电脑不改动用当前那台

- 日期：2026-11-08
- 触发：用户问「一个手机连多台、随时切换，这不是需要吗」，核下来能力早在、入口没有
- 状态：implemented

## 背景

N:M 的能力面早就齐了：`PairingStore` 按 `pcSignPubHex` 分槽（`save()` 只写自己那一槽，最后才写 `active`）、`HostSessions` 每台一份池化模型、`_switchTo` 只换凭据槽与可见指针，`docs/subsystems/app-channel-client.md` §6.4 把这三条写成了定案。

缺的是**入口**：已配对时能到达连接 sheet 的三个入口（顶栏状态点、空态出路、抽屉连接行）全都指向 `onRePair → _repair`，而 `_repair` 走的是 `ConnectionRecovery.repair()`，第一步就是 `pairingStore.clear()`（删当前那一槽）。于是"加第二台"的实际后果是先丢掉第一台 —— 一台手机永远只记得一台电脑，池化与「切换电脑」那一行在生产里没有机会被用到。

## 决定

1. 连接 sheet 增加一行 **「添加电脑」**，副标题写明「再配一台；现在这台保留」，紧贴在「重新配对（换一台电脑）」上面（两行后果相反，摆在一起靠副标题区分）。
2. 它的回调就是装配层已有的 `_openPairing` —— 与"没配对时的连电脑"是同一个动作：只把配对页推到前面，**不动凭据、不动池子**。取消时 `_pairing = false`，什么都没发生过。
3. 只有已配对时给这一行（`onAddHost: widget.paired ? … : null`）；没配对时"添加"与"连电脑"同义，多一行只是多一次辨认。
4. 配对成功那一步把"进这一趟之前是哪台"记进 `_previousHostId`（`_switchTo` 同一个指针），所以加完立刻有「切回上一台」。

## Alternatives considered

1. **在装配层再加一条 `onAddHost` 缝（新动作，明确"不清凭据"）**。最强理由：名字与后果一一对应，读代码的人不会怀疑"连电脑"会不会顺手清掉别的东西。否掉：装配层本来就只有一个进配对页的动作（`_openPairing`），它不清凭据是既有事实；再开一条只差"清不清槽"的缝，等于让两条路各自演化，而这类漂移的代价是用户丢凭据。页面侧用 `paired` 决定文案，装配侧只留一个动作。
2. **把「重新配对」改成不清凭据，两行合并成一行**。最强理由：少一行、少一个概念，用户不必分辨两条路的区别。否掉：「重新配对」还要服务"身份被拒"和"同一台换密钥"这两种情况，那两条必须清槽（旧 token 会把新的设备行顶掉）。合并就得在这一行内部判"是同一台还是另一台"，判据从用户意图退化成猜测 —— 而猜错的后果是拿作废凭据去连（症状：配上了、一直连不上）。
3. **入口只放设置页**。最强理由：低频动作不该占连接操作 sheet 的位置。否掉：用户想加一台时手里的就是那个 sheet，"任何状态 ≤2 步走到连接动作"是既定判据；挪进设置要 3 步，而且设置页回答的是"怎么连"，不是"连哪台"。
4. **不支持添加，只允许一台**。最强理由：少掉一整类跨台状态（分桶、通知前缀、前台服务按"还有没有人在要"起停都是为多台付的成本）。否掉：与 §6.4 的 N:M 基线冲突，且那些成本已经付过；砍掉能力不会让成本消失，只会让已有机制没有入口。

## Consequences

- 收益：加第二台不再丢第一台；加完能一步切回；两行的区别写在副标题上，不靠用户记住上次的后果。
- 代价：连接 sheet 又多一行（底部形态本来就可滚动，锚定形态的最大高度是 0.8）；`_previousHostId` 现在由 `_switchTo` 与 `_onPaired` 两处写，语义仍是"最近一次离开的那台"，同一台重新配对时不写（否则会把更早的指针冲掉）。
- 已知边界：**添加途中取消不需要回滚** —— `_openPairing` 全程没碰凭据与池子，`_closePairing` 只翻一个 bool。「添加电脑」不设台数上限：电脑侧裁剪的判据是"这一轮在服务的设备"，手机同时配几台不改变它。
