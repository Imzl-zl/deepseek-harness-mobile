# Agent Note: 三端的可移植性上限决定加密与本地库选型,且三端都不做后台长连接

Status: proposed

## Problem

方案 §3 只写了"一套 Dart 代码覆盖三端",没有写三端各自的能力上限。后来者据此会默认"桌面与安卓能做的事,iOS 和鸿蒙也能做",于是:选 libsodium 做端到端加密(鸿蒙编不出原生库)、选 drift + sqlite3 存增量事件(鸿蒙无适配)、把"后台保活"当成可靠性手段(三个平台各自封死),然后在真机联调阶段成片返工——而这时协议、存储格式和密钥方案都已经写进代码了。

## Decision

以**鸿蒙可用性**作为原生依赖的选型闸门,并以**三端都不做后台长连接**为默认。

准入门槛(可机械判定):

1. 任何引入的原生依赖必须在鸿蒙三方库适配清单里有明确条目,且覆盖我们锁定的版本线;没有条目就不引入(纯 Dart 包不受此限)。
2. 设备私钥在 iOS / Android / 鸿蒙三端都必须落在系统密钥库;鸿蒙上找不到满足条件的现成包时**自写 platform channel 接 HUKS**,不得退回"把密钥写进 preferences"的方案。
3. 三端都不得以"后台维持长连接"作为通知送达或状态正确性的手段:通知走系统推送,正确性走回前台补课。
4. 手机侧本地库三端同源:同一套 schema 与同一套迁移脚本,不允许按平台分叉存储格式。

## Alternatives considered

1. libsodium / `sodium`(原 `sodium_libs`)做端到端加密
   - 最强的理由:libsodium 是事实标准,API 稳定、常量时间实现久经审计,不需要我们自己对曲线与 AEAD 的细节负责。
   - 为何被否:它自 v4 起改为依赖 Dart build hooks 现场编译原生库,官方支持平台不含 ohos、鸿蒙适配清单里也没有条目;而纯 Dart 的 `cryptography` 同时提供 X25519 与 XChaCha20-Poly1305,并在适配清单里四条版本线全绿。留档:若 Dart build hooks 在 OHOS 落地,可以重新评估。
2. drift + sqlite3 3.x 作为本地库
   - 最强的理由:类型安全的查询、代码生成、成熟的迁移机制,长期维护成本最低,团队也最熟悉。
   - 为何被否:drift 官方 `NativeDatabase` 的平台表不含 ohos,`sqlite3` 在鸿蒙清单里是"适配中",`sqlite3_flutter_libs` 已 EOL → 三端同期交付没有背书。改用 sqflite(四条线全绿),代价是失去类型安全与代码生成,手写 schema、SQL 与迁移。
3. 安卓前台服务 / 鸿蒙长时任务做后台保活
   - 最强的理由:不依赖任何第三方推送账号,数据不经过厂商通道,后台也能即时收到事件,体验上限最高。
   - 为何被否:安卓自 Android 15 起 `dataSync` 有 24 小时内累计 6 小时硬上限且类型表里没有"长连接";iOS 官方明确后台不获得额外执行时间;鸿蒙长时任务同样没有通用长连接类型,且 `DATA_TRANSFER` 要求真实进度、10 分钟无更新即取消,类型与业务不一致会被系统挂起或终止。三端一致地做不到,不值得为它写三套平台代码。
4. SQLCipher 加密本地数据库
   - 最强的理由:静态加密由数据库层保证,数据库文件被单独拷走也读不出内容。
   - 为何被否:与第 2 条同因(鸿蒙无适配)。改为依赖系统级文件加密(三端在设置锁屏口令后默认开启)+ 敏感字段应用层加密 + 私钥进系统密钥库。

## Consequences

- 收益:选型闸门可机械判定("清单里有没有这条 + 覆不覆盖我们锁的版本线"),把"iOS/安卓能跑、鸿蒙编不出"这类返工提前到选型阶段;三端行为一致(都没有后台长连接),不需要为某个平台单独写可靠性逻辑。
- 代价:放弃了 libsodium 与 drift 的成熟度,本地库要自己写 schema、SQL 与迁移;推送必须在三个平台各接一套(iOS APNs、安卓厂商通道、鸿蒙 Push Kit 或极光的 ohos 适配),而"常驻后台即时收事件"这个体验上限永远拿不到——用户离开 App 后只能靠系统推送。
