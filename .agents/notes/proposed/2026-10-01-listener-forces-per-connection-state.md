# Agent Note: 监听面撬动的是"每连接状态"——两个必须先定的事实

Status: proposed（`attach(socket)` 已就绪；监听面本身**还没写**，因为它的前置不是代码量而是两个决定）

## 事实一：`ws` 目前只在 devDependencies

`connector/package.json` 里 `ws`（与 `@types/ws`）在 **devDependencies**：它现在只服务测试
（`tests/support/peer.ts` 起测试用服务器）。而 Node 22 的全局 `WebSocket` **只有客户端**，
没有服务端实现 —— 所以"接受连接"这条路要么把 `ws` 提到运行时依赖，要么自己实现 WS 握手与分帧
（后者不必讨论）。

这不是一个小抄近路的问题：**它给插件引入第一个运行时依赖**。要么接受它（`ws` 是纯 JS、事实标准、
无原生依赖），要么改成"只在测试/开发模式下启用监听"（那真机直连就不是产品能力）。**需要定夺。**

## 事实二：`connection` 是**单槽**，而且各层闭包都捕获了它

`index.ts` 里 `connection = next`（`:481`）只有一处，而 `start-transport` 里**一次性**构造了这些：

| 构造物 | 它怎么用到连接 |
|---|---|
| 方法面（`methodFace`） | 应答走 `next.send(...)`（闭包捕获 `next`） |
| 任务输出订阅 | `send: (sid, output) => next.send({t:'job'...})`、`waitWritable: () => next.whenWritable('job')` |
| 会话订阅 + 增量缓冲 | 同上（`ev` / `live`） |
| 配对端点 | `reply: (...) => next.sendPairingFrame(...)` |
| 状态回调 | `onFrame` / `onStateChange` / `onEstablished` 都是**这一条**连接的 |

于是**监听面 accept 第 N 条 socket 时，这些构造物全都指向第 1 条连接** ——
症状会很怪："第二台手机连上了、也握手成功了，但它收不到任何事件"（事件都在往第一条连接发）。
而契约 §5.5 明说增量缓冲的裁剪要看"**全部配对设备**"，也就是**多设备是设计内的**，不是可选场景。

## 三条路（需要定夺，不是我能自行选定的）

1. **每连接一套**：把上表那些构造物改成"按连接创建"（连接注册表 + 每条连接持有自己的
   方法面/订阅/缓冲/端点）。正确且符合多设备设计，但这是一次真正的架构改动：
   `start-transport` 要拆成"按连接装配"，生命周期与 dispose 也要跟着按连接收口。
2. **单活动连接**：监听面接受新 socket 时**替换**旧连接（同一时刻只服务一台设备）。
   改动小得多（`connection = next` 换成"先停旧的再装新的"），但多设备（契约 §5.5 明说要考虑）
   就不支持了 —— 而且"全部配对设备都确认才裁剪"这条会退化成"一台设备确认就裁"，
   **那是丢事件的方向**，不能默默做。
3. **先不做监听面**，改做 `relay/`：中转天然是多连接的（它按连接转发），
   桥接仍然是"一条到中转的连接"（现有单槽形状就够）。代价是中转是全新组件。

**我的看法**：路 3 与契约拓扑一致、且不需要动"每连接状态"这一层（桥接侧仍是单连接）；
但它把工作挪到一个新组件上。路 1 是迟早要做的（多设备是设计内的），
只是现在做会让这一轮从"加个监听"变成"重构装配"。

## 因此本轮停在这里

`attach(socket)` 已经就绪且被测（上一轮），**再往前一步需要上面那个决定**。
在它定下来之前写监听面，只会得到"能接受连接、但第二条连接收不到任何东西"的半成品 ——
而那种半成品在真机上表现为"偶尔连上但没反应"，比完全没做更难查。
