# Agent Note: 手机远控走「反向 WebSocket + 哑中转 + 端到端加密 + 敲门式推送」

Status: proposed

## Problem

`docs/design-and-tech-plan.md` §2 已经选了「反向连接 + 中转」，但把中转的职责写成「只转发/存会话」——既没说存什么、谁分配游标，也没说断线之后靠什么保证不丢。§10 又把 Tailscale 排在第 2 步、自建中转排在第 8 步，读起来像「中转只是后期的优化项」。§7.5 则已经声称密钥写入「经中转端到端加密」、通道要「端到端加密」，但没说这条加密覆盖到哪一层。

结果：后来者会自己推断出三个更严或更松的假限制——(a) 以为中转可以当缓存和存档用，于是把「手机随时能看到历史」实现成服务端持久化；(b) 以为直连阶段先「重连全量刷新」、以后再补增量，于是恢复语义在第一步就被写死；(c) 把「端到端加密」理解成「TLS 就够了」。

## Decision

手机与电脑之间只跑一条**反向 WebSocket** 通道；中转是**不存内容、不解析语义**的哑转发器；会话修订号由**电脑侧**分配并持久化；载荷**端到端加密**，中转只见路由元数据；锁屏与进程被杀时只发**敲门式推送**，正确性由回前台后的补课保证。

准入门槛（可机械判定）：

1. 中转代码里不得出现任何按事件内容分支的逻辑。删掉中转全部业务状态后重启，已配对设备重连必须仅凭电脑侧数据恢复——不丢事件、不产生重复条目。
2. 单个会话的恢复只允许两种结果：`snapshotRequired:false` 且给出从 `since` 起的完整增量，或 `snapshotRequired:true` 且明确要求基线快照。第三种「看起来补上了」的中间态一律不通过。
3. 重连后除持久增量外，必须**无条件重取全部瞬时事实**（电脑在线态、待审批、待回答、能力位）。少任何一类都不通过。
4. 所有写操作必须带幂等键：断线重发不得产生第二条消息或第二次审批。
5. 中转磁盘上不得出现会话正文与工具输出的明文；抓包与落盘检查只能看到路由元数据与密文。
6. 推送丢失、重复、乱序时，前台状态仍必须与电脑一致——即推送不参与正确性判定。
7. 条目身份与修订号解耦：稳定 itemId 必须由事件自身推导，不得用会话 `seq` 当主键（崩溃尾回合的合成事件会临时占用一个 seq，恢复后被真实事件替换）；任务条目同理，`JobId` 会跨重启重用。

## Alternatives considered

1. 中转长期存内容（参考项目 Agents-Anywhere 的做法：服务端持久化会话 meta 与 timeline，并分配持久序号）
   - 最强的理由：手机在电脑关机时也能看完整历史；换手机、重装 App 不用重新同步；服务端还能做搜索、去重与聚合。
   - 为何被否：服务器会变成会话内容的第二真值源与长期驻留点，与「手机看状态」的产品定位不符，还要多养一套存档、去重、迁移的服务逻辑；我们要的不是云端工作台。
2. 端到端加密推迟到后续版本，第一版只做 TLS
   - 最强的理由：省掉密钥协商、封箱、多设备密钥轮换一整块，第一版更快；TLS 已能挡住链路窃听。
   - 为何被否：§7.5 已把「密钥只朝一个方向过线 + 经中转端到端加密」写成原则，中转若能读内容，这条原则就是假的。且既然中转不存内容、不做语义处理，全量封箱并不比局部封箱难多少，却省掉一次「以后必须迁移」的返工。
3. SSE + POST 代替 WebSocket
   - 最强的理由：自带 `Last-Event-ID` 断线续传语义，穿过代理与 CDN 更老实，不需要自定义心跳和升级握手。
   - 为何被否：命令仍要另开一条写路径，双通道的鉴权、重连、幂等要各写一遍；电脑侧桥接本身就是行级 JSON-RPC over WebSocket，两端同构可省掉一层翻译。留档：若某天遇到明确拦截 WS 升级的网络环境，再补 SSE 作为只读降级通道。
4. MQTT（持久会话离线补课）
   - 最强的理由：QoS1 + `clean session=false` 天生解决「离线一段时间后补消息」，省掉自研重放窗口。
   - 为何被否：它的「补消息」有界且会静默丢——EMQX 默认会话过期 2 小时、离线队列 1000 条，会话过期时排队消息一并过期，正好落在「以为补齐了」这个最危险的失败模式上（EMQX/HiveMQ 文档）。此外多一个必须运维的 broker 与主题设计，命令仍是 RPC 形状要在其上再包一层，也解决不了「App 被杀」。净增组件、净增运维。
5. 直连（局域网 / Tailscale / WireGuard），不上中转
   - 最强的理由：零服务端成本，内容根本不经过第三方。
   - 为何被否：手机走蜂窝网时不可用；要求用户装并常开 VPN 客户端，国内可用性不稳定；更关键的是没有常在线的一方，就没人能替电脑发推送——「锁屏也能收到审批与完成通知」这条承诺直接落空。直连保留为第一阶段验证手段，不作为产品形态。
7. 只做一条「到达 DSH loopback webserver」的通道,手机直接讲 DSH 的 remote 协议
   - 最强的理由：DSH 已经有面向远程客户端的事件白名单（`approval/request`、`user-questions/request` 都在内）与 `sessionController` 的 `prompt`/`cancel`/`page`/`follow`（开场快照 + 无缺口持久事件帧）——「发消息 / 看历史 / 收事件 / 答审批 / 答提问」五件事在 DSH 侧已有现成 Remote 面。走这条路，投影语义全部由 DSH 官方维护，我们一行都不用写。
   - 为何被否：手机端就得去实现 DSH 的内部客户端协议（Typert 生成的方法面 + 事件白名单 + 绑定 authority 的 HMAC cookie 鉴权），而该协议没有任何稳定性承诺、也未找到官方客户端 SDK；它的鉴权是"每进程启动 token"，为 loopback 浏览器设计而不是为远端设备设计；且 shipped CLI **显式拒绝 `--host 0.0.0.0`**（理由是会向网络暴露任意代码执行），所以仍然要写一个转发件——省掉的只是投影层，代价是把手机端绑死在一个会随 DSH 版本漂移的内部协议上。而配对、端到端加密、推送、断线补课这四件无论走哪条路都要自建。
   - 保留的结论：不选这条通道，但**数据源照抄它的思路**——电脑侧插件是薄适配层，`follow()` 的开场快照直接当我们的基线快照，审批的 `allowed-once` 直接当我们的"允许一次"。
8. 把 DSH 的 Web 客户端反代到手机 WebView
   - 最强的理由：零客户端 UI 开发，DSH 有什么手机就有什么，永不分叉。
   - 为何被否：与 §3 已定的「原生 Flutter、不做 WebView 薄壳」冲突；§7.2、§7.9 那套触屏输入区与列表行结构在桌面 Web 布局下不成立。

## Consequences

- 收益：电脑侧插件是**薄适配层**——会话流、审批仲裁、历史分页、任务游标都复用 DSH 已有服务（`sessionController.follow/page/prompt/cancel`、`approval`、`userQuestions`、`ctx.jobs`），自研的只有「手机 ↔ 电脑」这一段，且 DSH 升级时语义跟着上游走，不会出现两套审批规则。
- 收益：中转可退化成极小服务（路由 + 有界重放窗口 + 推送投递 + 配对鉴权），被攻破时既拿不到会话正文也拿不到长期历史；恢复语义只有「增量或快照」两种结果，不依赖中转自身状态；电脑侧是真值源，不需要在服务端重建 DSH 语义。
- 代价：换手机或重装 App 后本机历史不在，需要回连电脑重新同步；电脑离线时手机只能看已缓存的部分；多设备各自缓存、各自持密钥，密钥轮换要自己写对；推送摘要对推送通道可见（仅摘要，且提供「只敲门不带内容」的隐私开关）。
- 代价：推送的触达能力被平台政策封顶——iOS 被用户强杀后系统不会自动拉起 App、只能靠用户点通知；安卓大陆只能走厂商通道，且受分类报备、模板与夜间时段限制；鸿蒙未申请自分类权益时单设备每日仅 2–5 条。因此「审批必达手机」不可承诺，可承诺的是「打开 App 后状态一定正确」。
