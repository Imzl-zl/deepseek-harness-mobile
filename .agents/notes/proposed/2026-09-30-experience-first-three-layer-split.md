# Agent Note: 多端按"体验"分三层,不以工程量为判据

Status: proposed

Supersedes: `.agents/notes/archived/2026-09-30-capability-packages-over-per-platform-dirs.md` —— 该篇「核心零分支 + 按能力切包」的结论仍然有效并在此保留,但它的**判据（工程量 / 收益比）被本篇替换为体验判据**,判据覆盖范围也从两层扩到三层。

## Problem

「三端共享一套 UI 还是分开做」被当成了一个二选一的成本问题:共享省事但可能体验差,分开体验好但工作量大。于是决定取决于"能投入多少",而不是"哪种能做出更好的体验"。更糟的是,一旦用"工程量"作判据,评审时无法判定——任何方案都能自称"够用"。

产业界的证据也不支持这个二分:官方给的从来是**光谱**（Kotlin Multiplatform 文档原话:从"共享除入口外的全部代码"到"只共享一段逻辑",或"共享业务逻辑、UI 保持原生"）,Google 官方背书的默认是**共享业务逻辑**、共享 UI 是附加项;而"体验好不好"的公开触发点集中在**启动/首帧、列表与手势掉帧、崩溃与可靠性、后台与系统限制适配、平台惯例、无障碍**——**没有一条是"UI 代码有没有共享"**。

## Decision

多端结构分三层,**每层的判据不同**,且判据必须可判定或可留痕,禁止使用"工程量""优雅"这类自评条件:

- **第一层 共享内核**(协议、恢复引擎、本地库、领域模型、状态机):禁止分叉。
- **第二层 共享信息架构与品牌呈现**(视觉体系、逐屏结构、时间线/甘特/diff 等复杂渲染),但**系统紧耦合控件一律跟平台惯例**。
- **第三层 每端专属表达**:凡"App 不在前台也要存在"的能力,必须每端实现,并作为产品体验上限来投入。

这条分层不是自创:官方示例 `platform_design` 的定位原文是"**maximizes application code reuse while adhering to different design patterns**… platform-agnostic content surrounded by platform-specific 'chrome'";Google Classroom 的公开数据也支持它——同一套 UI 覆盖"屏幕中间 90%",系统栏与底部控件按平台保留,启动时间降低 80%、新功能工时降到 1/3。

准入门槛:

1. **C1（机器判定）该能力是否需要在 App 不在前台或已被杀时工作?** 是 ⇒ 必须每端实现,归 `app/packages/<能力>_<端>/` + 壳工程原生代码,禁止试图用共享 UI 实现。
2. **C2（机器判定）该控件是否是用户凭肌肉记忆操作的系统紧耦合控件?**（导航转场、返回手势、下拉刷新、文本选择菜单、分享面板、开关/选择器/对话框/进度指示、触觉反馈）是 ⇒ 必须跟平台惯例:能用官方自适应构造器就用,官方没有的进 `app/lib/ui/adaptive/`,业务 UI 只调这一层。
3. **C3（评审留痕）该组件的复杂度是否高到三端重写会显著抬升不一致风险?**（流式 Markdown、时间线/甘特、diff 渲染、轨迹投影）是 ⇒ 留在共享层。这是"按复杂度划边界,而不是按平台划边界"。
4. **C4（评审留痕）该元素是否承载产品识别度与信息架构?** 是 ⇒ 共享,且禁止按端改。
5. **C5（禁止项）不得因为"这样写更快"而分叉;也不得因为"看起来整齐"而把 C2 类控件强行统一。**
6. **C6 每个平台必须有一名 advocate**,持有该平台的惯例清单并对其体验负责（这是 Flutter 官方文档给出的组织建议:"assign someone as an advocate for each platform"）。

重新评估条件（写清前提,避免下次被当成新方案重提）:**若产品形态变成"手势与延迟敏感的自绘工具"**（Figma / Linear 那一类,UI 本身就是产品）,第一、二层应重新评估为"每端原生 UI、只共享核心"。本产品不是那一类:它的体验上限在"不在前台时的表达",不在自绘 UI。

## Alternatives considered

1. 三端全原生、每端一套 UI（Telegram 式;Linear 的移动端也是这条路）
   - 最强的理由:体验上限最高。Linear 官方原话是"Fully native… to guarantee a fast and fluid user experience",甚至用两名 iOS 工程师把系统新材质与 Increase Contrast 无障碍行为都自己复刻;Apple HIG 与 Flutter 官方也都要求系统紧耦合控件按平台惯例——原生是这条要求的终点。若产品是自绘工具型,这条路是正确答案。
   - 为何被否:本产品的体验差距不在自绘 UI,而在"App 不在前台时的表达",那一层**无论选哪条路都必须每端单独做**;剩下能被共享的部分,三份实现带来的不是更好的体验,而是**体验漂移**——Duolingo 两个原生 App 就是活标本:Android 相对 iOS"帧率不稳、交互不一致或损坏、bug 多",还收到用户手写投诉,而触发点是**性能与稳定性,不是"长得不像原生"**。实证研究也显示 hybrid 与 native 的商店星级差异可忽略,投诉集中在性能与可靠性。把预算投在"每端专属表达 + 热路径性能"比投在"三份重复 UI"更接近"最好的产品"。
2. 全共享 UI,不做平台专属表达（一套 Flutter UI 三端通吃）
   - 最强的理由:实现与测试最省,三端像素级一致,品牌识别度最高;Flutter 官方也明确允许"stay unique"、允许统一外观,只要求行为遵循惯例。
   - 为何被否:等于主动放弃"锁屏看到任务跑到哪了""在通知上直接批准"这类体验,而这正是本产品的核心承诺;平台政策层面也有边界(Apple App Review 4.2 明确要求 App 的价值超出"repackaged website",Google Play 对崩溃与功能残缺同样有明文约束)。
3. 共享 UI,但把平台差异写成散落的 `if (platform)` 分支（Discord 早期形态）
   - 最强的理由:一处写完、见效最快;Discord 证明共享 UI 也能做到 99.9% crash-free、4.8 星。
   - 为何被否:Discord 达成那个数字的代价,是**在共享框架里为热路径写平台专属实现**（原生列表、手势、懒加载）,并公开接受"为体验而分叉"——它的边界靠人记。我们把同样的分叉显式化:C1/C2 的分叉只允许出现在能力包与 `lib/ui/adaptive/` 两处,不撒在业务代码里。

## Consequences

- 收益:三层各司其职,且每层判据可判定或可留痕,评审时能指出"这条属于 C1 还是 C3";平台差异有固定归处(能力包 + adaptive 层),不靠自觉;第一层零分支保证修复与优化三端同时生效;产品体验上限被显式排进路线(每端专属表达),而不是"以后再说"。
- 代价:**三端体验不对等是既成事实**——iOS 能在锁屏常驻显示进度(Live Activity 的生命周期不绑定 App 进程,官方原文如此),安卓的提升通知受官方"用户发起"标准限制(明文禁止"其他方触发"的活动),鸿蒙实况窗的 PROGRESS 场景明确排除后台自动任务、服务卡片每日额度也撑不住进度刷新。产品上不能承诺"三端一致",只能承诺"每端做到该端上限",并且要在界面与文案上如实表达这种差异。
- 代价:`ui/adaptive/` 与能力包都要我们自己维护——官方只有 **7 个 `.adaptive()` 构造器**,而自适应脚手架包 `flutter_adaptive_scaffold` 已于 2025-05 停更且无官方接续;官方把 AppBar 样式、底部导航形态、对话框这类差异明确划为"**设计期决策**",框架不会替我们适配。
- 代价:多两处结构——`lib/ui/adaptive/` 与后台/系统能力包,简单控件也要走一层;每个平台需要有人对惯例负责(C6),这是持续的人力承诺而不是一次性工作;若将来形态变成自绘工具型,第一二层要重新评估(重估条件已写在 Decision 里)。
