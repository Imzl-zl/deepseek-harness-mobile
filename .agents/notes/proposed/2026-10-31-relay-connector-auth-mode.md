# Agent Note: 中转的"连接器是否必须认证"可配

Status: proposed

## Problem

现在**连接器 → 中转**这一跳只有一种可能：必须带管理员签发的令牌
（`connector/src/index.ts:368-370`：`relayTokenRef` 缺失直接抛错；中转侧只有摘要表
一条认证路径）。于是"开源了但别人用不了你的中转"——每个想用的人都要找 owner 手工发令牌，
owner 一个人发不动。

而手机那一跳早就有成熟的换票机制（`POST /ws-ticket` 的 `offerId` 分支，
`relay/src/http-face.ts:58-82`），扫码即可。缺的只有电脑怎么第一次合法地上线。

需要在**不引入第二条认证路径**的前提下，让 owner 能用一个开关决定：
陌生连接器是"必须我发令牌"还是"自己来拿一张"。

## Decision

新增两个配置项，**都由 owner 自己定，不预设人为上限**：

| 字段 | 值 | 默认 |
|---|---|---|
| `connectorAuth` | `open` = 连接器不带令牌也能连（中转**自动签发一张真令牌**，不是跳过认证）；`required` = 只有管理员签发的令牌能连 | **`open`** |
| `autoEnrollLimit` | 自动签发总数上限：正整数；**`null` = 无上限** | **`null`（无上限）** |

默认开放的理由：这是开源项目，别人拿到地址就能用起来才算能用；要收紧就把
`connectorAuth` 改 `required` 或把 `autoEnrollLimit` 设成具体数字 —— **收紧是 owner 的动作，
不是产品的默认**。两个字段都能在管理面板里改，改完立即生效。

### 为什么是"自动签发"而不是"放行匿名"

放行匿名（开模式下跳过认证、用握手里的 `pcId` 当身份）会造出**第二条认证路径**：
吊销、配额、限流、审计、连接器名册全要分叉，而 `pcId` 在握手前不可信、可冒用。
自动签发则只有一条路径：签发完就是"一张普通令牌"，之后的认证、吊销、限流、
管理面板的每一行都不需要知道它是自动来的。**多出来的只是"怎么拿到令牌"这一步。**

### 端点

`POST /connector/enroll`（HTTP 面，**不认证**）

```
请求  { "pcId": "<连接器的稳定 id>", "name": "<电脑名，可选>" }
201   { "token": "<明文，只出现这一次>", "connectorId": "auto-<8 位>" }
403   { "error": "connector-auth-required" }        // 模式是 required
429   { "error": "auto-enroll-full" }               // 配了上限且已到（null = 永不到）
429   { "error": "rate-limited", "retryAfterMs": n } // 按来源 IP 分桶
```

- 中转侧用现成的 `issueToken` + `appendTokenToConfig` 落盘（`relay/src/issue-token.ts:72,87`），
  条目带 `source: 'auto'`，**与手工令牌同一张表**。
- 限流沿用 `pairing:anonymous:<addr>` 那套分桶（反向代理后等价于全局桶，
  `rate-limit.ts` 已写明这个退化）。**限流是速率，不是名额** —— 名额只由 `autoEnrollLimit` 决定，
  不设上限时不拦。

### 连接器侧

`relayTokenRef` 从**必填**改为**可选**：

| 情况 | 行为 |
|---|---|
| 有令牌 | 照旧拨号 |
| 无令牌，中转 `open` | 先 `enroll` → 令牌写进 DSH 凭据（`credentials.set`，**不进配置文件**）→ 拨号 |
| 无令牌，中转 `required` | 明确报"这台中转要求管理员签发令牌"，而不是现在那句 `validate-config` 抛错 |

### 管理面板

- 状态页显示「连接器认证：必需 / 开放」，可一键切换（写回配置 + 运行时立即生效）。
- 令牌表里自动签发的行标「来源：自动」，支持"吊销全部自动"。
- 切到 `open` 时弹一条横幅：任何拿到地址的人都能注册并借用这台中转的带宽。

## Alternatives considered

1. **开模式下跳过认证（匿名连接器）**
   - 最强理由：零签发、零存储，最省。
   - 为何被否：见上——第二条认证路径，吊销/配额/名册全要分叉；`pcId` 冒用无从追。
2. **一次性注册码（enrollment token）**
   - 最强理由：可设过期与名额，控制粒度最细。
   - 为何被否：owner 仍要为每个人生成一次码，开源场景下它的麻烦程度和"发令牌"几乎一样；
     用户明确要求"一个开关"。
3. **在 WS 握手里返回令牌（协议帧）**
   - 最强理由：一次连接搞定。
   - 为何被否：要改握手/线协议，`protocol/verify-fixtures`(454 项) 与向量都要跟着动；
     而 HTTP 面已经有 `/ws-ticket` 这样的先例，加一个端点不动协议。
4. **默认 `required`（安全优先）**
   - 最强理由：装了不会莫名其妙替别人中继流量。
   - 为何被否：这是开源项目，默认证就等于"陌生人拿到地址也用不了"，每个用户都要先找
     owner 要令牌才有第一条连接；owner 明确要求默认自动签发，把收紧留给自己选择。

## Consequences

- 收益：owner 一个开关决定开放程度；开放时无需为任何人手工操作；认证、吊销、限流、
  审计、管理面板复用同一条路径。
- 代价 1：`open` 是**默认值**，也就是"装了就能被陌生人连"——带宽、连接数、滥用成本
  默认由 owner 承担（内容仍是端到端加密，中转只见密文与元数据）。收紧只需改一个字段
  或把 `autoEnrollLimit` 设成具体数字，两者都在面板里能改。
- 代价 2：配置多一个字段，`connector/src/config.ts` 与 `relay/src/main.ts` 都要加校验；
  老配置缺省即 `required`，行为不变。
- 代价 3：连接器多一条"先兑换再拨号"的启动路径，必须有明确的失败台词
  （403 / 429 / 网络错分三种），否则现场只会看到"连不上"。

## Testing

- relay：`open` 下 enroll 成功且摘要落盘；`required` 下 403；限流 429；上限 429；
  自动行可被管理面板吊销，吊销后再 enroll 不影响既有行。
- connector：无令牌 + `open` → 兑换一次并写凭据；无令牌 + `required` → 报"要求签发令牌"。
- admin：面板切换写入配置，并立即改变 enroll 行为（不需要重启容器）。
- 回归：默认 `required` 时现有令牌路径的用例全绿（773 项不动）。
