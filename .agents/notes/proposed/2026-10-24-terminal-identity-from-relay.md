# Agent Note: 开工单 W3 —— 终态只有一个来源（电脑说"我不认你"），中转的 401 不是它

Status: proposed

## Problem

"这台手机还配着对，只是暂时连不上"与"这台手机被电脑停用了"在今天**走同一条动作**：
清凭据 + 回配对页。于是电脑那边只要停一会儿（中转重启），手机就把配对扔了 ——
用户必须重新扫码。

具体位置（两处，同一个根）：

1. **换票 401 被读成终态**：`app/lib/core/pairing_client.dart:75-85` 把 `401 || 409`
   映射成 `ErrorCode.notPaired`（`ClientAction.rePair`，`app/lib/core/errors.dart:92`）；
   `app/lib/platform/ticketed_transport.dart:62-78` 把它带上码抛给连接层，
   `app/lib/core/sync_client_impl.dart:311-320` 据此判终态并**不重连**、
   交上层清凭据（`app/lib/data/connection_recovery.dart:5-11`）。

   可是中转这个 401 说的是什么？名册里没有这个摘要 —— 而**名册是电脑侧的推力**
   （`relay/src/device-registry.ts:88`：令牌无效 / 已吊销 / 没见过都回 `undefined`；
   设备令牌由电脑签发、`POST /devices` 进名册）。中转重启后名册是空的，
   直到电脑连上来重新灌一遍。**所以那不是"你不配了"，是"我暂时不知道你"。**

2. **握手层收到"明说"却仍走退避**：电脑侧停用一台设备后，握手会以 close 4003 收场
   （`connector/src/transport/connection.ts:660`），协议错误表里也备了 `protocol/revoked`
   → 重新配对（`connector/src/protocol/errors.ts:30`）。但这两条**都没进终态那条路**
   —— 终态判据只覆盖"建连失败"（`app/lib/core/sync_client_impl.dart:316-320`），
   于是真正该清凭据的信号反而在退避里转圈。

一句话：**我们把"我不知道"当成了"我不要你"，又把"我不要你"当成了"再试试"。**

## Decision

**终态（`ClientAction.rePair`）只有一个来源：电脑侧在协议里明说"不认这台设备"。**

- 握手 close 4003（带 reason）与 `protocol/revoked` 帧 ⇒ 终态：不清凭据也**不重连**，
  由上层呈递"这台设备已被电脑停用，请重新扫码"，用户点确认才清凭据。
- **换票 401（已配对设备的换票路径）⇒ 不是终态**：按传输失败退避重试，
  文案如实说"中转不认这台设备（名册里可能还没同步）"，并给一个手动的"重新配对"入口。
- **配对过程中的 401/409 保持原样**（那条路上 `notPaired` 是对的：邀请/秘密不对）。
  两个调用点共用 `_ticket`，所以要把"状态码 → 错误码"的策略**按调用点分开**，
  而不是在共享函数里再分叉。
- 终态判据**只写一处**：`ClientAction.rePair` 由错误码表（`app/lib/core/errors.dart`）
  决定，连接层与握手层都只问它，不各自 `if (code == notPaired)`。

## 为什么不是"让中转分开说 revoked / unknown"

中转**不知道**：设备名册是电脑推上去的（`relay/src/device-registry.ts:88`，
`relay/src/digest-auth.ts:39-46` 也只管连接器令牌），电脑停用一台设备的方式是
**不再把它报进名册**。所以中转能说的只有"名册里没有"。要让中转知道"已吊销"，
得新加一条"电脑把吊销同步给中转"的协议面 —— 为一条 401 造一个新面，是更大的偏离。

**"明说"的那一侧是电脑**（`connector/src/transport/connection.ts:660` 的 4003 + reason），
它本来就在线上，我们只是没读。

## 判据

- **单测（0 真机）**：换票 401 ⇒ 连接层**不**判终态、走退避，且 `lastConnectWasTerminal`
  为 false；文案里出现"名册"。
- **单测**：握手 close 4003 ⇒ 终态、不重连、呈递一次"已被停用"；`protocol/revoked` 帧
  同一条（同一个判据，两条入口）。
- **单测**：配对路径的 401/409 仍是 `notPaired`（策略按调用点分开，不回归）。
- **变异校验**：把 4003 的终态判据删掉 ⇒ 恰好握手那条红；把换票 401 改回终态 ⇒ 恰好第一条红。
- **真机 2 个回合**（合并成一次联调）：① 中转重启 → 手机**自动恢复**、配对不掉；
  ② 在电脑上停用这台设备 → 手机**明说**已被停用（不静默清凭据）。
  报价 **1–2 回合**（同一个隔离实例里可以连着做）。

## 代价

- flutter 门禁（1140）会变：`not-paired` 相关的用例要按"两个调用点两种策略"改写；
  新增 3–4 条。**不是放宽**：终态的行为从"两个来源"变成"一个来源"，断言数量应升。
- 用户可见行为变了：电脑停用设备后，手机**不会自动**回配对页（要点一下）。
  这是有意的 —— 自动清凭据在"中转重启"这种可恢复场景里代价太大。
- 契约 §11 的故障矩阵要同步两行（401 的客户端动作；4003 / `revoked` 的动作），
  `app/lib/data/connection_recovery.dart:5-11` 的注释也要跟着改一句话。

## Alternatives considered

1. **保持现状 + 把"401 之后可能恢复"写进 docs**
   - 最强的理由：零改动。
   - 为何不选：这是一条**会丢用户数据（配对凭据）**的路径，写进 docs 不会让它不丢。
2. **中转改回 200 + "名册为空"标记**
   - 为何不选：那是把"未认证"伪装成"认证成功"，`relay/src/digest-auth.ts:43` 的
     设计（合并原因）也不是错，错的是消费它的那一侧。
3. **App 侧对 401 做"连续 N 次才终态"**
   - 为何不选：凭空造一个阈值（正是 `AGENTS.md` 常驻军规点名的形状）。终态应由**语义**
     决定，不由次数决定。
