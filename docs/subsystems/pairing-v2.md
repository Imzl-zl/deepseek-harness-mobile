# 首配 v2 与独立数据连接

本文件承载 `remote-channel.md` §2、§12.1 的配对与连接隔离细节。业务会话信封仍为 v1；二维码/首配载荷为 v2，旧明文 `pair` / `pair-ack` 不再允许。

## 1. 不变量

- 二维码是电脑身份与配对秘密的唯一带外来源。中转只知道公开 `offerId`，不知道秘密 `code` 或可直接用于授权的替代凭据。
- 配对候选不是已配对设备。候选只有完成本次连接的持钥证明后才能提交秘密；提交正确秘密且用户已确认后才写正式设备表。
- **手机以安装级 `deviceCode` 关联历次配对身份**：正常覆盖升级与重新配对保留显示码；鉴权密钥、`devId` 和令牌仍按有效重新配对轮换。新身份正式鉴权成功才退役登记时捕获的旧身份。旧无设备码记录只按目标电脑的精确旧 `pairingId` 关联，不按名称、型号或短码推断。
- 同一条数据连接只对应一个设备、一个连接代次。握手、AEAD 密钥、`fc`、流控和订阅不得跨连接共享。
- 中转只做连接路由。它不能通过修改候选公钥、设备 ID 或连接代次让电脑授权另一台设备。
- 所有长期令牌只在电脑/手机端以明文使用，配对回执端到端加密；中转名册只存摘要。
- **中转永不签发设备令牌**：它只签连接器令牌。设备令牌由电脑侧签发、摘要经 `POST /devices` 进名册 —— 转发器不该能凭空造出"我是某台设备"的凭据。摘要表里出现 `device` 条目时中转**拒绝启动**（那种配置"起来了也谁都连不上"：设备 403、电脑侧一切正常，比起不来难查得多）。`--issue-token` / `--revoke-token` 因此只认 `connector`。
- 传输断开不代表写入回滚。最后回执丢失时显示“结果待确认”，不能假报“未配对”。

## 2. 连接拓扑

- `/ws/connector`：连接器令牌认证的控制连接，每个连接器一条；不承载设备的业务帧或 E2EE 握手。
- `/ws/device?ticket=…`：手机连接。票绑定连接器、设备公钥标识、用途（`paired` / `pairing`）与候选元数据。
- `/ws/connector?dev=<deviceId>&channel=<channelId>`：电脑为该设备建立的数据连接。中转同时校验连接器身份、票绑定的归属、目标设备和当前连接代次。
- 中转为每次手机连接生成新 `channelId`；通过控制连接通知电脑创建/关闭对应数据连接。
- 控制消息为 `relay.open` / `relay.close`，只含路由元数据与候选公钥。配对秘密、方法名与业务内容不得进入控制消息。
- **局域网直连**：`<lan>/?pair=<offerId>&cand=<候选>`。手机拨连接器的监听面（默认 `0.0.0.0:8790`），不经中转 —— 连接器自己持有 offer，也自己听得见这个端口，所以"保管邀请"与"转告有候选"在局域网上都不需要服务器。`pair` 是触发参数，`cand` 是无填充 base64url 的候选 JSON（公钥与设备名，都不是秘密）。
  - **`lan` 有多条时手机一起拨**：同一轮内对全部候选发起受限握手，先通先用，其余（含还在握手中的）当场收掉；连输家留在半开状态都不行。失败时**只给一句**「局域网不通（试了 N 个地址，是否同一 Wi-Fi？）」，每个地址的原始错进诊断日志 —— 逐条红字会把"配对码过期"这类真因淹掉。取舍见 `.agents/notes/implemented/2026-11-24-pairing-dials-lan-in-parallel.md`。
- 数据路径逐条双向转发，不按 `sid` 广播，不按请求 `id` 猜回程。`credit`、`ping`、`res` 与事件共用同一条已绑定数据路径。
- 等待电脑数据连接时只暂存有界的首批帧；超限或连接建立超时即明确关闭。
- 替代连接出现后，旧连接的收帧与关闭回调都无权改动新代次。任一数据端断开关闭配对的另一端；控制连接断开关闭它的数据连接，客户端正常重连。
- 中转清空重启后，电脑控制面重放已配对名册；手机重新换票、重新握手。旧密文不跨密钥代次重放，业务恢复由电脑的会话序号与快照负责。

## 3. 二维码与发现

二维码 SVG 自身必须在四边保留至少 4 个码元静区，白边不得靠页面或测试另补；符合 [DENSO WAVE 的标准 QR 规则](https://www.qrcode.com/zh/howto/code.html)。解码回归直接使用实际 SVG 的完整范围，不裁白边或改变载荷。

二维码包含：`{ v: 2, relay, lan?, routes?, pcId, pcPubEd, pcPubDh, offerId, code }`。

- `offerId`、`code` 分别独立生成 16 字节随机数并编码为无填充 base64url；两者不可相互推导。
- 有效期沿用 5 分钟。电脑同时只保留一份当前出码状态；重新出码使旧的未完成尝试失效。
- 电脑保存 `code` 的 SHA-256 校验值，**不向中转登记该校验值**。
- `routes`（可选）= 这张码**实际有哪几条路**：`['lan']` / `['lan','relay']` / `['relay']`。直连监听在跑才有 `lan`，中转**控制面连上了**才有 `relay`（不看配置里的地址）。新版手机据此只试真有的路；旧版忽略它，仍按 `relay` + `lan` 走。
- 出码先向中转登记 `offerId`。**中转那条腿不在**（控制面没连上）时不登记、`routes` 不含 `relay`；码里写哪几条只由此刻的能力决定，没有"这张码给谁用"的选项。要登记而登记失败时：载荷里有 `lan` 仍出码（手机走局域网直连，跨网那条路没了而已，`lanOnly: true`），没有 `lan` 则不出码 —— 那种码扫了也配不上。两条腿都没有时不出码，错误正文说清缺的是哪条（`connector/src/endpoints.ts` 的 `noLanAddressReason`：监听未启动 / 没枚举到地址 / 没有局域网 IPv4 / 被 `hide` 删空）与「中转未连接」。
- **出码的唯一入口是插件面板的 `POST /api/dsh-mobile/pair`**（斜杠命令不能当入口：DSH 的 `CommandResult` 只能回文本，给不出二维码）。
- `lan` 是这台电脑**此刻**枚举到的**全部局域网 IPv4**（`endpoint.describe` 的 direct 那一组，判据 `connector/src/endpoints.ts` 的 `autoAdvertisedUrls`：只认 RFC1918，不看网卡名/MAC/默认路由；用户点名 `extra` 的也照办，`hide` 的照藏），**每次读都重新枚举网卡**、端口是实际绑定端口 —— 换 WiFi 后重出码就是新地址。为空就不写这一格（老载荷形状，手机按老路换票）。
- 手机对 `lan` 里的每一条过与中转地址同一道边界（`checkedRelayUri`）；认不出的条目丢掉，不让整张码作废。
- 首配换票请求为 `{ v: 2, offerId, devPubEd, devPubDh, name }`。公钥必须是 32 字节十六进制，名字有长度上限；设备 ID 由公钥按现有规则派生，不接受请求方任意指定。
- 换票只查询公开邀请并建立候选，不消费电脑的配对秘密。候选数量、换票频率和寿命有界；无效试探不能使真正的扫码设备失去授权机会。
- 生产地址只接受 HTTPS/WSS。明文仅用于显式开启的本机调试，不允许在 release 中放行。

## 4. 受限配对握手

复用现有 `hello → hello-ack → confirm` 的签名、DH 派生与 AEAD 实现，不新增另一套密码学。

- 正常设备的 `peerOf` 仍只查正式设备表。
- 配对用途的 `peerOf` 只返回本连接绑定的候选公钥；不得写正式设备表，也不得触发普通业务的 `deviceEstablished`。候选公钥有两个来源，形状相同：中转控制面的 `binding.candidate`，或局域网升级请求的 `cand`。两者都只**自报**，可信性由下一行与第 6 条决定。
- 手机的电脑公钥和 `pcId` 固定来自二维码。中转下发的候选信息、局域网请求里的候选信息都不是信任来源 —— 候选公钥进配对认证上下文并被签名进 transcript，换掉任一字节两侧就算出不同密钥，握手在验签处失败；授权仍由二维码里的 `code` 完成。
- 配对认证上下文为固定字段顺序：用途/版本、`offerId`、`pcId`、电脑两把公钥、设备 ID、设备两把公钥、设备名的 SHA-256。上下文纳入签名 transcript。
- 配对密钥派生使用独立的 `dsh-mobile/v2/pairing-keys|` 域，临时配对标识使用 `offerId`；正常业务的 v1 派生不变。
- 握手结束只表示“配对加密可用”，不表示业务授权。该连接仅允许加密的保活/流控与 `pair-commit`，其余业务请求一律拒绝。

## 5. 用户确认与提交

手机流程：解析二维码 → 验证电脑身份 → **按连接方式策略决定探测范围**（`auto` 探码里的两条；`directOnly` / `relayOnly` 只探允许的那条，另一条标「按设置未尝试」）→ 每条真实拨号、受限握手，结果逐条立即呈现 → 任一允许路径握手成功即可选中并确认，不等待其他路径；未完成的仍显示「检测中」→ 显示电脑身份和授权说明 → 用户确认 → 只在选中路径加密提交，取消其他候选 → 收到成功回执立即 await 保存凭据并正式连接，不加第二次「完成」落盘门。保存失败明确显示「电脑已登记、本机保存或连接未完成」，保留同一回执重试，不重复提交秘密。退出或选定后，迟到结果不能复活旧页面或改选路径。

- 用户确认前不发送秘密、不创建有效设备记录、不签发长期令牌。
- `pair-commit`：`{ v: 1, t: 'pair-commit', id, fc, box }`，密文载荷为 `{ v: 2, offerId, code, previousPairingId?, deviceCode? }`。
- **`deviceCode`（可选）**为手机本机安全存储中的 22 字符安装级定位/显示码；它是公开定位信息，不是硬件标识或认证凭据。码、旧定位信息不进入候选 URL、匿名换票或中转名册。缺码的正常升级用当前完整槽实际 `helloDeviceId()` 初始化；已有设备码不跟随密钥轮换。首次没有完整当前槽才随机创建；读取失败或已有坏码明确抛错，不重建。清配对保留码，卸载/清应用数据不承诺延续。
- **`previousPairingId`（可选）= 重新配对同一台电脑时手机自报的旧配对标识**。电脑侧据此找到上一次的设备行并写一条**替换它的新行**：换密钥、换令牌、换 `pairingId`，**保留首次配对的 `pairedAt`**；旧行留到新身份连上再裁。于是同一台手机反复扫码不再攒行（2026-10-17 用户："为啥每次扫都是一个新设备"）。
  - 它**不是认证凭据**：授权完全由一次性二维码秘密 + 候选持钥证明完成（第 6 条的判据在此之前已经跑过）。它只是**行定位符**，且只在 `pair-commit` 的密文里过线（中转不可见，I10）；换票请求是匿名的，绝不能把它放进去。
  - 没有旧行（首配、手机凭据丢过、那行被管理面删了）就照旧写新行。**停用过的旧行也允许被替换** —— 重新扫码本身就是恢复路径，新行天然不带吊销标记。
  - 登记将“找旧集合 → 原子写新行 → registered”串行执行；新行带登记时已存在的旧身份集合快照 `replacesAll`，兼容旧 `replaces` 关系。集合按全长设备码及精确旧定位信息取得，`pairedAt` 只作展示，不作为代次顺序。**只写新行、旧行先留着**（轮换窗口两把令牌仍有效）。旧行仅在**新身份正式握手成功且当前行仍有效**时裁；裁剪只按当代快照，旧重连不得动态扫描同码去删除后来登记的身份。旧格式缺快照才沿已存 `replaces` 链传递。（`pairing-endpoint.ts` 的 `replacedRowsOf` + `index.ts` 的 `pruneReplaced`）。理由：`pair-result` 可能到不了手机，那时手机手里仍是旧凭据 —— 旧行提前删掉就成了孤儿（下次握手 `protocol/not-paired`，手机按契约清凭据，用户看到"凭据莫名失效"）。取舍见 `.agents/notes/implemented/2026-10-28-atomic-repair-keeps-old-device-row.md`。
  - 旧定位从二维码钉死的电脑 Ed25519 公钥对应槽读取，并核对 `pcId`；清槽前将非凭据 hint 持久保存，重启仍可读取，不恢复密钥或令牌。
  - 威胁模型：设备码与旧 `pairingId` 都可被已知定位信息的提交者自报，但仍需一次有效扫码（物理接触电脑屏幕）才能提交，而能提交的人本来就已获得授权（今天他会得到一条新行）；`previousPairingId` 只把"新增一行"变成"替换旧行"，效果是旧手机被踢下线（可恢复、管理面可见）。取舍全文见 `.agents/notes/implemented/2026-10-17-repair-replaces-device-row.md`。
- 设备公钥、设备名与 ID 来自已认证的连接候选，不重复信任提交载荷中的自报身份。
- 电脑确认邀请尚有效、秘密正确、候选身份一致后，原子地认领这次授权。不同候选不能消费已被认领的邀请。
- 正式 `pairingId` 沿用 `pairingIdOf(sha256(code))`，只作为正常业务握手派生上下文，不作为配对授权凭据。
- `pair-result`：`{ v: 1, t: 'pair-result', id, fc, box }`，密文包含成功/失败结果；成功字段为设备 ID、电脑 ID、设备令牌、刷新令牌与辅助 SAS。**刷新令牌只存不用**：轮换流程本期不做（设备令牌长期有效，轮换 = 重新扫码），理由与代价见 `.agents/notes/implemented/2026-10-09-token-and-scope-decisions.md`。
- 现有六位 SAS 仅作辅助显示。安全性来自二维码固定的电脑身份、候选持钥证明和秘密验证，不依赖可离线枚举的六位公钥哈希。

## 6. 一次性、重试与失败

- 错误秘密/身份不一致：拒绝且不登记设备，不消费合法邀请。
- `previousPairingId` 形状不合法（非 43 字符 base64url）：拒绝（`invalid`）—— 静默忽略会让"替换旧行"悄悄退化成"又攒一行"，而用户看不到任何原因。
- 过期/重新出码：旧邀请失效；显示重新出码，不静默切换身份。
- 同一个有效邀请、同一候选身份重复提交：合流到同一提交结果，不重复写设备、不重新生成令牌；**替换也是幂等的**（旧行只删一次）。
- 电脑在邀请的有效窗口内保留完成结果，仅同一候选通过新的持钥证明及秘密检查后可恢复结果。缓存不作为永久设备真值。
- 写库失败：明确报未保存，不返回成功，旧授权保留；同一授权重试沿用已捕获的登记计划，不临时重算另一套旧集合。
- 配对与设备管理回执以本地持久提交为完成点，名册仅后台调度。已写库但**名册上报**失败：**不是配对失败**。设备行已落盘、令牌已签发，名册会在下一次连上中转时整份重放；中转侧那段时间只会说 `device-unknown`（手机提示"稍后重试"，不必重新配对）。纯局域网配对根本没有中转，这条上报必然失败。
- 已写库但**回执**没送到手机：保留可恢复结果，报告阶段与不确定性；不可把超时当回滚，亦不可偷偷轮换凭据。
- 电脑重启使未完成的临时配对状态失效。已正式落盘设备仍可正常认证；无法恢复的未完成尝试明确要求重新配对。
- 断开/取消时清理候选连接、定时器与敏感临时数据，不能取消其他设备的连接。尚未完成升级的 WebSocket 取消必须终止在途拨号并立即释放调用方；不得等待未就绪 sink 的关闭回执。迟到的拨号结果无权重新订阅或启动握手。

## 7. 安全回归

必须覆盖：只有公开邀请或旧哈希不能配对、替换任一公钥/上下文失败、未确认不入库、候选不能调用业务、秘密与令牌不出现在中转明文、重复提交不换令牌、回执丢失的恢复、过期与写库失败、两设备互不干扰、旧连接不能干扰新代次。正常业务的跨端向量与既有恢复 fixtures 继续成立。

局域网直连追加：没有中转时出码与配对照样成立、`?pair=` 与候选 `offerId` 不一致不按配对建、过期/被新码顶掉的邀请连不上（判据是 `pairing.allows`，不是 URL 里有 `pair`）、解不出的候选不静默拼一个出来、配对之后同一监听面认得这台设备（普通直连）、接受来的连接断开后不留定时器。

重新配对（`previousPairingId`）追加：泄露旧标识的重放**不能越权**（仍需一次有效扫码，而能扫码者本来就能配对）、替换不破坏可用性（旧行留到新身份握手成功；提交这一步不删行）、停用的旧行也可被替换、`previousPairingId` 不进换票请求（中转明文不可见）、形状不合法被拒而非静默忽略。
