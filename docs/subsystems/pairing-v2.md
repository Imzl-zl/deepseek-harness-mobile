# 首配 v2 与独立数据连接

本文件承载 `remote-channel.md` §2、§12.1 的配对与连接隔离细节。业务会话信封仍为 v1；二维码/首配载荷为 v2，旧明文 `pair` / `pair-ack` 不再允许。

## 1. 不变量

- 二维码是电脑身份与配对秘密的唯一带外来源。中转只知道公开 `offerId`，不知道秘密 `code` 或可直接用于授权的替代凭据。
- 配对候选不是已配对设备。候选只有完成本次连接的持钥证明后才能提交秘密；提交正确秘密且用户已确认后才写正式设备表。
- 同一条数据连接只对应一个设备、一个连接代次。握手、AEAD 密钥、`fc`、流控和订阅不得跨连接共享。
- 中转只做连接路由。它不能通过修改候选公钥、设备 ID 或连接代次让电脑授权另一台设备。
- 所有长期令牌只在电脑/手机端以明文使用，配对回执端到端加密；中转名册只存摘要。
- **中转永不签发设备令牌**：它只签连接器令牌。设备令牌由电脑侧签发、摘要经 `POST /devices` 进名册 —— 转发器不该能凭空造出"我是某台设备"的凭据。摘要表里出现 `device` 条目时中转**拒绝启动**（那种配置"起来了也谁都连不上"：设备 403、电脑侧一切正常，比起不来难查得多）。`--issue-token` / `--revoke-token` 因此只认 `connector`。
- 传输断开不代表写入回滚。最后回执丢失时显示“结果待确认”，不能假报“未配对”。

## 2. 连接拓扑

- `/ws/connector`：连接器令牌认证的控制连接，每个连接器一条；不承载设备的业务帧或 E2EE 握手。
- `/ws/device?ticket=…`：手机连接。票绑定连接器、设备公钥标识、用途（`paired` / `pairing`）与候选元数据。
- `/ws/connector?dev=<deviceId>&channel=<channelId>`：电脑为该设备建立的数据连接。中转同时校验连接器身份、票绑定的归属、目标设备和当前连接代次。
- 中转为每次手机连接生成新 `channelId`；通过控制连接通知电脑创建/关闭对应数据连接。
- 控制消息为 `relay.open` / `relay.close`，只含路由元数据与候选公钥。配对秘密、方法名与业务内容不得进入控制消息。
- 数据路径逐条双向转发，不按 `sid` 广播，不按请求 `id` 猜回程。`credit`、`ping`、`res` 与事件共用同一条已绑定数据路径。
- 等待电脑数据连接时只暂存有界的首批帧；超限或连接建立超时即明确关闭。
- 替代连接出现后，旧连接的收帧与关闭回调都无权改动新代次。任一数据端断开关闭配对的另一端；控制连接断开关闭它的数据连接，客户端正常重连。
- 中转清空重启后，电脑控制面重放已配对名册；手机重新换票、重新握手。旧密文不跨密钥代次重放，业务恢复由电脑的会话序号与快照负责。

## 3. 二维码与发现

二维码包含：`{ v: 2, relay, pcId, pcPubEd, pcPubDh, offerId, code }`。

- `offerId`、`code` 分别独立生成 16 字节随机数并编码为无填充 base64url；两者不可相互推导。
- 有效期沿用 5 分钟。电脑同时只保留一份当前出码状态；重新出码使旧的未完成尝试失效。
- 电脑保存 `code` 的 SHA-256 校验值，**不向中转登记该校验值**。
- 出码向中转登记 `offerId`；登记失败不能向用户提供可用二维码。
- 首配换票请求为 `{ v: 2, offerId, devPubEd, devPubDh, name }`。公钥必须是 32 字节十六进制，名字有长度上限；设备 ID 由公钥按现有规则派生，不接受请求方任意指定。
- 换票只查询公开邀请并建立候选，不消费电脑的配对秘密。候选数量、换票频率和寿命有界；无效试探不能使真正的扫码设备失去授权机会。
- 生产地址只接受 HTTPS/WSS。明文仅用于显式开启的本机调试，不允许在 release 中放行。

## 4. 受限配对握手

复用现有 `hello → hello-ack → confirm` 的签名、DH 派生与 AEAD 实现，不新增另一套密码学。

- 正常设备的 `peerOf` 仍只查正式设备表。
- 配对用途的 `peerOf` 只返回本连接绑定的候选公钥；不得写正式设备表，也不得触发普通业务的 `deviceEstablished`。
- 手机的电脑公钥和 `pcId` 固定来自二维码。中转下发的候选信息不是信任来源。
- 配对认证上下文为固定字段顺序：用途/版本、`offerId`、`pcId`、电脑两把公钥、设备 ID、设备两把公钥、设备名的 SHA-256。上下文纳入签名 transcript。
- 配对密钥派生使用独立的 `dsh-mobile/v2/pairing-keys|` 域，临时配对标识使用 `offerId`；正常业务的 v1 派生不变。
- 握手结束只表示“配对加密可用”，不表示业务授权。该连接仅允许加密的保活/流控与 `pair-commit`，其余业务请求一律拒绝。

## 5. 用户确认与提交

手机流程：解析二维码 → 验证电脑身份并建受限连接 → 显示电脑身份和授权说明 → 用户确认 → 加密提交 → 保存凭据 → 正式连接。

- 用户确认前不发送秘密、不创建有效设备记录、不签发长期令牌。
- `pair-commit`：`{ v: 1, t: 'pair-commit', id, fc, box }`，密文载荷为 `{ v: 2, offerId, code }`。
- 设备公钥、设备名与 ID 来自已认证的连接候选，不重复信任提交载荷中的自报身份。
- 电脑确认邀请尚有效、秘密正确、候选身份一致后，原子地认领这次授权。不同候选不能消费已被认领的邀请。
- 正式 `pairingId` 沿用 `pairingIdOf(sha256(code))`，只作为正常业务握手派生上下文，不作为配对授权凭据。
- `pair-result`：`{ v: 1, t: 'pair-result', id, fc, box }`，密文包含成功/失败结果；成功字段为设备 ID、电脑 ID、设备令牌、刷新令牌与辅助 SAS。
- 现有六位 SAS 仅作辅助显示。安全性来自二维码固定的电脑身份、候选持钥证明和秘密验证，不依赖可离线枚举的六位公钥哈希。

## 6. 一次性、重试与失败

- 错误秘密/身份不一致：拒绝且不登记设备，不消费合法邀请。
- 过期/重新出码：旧邀请失效；显示重新出码，不静默切换身份。
- 同一个有效邀请、同一候选身份重复提交：合流到同一提交结果，不重复写设备、不重新生成令牌。
- 电脑在邀请的有效窗口内保留完成结果，仅同一候选通过新的持钥证明及秘密检查后可恢复结果。缓存不作为永久设备真值。
- 写库失败：明确报未保存，不返回成功。
- 已写库但名册上报/回执失败：保留可恢复结果，报告阶段与不确定性；不可把超时当回滚，亦不可偷偷轮换凭据。
- 电脑重启使未完成的临时配对状态失效。已正式落盘设备仍可正常认证；无法恢复的未完成尝试明确要求重新配对。
- 断开/取消时清理候选连接、定时器与敏感临时数据，不能取消其他设备的连接。

## 7. 安全回归

必须覆盖：只有公开邀请或旧哈希不能配对、替换任一公钥/上下文失败、未确认不入库、候选不能调用业务、秘密与令牌不出现在中转明文、重复提交不换令牌、回执丢失的恢复、过期与写库失败、两设备互不干扰、旧连接不能干扰新代次。正常业务的跨端向量与既有恢复 fixtures 继续成立。
