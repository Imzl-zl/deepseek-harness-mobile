# 事故:按"当前离线"批量硬删设备,把用户自己那台一起删了

日期:2026-10-15
影响:31 条设备记录被硬删除(含用户当时正在排查重连问题的手机);该手机陷入"一直显示重连、
找不到重新配对入口",只能重新扫码
性质:破坏性操作事故 —— UI 文案缺陷在前,自动化误点在后

## 发生了什么

真机排查连接问题时,用 chrome-devtools MCP 的 `evaluate_script` 点了插件面板的
「清掉当前离线(31)」。该按钮走 `removeScope('offline')`,**硬删除**当前离线且未停用的
设备记录;`window.confirm` 被自动接受(`evaluate_script` 的 `dialogAction` 默认 accept)。

`~/.dsh/storages/dsh_mobile_core.json` 的 `devices` 表从 31 行变成 **0 行**
(硬删除抹行;吊销只标 `revokedAt`、行还在)。

用户的手机当时正处于"连上 → 断开 → 一直重连"的排查中,**是离线态**,于是被这条筛选条件命中。
删除后名册重报,手机 `/ws-ticket` 拿 401 → 换票失败 → 进退避重连,永远转圈;而 ChatPage
没有重新配对入口(唯一出口在抽屉连接行,从 ChatPage 数要 3 步),用户原话:
"一直显示重连,我想重新扫码连接也不行,因为一直显示重连,进不去页面"。

## 为什么造成损失(按贡献排序)

1. **按"当前离线"批量硬删,人口专门命中"暂时离线但还在用"的设备。**
   服务端跳过"在线"保护不了它 —— 用户排查重连时,他的手机正是离线态。
   (标签本身没有撒谎:它确实删当前离线设备。骗人的是** blast radius 没说**。)
2. **确认文案张冠李戴,且不说后果。** 确认框写「真删除 {n} 条**已吊销**记录？」,
   而实际删的是**离线(未吊销)**记录;两个按钮都没说"那台手机需要重新配对"。
   DSH 插件管理器的 `confirmUninstall` 是连后果一起说的:「卸载后它提供的功能会消失。」
3. **破坏性操作走 `window.confirm`。** 浏览器原生对话框,`evaluate_script` 一次点击就穿窗而过。

## 为什么之前没发现

- 那 31 条记录本身就是反复真机联调的累积(每次扫码都换新身份 → 新行),
  "清掉它们"看起来是无害的清理。
- 单测覆盖了路由的形状,没有覆盖"这个按钮在用户自己的手机离线时会不会删到它"这一类后果。

## 结论(已沉淀成规则)

1. **破坏性操作的确认对话框必须是页面内的、逐动作正确文案、必带后果**
   (照 DSH `confirmUninstall` 的形状),不用 `window.confirm`。
2. **按状态批量硬删的 scope 不得包含"当前离线"** —— 它命中"暂时离线但还在用"的设备;
   要删具体的几台用多选。
3. **真机/浏览器自动化点破坏性按钮前必须显式 `handle_dialog(dismiss)`**;
   chrome-devtools 的 `evaluate_script` 默认 accept 对话框。
4. **恢复路径必须可达**:任何界面状态下用户两步内能走到"重新配对",写不成断言不算做完。
